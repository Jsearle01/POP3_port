### 3 — Reasoning

#### 3A — What the disk actually costs

`probe_loads` only ticks on completion, so every previous disk figure in this project
was inferred from tracks × seconds-per-track. Two taps measure it instead. A read tap
on the WD1773 data register (`$FF4B`) sees every byte the controller moves —
including DECB's boot `LOADM`, which the engine's counter cannot see because the
engine is not running yet. A write tap on DSKREG (`$FF40`) brackets each operation
from drive-select to `clr DSKREG`.

```
transfer        2.80 s   39,168 bytes in 12 bursts
drive engaged  17.20 s   8.20 boot+bundle | 3.00 splash | 3.00 prolog1 | 3.00 prolog2
```

A 4,608-byte track transfers in 0.20 s — one disk revolution, the floor. Within one
2-track read: **0.80 s lead-in, 0.20 transfer, 1.00 s between the two tracks, 0.20
transfer, 0.80 s release.**

Three consequences:

1. **Compression is spent.** P3.12's report §8 and my advice to Jay both ranked
   further compression highly. At 2.80 s of transfer it is not: squeezing both
   prologue screens into one track each would save ~0.4 s, not the ~2.6 s I told Jay
   when the estimate came from tracks × 1.31 s.
2. **Prefetch is worth ~6 s, not ~18 s.** I gave Jay 18 s; that figure predated
   compression, which had already taken most of the same prize. The two optimisations
   were competing for one pot and I ranked them as if they were additive.
3. **A 1.00 s gap between consecutive tracks of the same read is unexplained.** At
   300 RPM that is five revolutions to reach the very next track, on a DMK authored
   at interleave 0 specifically so it would not. It is the largest single recoverable
   item (~3 s across the intro) and I do not know its cause. [Authority: trace.]

#### 3B — The .hdv does not write back (oracle target)

A 137 s operator run at 100.00% speed left the scratch copy byte-identical to the
Phase 0 reference `c4f0b13e49b77dd0fbc5063e27e53a24`. So the CFFA2 `.hdv` mount does
**not** behave like the coco3 side's JVC `.dsk`, which MAME saves back unbidden
(coco3 idiom 24) — an assumption easy to carry between targets and wrong here.
Recorded with its limit: one intro run did not write, which is not proof the image is
never written.

#### 3D — The wipe: what it is, and the three ways to build it

`MASTER.S:846` — `Prolog1` is `lda #pacProlog / sta RAMRDaux / jsr DblExpand`, with no
page flip. `UNPACK.S:246` — `DBLEXPAND` jumps straight to `WipeRgtExp`:

```asm
WipeRgtExp lda #0
           sta XClmPos
:Loop      lda #0 / sta YScrPos / jsr ExpandClm   ; one column, top to bottom
           lda #1 / sta YScrPos / jsr ExpandClm
           inc XClmPos
           lda XClmPos
           cmp #80
           bne :Loop
```

80 columns, left to right, each expanded into the page being displayed. **The sweep is
the decompression order made visible** — no separate routine, no timing loop. It takes
as long as expanding takes, which is the ~101 frames our beat table already budgets.
[Authority: source, prompted by Jay's live observation.]

**Scope.** `DblExpand` serves `unpacksplash`, `Prolog1`, `Prolog2` and the epilog, so
every whole-picture beat wipes in — splash, both prologues, and the reprise (via
`SilentTitle`'s `unpacksplash`). Captions use `DeltaExpPop` onto the hidden page and
flip, which P3.3's trace independently confirmed and which our port already matches.
`DELTAEXPWIPE` exists as a vector and is never called in this tree.

**What the port does.** `sq_beat` runs `load_screen` (read + `lz_unpack` into the back
buffer), `HAL_gfx_swap`, then `hold_frames(beat_pre)`. Right duration, wrong
appearance. **P3.8 knew** — the beat table comment beside the constant 101 says "the
oracle spends these wiping the picture in over the splash" — and implemented a pause.

**Jay's "the border is left untouched", measured.** Splash vs prolog1, the bytes that
differ are **columns 10–148, rows 0–169** of 160×192. Columns 0–9 and 149–159 never
change: they are the +20 px centring margins, which have no counterpart on the Apple
II, where 80 columns is the whole active width and everything outside is physical
screen border. Rule for the build: **the sweep covers the centred 140-byte content
region and leaves the margins alone.**

**The obstacle.** The oracle has one page and destroys it in place, its source being
the small compressed stream. We have two buffers and the HAL maps only the *back* one
into the draw window; `gfx_map_blocks` is HAL-private. A wipe therefore needs either a
way to write the displayed buffer, or room for two full images plus a composite.

| | extra RAM | 128 KB | principal risk |
|---|---|---|---|
| **A** decode column-ordered straight to the visible page | none | ✓ | assets stored transposed; LZ back-references must resolve in stream order, destroying the `lda ,y+ / sta ,x+` inner loop (decoder is ~680 ms/screen today) |
| **B** decode as now, blit column-by-column into the front buffer through `$FFA2` | none | ✓ | a column is 192 bytes at stride 160 spanning all four blocks; boundaries fall mid-row (8192/160 = 51.2 rows) |
| **C** composite in the back buffer, flip every frame | +32 KB bank | ✗ | needs a second bank — free at 512 KB (48 blocks spare), impossible at 128 KB; each frame must copy *two* frames' worth of columns, since the written buffer is two flips stale |

**Recommendation: (B).** It keeps 128 KB, needs no asset change, and its difficulty is
bounded fiddliness rather than a rewrite of the decoder's hot loop. (C) is materially
less code if the wipe may be 512 KB-only — a product decision, not a technical one.

**Order of work: the wipe BEFORE prefetch.** Prefetch assumes the picture arrives by
swap; a wipe means it does not. They remain compatible, but the wipe settles *where
the decoded bytes must live*, after which prefetch is "put them there earlier" — which
is closer to the oracle, since it batches all loading up front and runs the sequence
with the drive untouched.

**A missing number.** Beat PREs are 99 (splash), 101 (prolog1), **0 (prolog2)**, 178
(reprise). Prolog2's is 0 because the oracle's gap there is the `PrincessScene`
cutscene we have not built, so **no oracle-derived duration exists for prolog2's
wipe.** It must be traced or chosen, and choosing is the Orchestrator's call.

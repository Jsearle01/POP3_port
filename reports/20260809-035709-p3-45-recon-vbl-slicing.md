cl_tick:  dec  <cl_dwctr        ; per VBL
          beq  cl_advance

All three of its per-VBL ticks are that shape; the scroll steps on `S4_KFRAMES equ 4`. The "chunking" in the

### 3 — Reasoning

#### 3A — §1: why does the port redraw every frame? Nothing makes it.

The question was asked as *why must it*, so here is what was checked and what each turned out to be.

**The loop draws unconditionally.** `cutscene_room.s:288-308`:

```
room_loop
        jsr     flicker                 ; unconditional
        jsr     HAL_time_frame_count
        jsr     [CHARS_TAB]             ; chars_frame — unconditional
        jsr     HAL_gfx_swap            ; waits for VBL, THEN flips — unconditional
```

**The cadence gate exists and is applied one level too shallow.** `chars_frame` calls `vm_nextframe`
(*"the DECIDE half"*) then `vm_frameadv` (*"the DRAW half"*). `vm_nextframe` compares `vm_now` against
`vm_due` and returns at `vn_hold` when the step's frames have not elapsed — **so the VM already knows the frame
is a no-op, and `vm_frameadv` runs anyway.** Karateka's `cl_tick` puts the identical test one level out, in
front of the render, and returns.

**Is it the peel?** No. The state is already per (character, slot): `ch_last` holds x/y/w/h *that buffer* last
saved, `ch_drawn` the cel *that buffer* last drew, `ch_seen` a bit per (character, buffer). A buffer redrawn
after an arbitrary gap erases with what **it** saved. **The state an irregular redraw cadence needs is already
there** — it was built for the every-other-frame case, and nothing in it assumes the gap is exactly two.

**Is it the double buffer?** No. Flip-on-change leaves the displayed buffer showing the newest state and the
back buffer one change behind, which is the case the per-slot state already handles.

**Is it the HAL?** **This is the one that looked like a real constraint, and it is not.** `cutscene_room.s`
states: *"The oracle avoids this by drawing its flames straight onto the displayed page (`lay`, a direct hires
call) and never flipping for them; our HAL maps only the back buffer, so the port flips instead."* The first
half is true (P3.44 §3F read it in the oracle). The second half is true of the **per-frame path** and false of
the **HAL**:

- `HAL_gfx_mirror` (`gfx.s:611-635`) *"maps BACK low and FRONT high, as one critical section."*
- It refuses only when `HAL_gfx_cur_words > GFX_MIRROR_MAX` (8,192) — *"16-colour: no room for two at once."*
- **The 4-colour mode is 15,360 B = 7,680 words**, under the limit — and `room_ready` takes the mirror path
  (`bcs room_mirror_slow ; 16-colour would refuse; this is not`), which the room suite exercises on every run.

**So the answer to §1 is: nothing compels it.** The every-frame redraw is how the loop was written, and the
comment that reads as its justification describes a limitation the HAL does not have.

#### 3B — §2: Karateka's slicing, searched exhaustively and not found

Per CLAUDE.md §2A.4, absence is claimed only after enumeration. Surfaces searched across the whole Karateka
tree: `slice` / `band` / `chunk` / `budget` / `quota` / `deadline`; `resume` / `partial` / `remaining` /
`pending` / `work queue` / `scheduler`; `split across frame|vbl`, `carry.*next frame`, `defer.*next frame`;
`twelve` / `12 (slices|slots|buckets|parts|steps)`; `no slice` / `exceed 100`; and every `*_tick` entry point
in `src/engine`.

**What exists instead — a cadence gate on the render, in all three controllers:**

| | gate | on expiry |
|---|---|---|
| `climb_controller.s:54` | `dec <cl_dwctr / beq cl_advance / rts` | `cl_load_dwell` + **`cl_render`** |
| `sprite_engine.s:69` | `dec <eng_cadctr / bne eng_tick_done` | reload + **`eng_render`** |
| `princess_controller.s:185` | per-state cadence | render |
| `scene4_scroll.s:39` | `S4_KFRAMES equ 4` — *"VBL frames per step"* | one scroll step |

Dwell values are in VBL units and are per-pose (`climb_controller.s:11-16`: 21, 7, 7, 7, 7, 7). **On a non-step
VBL Karateka executes `dec`, `beq`, `rts`** — about 15 cycles against our 57,074.

**The scroll's "chunks" are not slices.** `scene4_scroll.s:161-203` chunks a bulk copy *"across MMU pages via
the `$4000` window"* — an address-space limit (`$2000 - coff`), not a time budget.

**Reported as Karateka's mechanics, distinct from what we would adopt** (§2G): Karateka gates rendering on a
per-pose dwell table of its own devising. **We would take the mechanism — gate the render, not just the
decision — and set the cadence from the POP oracle** (§3E), not from Karateka's numbers.

**One further thing Karateka already has that we do not:** `cl_init` calls `cl_save_clean` **once**, and
`cl_render` calls `cl_restore` — *"clean-restore the bbox in the BACK buffer"*. **That is P3.44's Option 1 —
restore from a clean snapshot, with no per-frame save — already implemented in the sibling.**

#### 3C — §3: the flip, and why pass order survives

**Karateka flips inside `cl_render`, after the blits** — the render restores, blits every part, *then*
presents and toggles. So the flip cannot land mid-sequence: **it flips only when a complete frame's work has
finished, and the display shows the previous complete frame meanwhile.** That is the answer to the dispatch's
central question, and it is answered by there being no partial work rather than by machinery that guards
against it.

**Consequently our three passes survive, and not narrowly.** Change-gating does not subdivide a redraw; when a
redraw happens, `vm_frameadv` runs erase-all → save-all → draw-all exactly as today, and the flip follows. **No
buffer can be presented with erases done and draws pending, because nothing interrupts the sequence.**
P3.32's invariant — *all saves complete before any draw begins* — is untouched: it is a property of
`vm_frameadv`'s three `ch_pass` calls, and change-gating does not enter `vm_frameadv` at all.

**The risk the dispatch named is real, but it belongs to slicing.** If the six blits were distributed into
per-VBL buckets with a flip on a bucket boundary, a buffer *could* be presented erased-but-not-drawn. **Nothing
in the tree does that and nothing in this report proposes it** — which is worth stating plainly, because the
dispatch's framing assumed slicing was the model and it is not.

#### 3D — §3/§4: what actually changes, measured — and a unit bug found doing it

`harness/tools/change_census.lua`, live-disk, frames 1900-3400. Detection is from the engine's own stores, not
re-derived: `std vm_due` (reached only on a step boundary) for the VM; `sta fl_state0` (only when `fl_step` is
set) for a torch; and the star **lit mask** sampled per iteration — `star_cnt` is decremented every frame a
star is lit, so counting its writes would count *ageing*, and only the lit/dark flip reaches the screen.

```
694 iterations over 1498 video frames (2.159 frames/iter)
VM stepped      in 478 of 694 (68.9%)
a torch stepped in 231 of 694 (33.3%)
a star changed  in  13 of 694  (1.9%)
NOTHING CHANGED in 128 of 694 (18.4%)   <- the skippable ceiling
  --- 128 (18.4%)   -F- 81   -FS 7   V-- 335 (48.3%)   VF- 137 (19.7%)   VFS 6
```

**Naive change-gating is worth 18.4%** — ~46,700 cy average, **157% of budget. Not 6×.** The composition says
why: the two animators are near-coprime and between them cover 81.6% of iterations.

**★ And the torch cadence is wrong, by the unit error P3.25 already fixed once.** `flicker` opens with
`dec fl_div` and `flicker` is called **once per loop iteration**, not once per VBL. Measured: a torch step
every **3.0 iterations** (= `FLAME_DIV equ 3` ✓) × 2.159 frames = **6.48 video frames = 9.25 Hz**, against the
constant's own comment: *"FLAME_DIV equ 3 ; ~20 Hz, the oracle's SPEED-7 cadence."* **20 Hz is what 3 gives if
one iteration is one frame** — which was true when it was written, before the character draw pushed the
iteration to 2.16 frames.

`vm_nextframe`'s header describes the identical bug being fixed for the VM: *"The old version decremented a
counter once per call, which is once per LOOP ITERATION — and P3.25 measured 0.84 iterations per video frame,
so a 2.60-iteration step took 3.09 frames."* **The fix was applied to the VM and not to the flames.** Fifth
instance of *an assumption true when written can silently become false*, and a second instance of *a lesson
recorded is not a lesson applied.*

#### 3E — §3: the target cadence, and PA.2's 6.0 is not it

The dispatch names PA.2's 6.0 frames as the specification. **Checked, and it is a measurement of a different
scene.** PA.2 §M2 derives it from PA.1's trace: *"738 page-flip events whose median interval is 6.0 frames"*,
and its cost model is *"a typical load (prince + 1 guard + 3 dynamic tiles)"* — **gameplay**, not the cutscene.

The oracle's measurements for **this** content, both already in the record:

| figure | value | provenance |
|---|---|---|
| cutscene SPEED-7 floor | **2.60 frames/step** | P3.23, measured on the oracle |
| cutscene achieved, animating | **3.9 frames/step** | P3.26, measured on the oracle |
| gameplay page-flip median | 6.0 frames | PA.2 / PA.1, measured on the oracle |

**Using 6.0 for this scene would multiply our budget by a factor measured on other content** — the same
dimensional substitution the dispatch's own standing invariant warns about, arriving from the other direction.
**The specification for this scene is 2.60 (floor) / 3.9 (achieved).** Both are measured; both are the
oracle's; neither is inherited.

**It fits, with margin, and P3.44's options 1-4 become unnecessary as budget fixes.** Option 1 (drop the save,
restore from a clean snapshot) remains worth having **for correctness rather than for cycles** — it is what
Karateka already does, and it removes the captured-state class that produced P3.21, P3.25, P3.28 and P3.32.

**What it would cost, stated as cost and not designed:**

1. **A cadence gate in front of the render** — the test `vm_nextframe` already computes, moved one level out.
2. **Torch drawing on the front buffer** — `HAL_gfx_mirror`'s both-mapped arrangement made available to the
   per-frame path. **The window is 32,768 B and two 4-colour buffers are 30,720 B**, so they fit, but what else
   lives in the window at `$8000+` has not been checked here.
3. **Fixing the flame cadence unit** (§3D) in the same change, or the torch rate shifts again the moment the
   loop gets faster — which is precisely what this change does.
4. **Tearing.** Drawing to a page being scanned out has no VBL protection. **The oracle accepted this for its
   flames**; whether it is acceptable here is Jay's visual gate and cannot be settled from source.

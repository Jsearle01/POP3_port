## (b) RND and RNDseed's initial value — INITIALISED (to 0), not uninitialised RAM

- RND GRAFIX.S:1386-1395 is exactly `RNDseed := (5*RNDseed + 23) mod 256` (asl/asl/adc/adc #23). Full period
  256 (c odd, a-1 divisible by 4). RNDseed = GAMEEQ.S:426 = $9E in the AUX zero page.
- Grep: the only instruction naming RNDseed that stores is GRAFIX.S:1394. **But the initial value comes from a
  block clear:** `INITSYSTEM` TOPCTRL.S:120-139 does `sta ALTZPon` (:121) then `ldx #0 / txa / :loop sta $0,x /
  inx / bne :loop` (:132-136) — the whole aux zero page, RNDseed included, is zeroed once at boot.
- Measured: the write tap on $9E caught that store — `R 141 00>00 pc=203D` ($203D = TOPCTRL.LST line 134) —
  and the first RND call (`R 2681 00>17`, from the cutscene play loop SUBS.S:879) starts from 00.
- Other writers of $9E seen: 84 writes from pc $D157 = rw1835.pop.LST:329 (`:zrest lda ZPAGEBUF,x / sta 0,x`,
  the disk driver restoring a zero page). **None changes RNDseed:** across all 4,038 RND writes the old value
  always equals the previous new value (`continuity breaks: 0`), and every one satisfies the LCG.
- Not uninitialised => no cost from garbage RAM. **The real cost is different:** the seed is never reset
  after boot, so the demo's seed is the product of every RND call since INITSYSTEM:
  - 2,341 calls before the demo's level write (1,118 torch flames in the cutscene via SUBS.S:333, 973 + 3x35
    pstars SUBS.S:376-385, 145 play loop SUBS.S:879) -> **seed CB at cycle 1's level-0 start (frame 7890)**.
  - Cycle 2 (same boot): **seed D6** at its start (F 18673). 4,041 RND calls per attract cycle (mod 256 = 201).
  - **Consequence, measured:** cycles 1 and 2 are identical through the walk (145 distinct kid states, K
    byte-identical) and the first 39 distinct states after the guard appears, then diverge at the kid's first
    random decision (cycle 1 F9254 vs cycle 2 F20027). Cycle 1 fight: 292 AI rnd calls, AutoCtrl to F10898;
    cycle 2: 128 AI rnd calls, AutoCtrl F19663..F20942. Both end with the guard dead (posn 185) and the kid
    running off. **Every attract cycle plays a different duel.**

## 4. Every RND call on the demo's path (measured, cycle 1, F7890..F10898)

Breakpoints were not needed: a write tap on $9E fires at `sta RNDseed` ($0A5C), and the caller is the return
address on the stack (RND is reached by `jsr rnd` -> `jmp RND`, or `jsr rndp` -> `jmp rnd`, so the top of
stack is always the real call site). Ordered list: `build/p535/summary.txt` ("AI rnd calls in order", 292
lines) and `oracle_rnd_trace.txt` (every call).

Counts F7890..F10898: **1,714 RND calls** = 448 MainLoop (TOPCTRL.S:367; one per game frame) + 950 torch
flames (GETFLAMEFRAME MOVER.S:1087 <- animtorch :1072; one per torch per game frame: **3 on screen 1, 2 on
screen 2, 2 on screen 4**) + 7 TRIGTORCH (MOVER.S:313; 3 at FirstFrame, 2 at each cut) + **292 AI**
(strikeprob 207, advprob 25, blockprob 24, impblockprob 21, restrikeprob 11, CHECKSTAB 4; gp 10: 141,
gp 11: 151). No other consumer on the demo path (no loose floors, no sword gleam, no pstars).

Per-game-frame order (fixed by NextFrame): MainLoop rnd -> torches (animtrans, TOPCTRL.S:506) -> kid AI
(DoKid) -> guard AI (DoShad) -> CHECKSTAB rndp. Example, game frame of F9244:
```
R 9242 F3>D6 r0=218F (MainLoop)   R 9242 D6>45 / 45>70 r0=F336<-F32C (2 torches)
A 9242 kid gp=10  R 9242 70>47 r0=57B4 (MaybeAdvance)   A 9243 guard gp=11  R 9243 47>7A r0=57B4
```

**Verdict: YES, the trace can serve as the AI's oracle,** with two conditions.
1. The call order is a pure function of state the port would have: game-frame count, torch count of the
   visible screen, cuts, and the two fighters' records plus refract/justblocked/gdtimer/EnemyAlert. Nothing
   timing- or disk-dependent touches RNDseed during the demo (the $D157 zero-page restores preserve it;
   continuity 0 breaks), and two independent boots gave identical records (320/320).
2. The seed is NOT reproducible from the demo alone — it is the boot history (CB in cycle 1, D6 in cycle 2).
   The port must either seed from a measured value at a defined checkpoint (e.g. CB at the level-0 start, or
   66 before game frame 180) and reproduce consumption from there, or accept a different (but equally
   faithful-in-kind) duel. Because every attract cycle already plays a different duel, matching cycle 1
   exactly is a TEST choice, not a fidelity requirement (§2I).
   A divergence of one game frame, one torch, or one AI branch shifts the 256-period stream and every later
   decision differs — so the oracle comparison is exact-or-nothing and makes a sharp test.

## 6. Proposal — the first AutoCtrl build dispatch (one page, no code)

**Build: "The guard goes en garde" — AutoCtrl for the screen-4 guard against a REPLAYED kid, over the
rnd-free window (game frames 180-217).**

Why this slice: it is the first point where AutoCtrl changes anything, it is deterministic (no random number
is drawn until game frame 218), and it exercises the real AI path (AUTOCTRL dispatch + timers, GuardProg ->
Alert -> DoEngarde, EnGarde -> InRange -> DoAdvance/DoStrike, the Do* latches) plus the GuardCtrl/FightCtrl
subset that turns latches into sequences. It needs none of items 1-2 above if the scene is SEEDED from the
oracle's state at game frame 179 — a divergence from the oracle's route that §2I permits for a test bed, to be
stated as such (Jay's call whether it ever ships).

Scope:
- Full 16-byte Char/Kid/Shad/Op records and Load/Save-with-Op, with DoKid-then-DoShad order.
- AUTOCTRL + GuardProg/Alert/EnGarde/InRange/GenFight/Maybe*/Do* transcribed, plus guardprog, refract,
  justblocked, gdtimer, alertguard, droppedout as globals. The oracle LCG `5x+23` as its own routine (not the
  cutscene's xorshift). The probability table (all 12 columns, 96 B).
- GuardCtrl + FightCtrl's advance/strike/block/retreat entries; the guard sequences reached in the window.
- The kid is NOT simulated: his per-game-frame record is replayed from the oracle trace (K= records,
  F8882..F9234) into Kid/Op. EnemyAlert is replayed too (log it — see below) rather than porting CHECKALERT.
- Screen 4 bake for the visual gate (or reuse screen 1's page with an explicit "wrong room" label).

**Discriminating test (25.1):** a harness check, like kidrun_plan.py's IDENTICAL line, that compares the
port's guard record (Posn, X, Face, BlockX, Action, Sword, Seq) after every game frame against the oracle's
S= record for game frames 180..217 — **byte-identical for all 38 frames**, and **zero RND calls** in the
window. Two independent derivations: a host-side Python transcription of the same routines must also walk
identically. Negative control: start with guardprog forced to 0 or EnemyAlert forced to 1 and show the check
FAILS (the guard must then stay put), so the test cannot pass vacuously.

**Prerequisite instrument (a recon step inside the dispatch):** extend oracle_rnd_trace.lua to dump, at game
frame 179, every variable in §2's table (refract, justblocked, gdtimer, alertguard, droppedout, offguard,
EnemyAlert, strengths, guardprog, RNDseed) — and EnemyAlert per frame — so the seed state is complete.

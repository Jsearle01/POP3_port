### 1 — Summary

**The contract is adopted, assembles, and does not regress P1.1 or P1.3.** All 10 HAL files were copied
**byte-identical**; the only edit anywhere is a 2-line `ifdef`/`endc` guard in `gfx.s`.

**The headline classification: POP's dormancy is 77% of the HAL's code.** The runtime masked blit —
`HAL_gfx_blit_sprite`, `_opaque`, plus four undeclared variants — measures **1,231 of 1,609 bytes**. PA.6
ruled that blit INFEASIBLE for POP (5.4× the assumed cost) and PA.7/PA.9/P1.3 replaced it with compiled
sprites. So it is guarded dormant: **391 B built vs 1,622 B with `-DPOP_HAL_RUNTIME_BLIT`**. That measurement
is why the guard exists rather than a note in a table — leaving it assembling is not free.

**The audit found the "29-function contract" is a declaration, not an inventory** (§3.2). `hal.inc` declares
29; **only 16 are implemented**. `debug.s` is referenced by `hal.inc` three times and **does not exist**. And
`gfx.s` implements **4 entry points `hal.inc` never declares**. None of this is wrong of Karateka — it is a
maturing HAL — but a report that repeated "29 functions implemented" would be false.

**Three rule-4 improvements FLAGGED, zero applied** (§3.4). All three are HAL-WIDE, i.e. they implicate the
shared contract and therefore Karateka; applying them to POP alone would fork it. Jay's call, both the
merits and the landing:
1. **`KCOCO3_INIT0_COCO3 equ $4C` is a live trap.** No code uses it; `gfx.s` writes a literal `$6C` precisely
   *because* `$4C` clears IEN and would kill the GIME VBL interrupt. A consumer who reaches for the named
   constant gets a silently dead VBL.
2. **`mem.s` ends with `end boot`** — a build directive naming the *engine's* entry symbol, inside a HAL
   module. Demonstrated failure: it is why the HAL would not assemble in POP, and why it must be last in the
   build list.
3. **`gfx.s` implements 4 entry points `hal.inc` does not declare** — the contract under-describes the
   implementation.

**Adoption surfaced 6 hidden couplings** (§3.3): the HAL reads six symbols declared in Karateka's
`src/engine/globals.s`, so it cannot assemble without engine-band declarations. Adopted at Karateka's exact
addresses into `hal_globals.s` — HAL band only; engine bands stay out of scope.

**File streaming: NAMED, NOT DESIGNED**, as directed — gated on the §5.34 disk-timing recon.

#### 3.2 — "29 functions" is a declaration count, not an implementation count
`hal.inc` declares 29 symbols. Counting actual entry points: gfx 5 declared + **4 undeclared**, time 4,
sound 1, input 2, sys 2, mem 1, file 1 = **16 of the 29 implemented**; 13 are stubs or, for the 3 debug
functions, have **no module at all**. Recorded because the dispatch's framing ("29 functions across 8
subsystems", superseding the doc's 27) reads as an inventory of working code, and it is not. Karateka's own
`hal.md §8` says "21", also stale. The *contract* is 29; the *implementation* is 16.

#### 3.3 — What adoption surfaced: 6 hidden couplings
The HAL does not stand alone. Assembling it in POP failed until six symbols declared in Karateka's
`src/engine/globals.s` were supplied:

| Symbol | Addr | Band | Consumed by |
|---|---|---|---|
| `hal_frame_hi` / `hal_frame_lo` | `$10`/`$11` | HAL | `time.s`, `irq_vbl.s` |
| `gfx_initialized` | `$12` | HAL | `gfx.s` |
| `page_register` | `$50` | **engine** | `gfx.s` (`HAL_gfx_present` reads it) |
| `PAGE_A_TOKEN` | `$20` | **engine** | `gfx.s` (`cmpa #PAGE_A_TOKEN`) |
| `s4_dest_row` | `$66` | **engine** | `gfx.s` (`HAL_gfx_blit_scroll`) |

Three sit in the **engine** band by `hal.inc`'s own DP policy, yet the HAL reads them — so the HAL cannot
assemble without engine-owned declarations. Adopted at Karateka's exact addresses into `hal_globals.s`
(diverging would fork the contract). Reported as an observation, **not changed**: making the HAL
self-contained would reshape the interface, which rule 2 forbids.

#### 3.4 — Rule-4 flags: three raised, zero applied, all HAL-WIDE

Held to the stated bar — a named failure, not a preference. Ranked by strength.

**FLAG 1 — `KCOCO3_INIT0_COCO3 equ $4C` is a trap. (Correctness hazard. HAL-WIDE.)**
`hal.inc:107` declares it as *the* `$FF90` INIT0 value. **No code uses it.** `sys.s:186` writes a literal
`$4C`; `gfx.s:143` writes a literal `$6C`, and gfx.s's own "IEN PRESERVATION NOTE" explains why: `$4C` has
IEN=0, and `HAL_time_init` needs IEN=1 for the GIME VBL interrupt, so gfx must not clobber it.
**Named failure:** a consumer who writes `lda #KCOCO3_INIT0_COCO3 / sta $FF90` anywhere after `HAL_time_init`
silently kills the VBL interrupt — no error, just a frame counter that stops. POP is exposed identically:
P1.1's probe needs IEN=1 for the `$FF92` VBORD latch. **Not applied.** A fix (rename to
`KCOCO3_INIT0_SYSINIT`, add `KCOCO3_INIT0_IEN`, or use the equates in both writers) changes the shared header,
so it implicates Karateka.

**FLAG 2 — `mem.s` ends with `end boot`. (Layering / build robustness. HAL-WIDE.)**
The last line of a HAL module is a build directive naming the **engine's** entry symbol.
**Named failure, demonstrated:** the adopted HAL would not assemble in POP —
`Undefined symbol boot` — and it forces `mem.s` to be last in the build list (Karateka's `build.bat:28` does
exactly that). A HAL module should not know the engine's entry point. **Not applied**; POP works around it by
leaving `mem.s` out of the build list, which is dormancy-by-configuration and costs only
`HAL_mem_size_detect` (a 3-instruction stub today).

**FLAG 3 — `gfx.s` implements 4 entry points `hal.inc` does not declare. (Contract drift. HAL-WIDE.)**
`HAL_gfx_blit_sprite_mixed`, `_masked`, `HAL_gfx_blit_stencil_punch`, `HAL_gfx_blit_scroll` — 849 B of real
code invisible to anyone reading the contract. **Named failure:** a consumer sizing or auditing from
`hal.inc` under-counts the HAL by 4 functions and 53% of its code. Weakest of the three (documentation drift,
no runtime consequence), raised because it is factual and checkable, not stylistic. **Not applied.**

**Deliberately NOT raised:** several places where I would have structured things differently (module
boundaries, comment-vs-code duplication of DP maps, the `disk_read.s`/`file.s` split). Those are preferences;
rule 1 says they defer to as-is silently, and they do.

#### 3.5 — Dormancy mechanism: a guard, not commenting-out
The rule says "comment out so they DON'T ASSEMBLE, but LEAVE THEM IN SOURCE". I used
`ifdef POP_HAL_RUNTIME_BLIT` / `endc` instead of prefixing every line with `*`. It meets all three stated
goals (does not assemble; stays in source; ready to re-enable) and additionally keeps the dormant bodies
**byte-identical to Karateka's** — literal commenting would touch ~500 lines and destroy that. Re-enabling is
`-DPOP_HAL_RUNTIME_BLIT`, no source edit. Surfaced in §6 as a deviation from the literal instruction.

### 6 — Reactive deviations

1. **Dormancy via `ifdef` guard, not literal commenting-out** (§3.5). The rule said "comment out"; a guard
   meets all three stated goals *and* preserves byte-identity of the dormant bodies, which commenting would
   destroy. Reporting the mechanism choice rather than assuming it was intended.
2. **`hal_globals.s` created — a file with no Karateka counterpart.** The HAL reads 6 symbols Karateka
   declares in `src/engine/globals.s`; POP has no engine and engine code is out of scope. Only the HAL-needed
   declarations were adopted, at Karateka's exact addresses. This is the one structural difference between
   POP's HAL and the sibling's, and it exists because POP is adopting the HAL *before* the engine.
3. **`mem.s` adopted but NOT built** (§3.4 flag 2). It is in source, byte-identical; it is simply absent from
   the build list. That costs `HAL_mem_size_detect` — a 3-instruction stub. Alternatives (editing out
   `end boot`, or inventing a POP `boot`) would reshape the module or write engine code.
4. **`src/harness/hal_build.s` created** to give `build.bat` something to assemble. Not engine code, no entry
   point, explicitly redundant once POP's engine includes the modules itself.
5. **The audit reports 16-of-29 implemented** (§3.2), which contradicts the dispatch's framing of 29 as the
   implemented contract. Surfaced rather than absorbed, because downstream planning that assumes 29 working
   functions would be wrong.

### 7 — Uncertainty flags

1. **No HAL function was EXECUTED.** This dispatch proves the HAL *assembles* and does not regress the
   existing harnesses. P1.1's probe and P1.3's compiled-sprite proof both carry their **own inline** GIME
   setup — they do not call `HAL_gfx_init`/`HAL_gfx_present`. So "the adopted gfx/time primitives still drive
   the harness green" is true only in the sense that nothing broke. **Re-pointing a probe at the HAL entry
   points is the real test and it has not been done.**
2. **Classification of the sound stubs is a judgement.** I marked all six AS-IS because they are stubs in
   Karateka too and PA.12 showed the shapes fit POP (`tone_start/stop` maps 1:1 to POP's `tone(pitch,dur)`).
   A defensible alternative is ADDITIVE — POP will need real implementations. I chose AS-IS because the
   *contract* transfers; only the bodies are missing, in both projects.
3. **`disk_read.s` (12.8 KB) was adopted but not analysed.** It contains no `HAL_` entry point and is not in
   POP's build. Whether it is the substrate POP's streaming File layer should build on is exactly the §5.34
   recon's question.
4. **The 4 undeclared gfx entry points may be intentional internals** rather than contract drift. They are
   named `HAL_*` and globally visible, which is why I read them as functions; if Karateka considers them
   private, flag 3 weakens to a naming observation.
5. **`hal_globals.s` fixes POP's DP addresses now.** If POP's engine later wants `$50`/`$66` for something
   else, it must move the HAL's consumers — a cost created by adopting HAL-before-engine.

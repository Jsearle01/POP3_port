### 3 — Reasoning

#### 3A — Phase 1: what was ruled out, and how

**Carried in from P3.22 (geometry, already eliminated):** both cels report `trim lead=0` so neither origin is
shifted; both have `Fdx=0`; both are 21 Apple px wide. A width- or facing-based origin rule would move them
together, which it cannot, because the vizier derives correctly from `CharX`.

I add one more elimination, and it is the load-bearing one:

**Mirroring cannot be the mechanism.** A mirror maps local column *k* to *W−1−k*. With W = 21 px, *W−1 = 20* is
even, so **parity is preserved under mirroring for these cels**. That matters because facing was the leading
hypothesis (both characters have `CharFace=−1`) and because `sprite_convert.py`'s own note says a mirrored cel
needs `--flip-parity` only "for even `width_pixels`". 21 is odd. So facing/mirroring is out on arithmetic, not
on inspection.

**Then the empirical route, and why it failed.** The authoritative test is the oracle's own rendering
(CLAUDE.md §2: trace over source). `probe_cel_parity.py` converts a cel at BOTH parities and matches it
against an oracle capture, scoring only opaque pixels.

**This probe is deliberately not the tautology P3.22 shipped.** Its reference is an oracle capture — produced
by the Apple II, not by our converter — so a wrongly-converted cel cannot match it. That is the corrective to
P3.22's worst finding, applied to the very next check I wrote.

Result: **no match anywhere.** Free search over rows 88–155 gave 67–75% of opaque pixels wrong at the best
fit for both characters. Testing the princess at her *exact* standing position (row 109, col 35, from
CharX=120) across **all 15 captures** gave a best of 60.7% wrong:

```
  capture                        as-CharX(EVEN)      flip(ODD)
  proom_f4200.raw                 269/ 298  90.3%  181/ 298  60.7%
  proom_f3000.raw                 260/ 298  87.2%  207/ 298  69.5%
  room_page1.raw                  257/ 298  86.2%  243/ 298  81.5%
  ...
```

60.7% wrong is not a parity disagreement — a parity error inverts orange and blue and would leave the shape
and the black/white pixels intact, scoring far lower. **This is a different cel, or a different position, or
both.** The captures containing characters are all mid-cutscene (`room_page1` is f4750, well past
`startP0`/`startV0`), so they hold whatever frame the sequences had reached, not `Pstand`.

**Conclusion:** the rule cannot be settled from the repo as it stands. Not because the method is wrong — the
method is right and is now committed — but because the reference image does not exist yet.

#### 3B — Phase 1: the cheapest next probe, precisely

One MAME run against the oracle, capturing at a frame just after `startP0`/`startV0`, and reading out of Apple
memory **at the same instant**:

- `CharX` / `CharY` for each character — so position is read, not assumed
- the current cel number — so cel identity is read, not assumed
- the hires page — the reference rendering

Then `probe_cel_parity.py` matches at the known position with the known cel. That yields the true `start_col`
for both characters in one run, and the difference between them *is* the rule.

**Two known hazards to respect** (both already in the idioms files): `mem:read_u8` honours the RAMRD soft
switch and POP sets RAMRDaux, so a naive read returns AUX — flip `$C002`/`$C003` before reading, as
`harness/tools/oracle_ram_dump.lua` does (P3.17). And 6502 read-taps silently false-0; watch the data, not the
code (idioms §1).

#### 3C — Phase 2: the conversion, and why no scaling factor is needed

`play` does `lda SPEED` / `jsr pause` [`SUBS.S:876-881`]. `pause` is a 3-byte load-time dispatch vector
[`GAMEEQ.S:315`], so its cycle cost is not readable from the source tree — which is fine, because the dispatch
asks for the **wall-clock** value and P3.17 already measured that on the running oracle.

**The measurement is sound because of what it measures.** P3.17 timed the gaps between torch-flame updates,
and the flames advance once per `play`-loop iteration — so the gap between updates *is* the `pause` period.
Measured: 2–3 frames under SPEED 7 (mean 2.6), 6 under SPEED 12.

**Frame periods, from the project's own constants:**

```
CoCo3 frame    16.683 ms   (29,859 cy at 1,789,772 Hz)   59.94 Hz
Apple frame    16.688 ms   (17,030 cy at 1,020,484 Hz)   59.92 Hz
ratio 1.00030
```

**So frame counts transfer 1:1.** This is worth stating because it removes a whole class of error: SPEED
expressed in Apple frames needs no conversion arithmetic at all, only a decision about rounding.

**And rounding is where the fidelity lives.** SPEED 12 rounds free (−0.03 ms). SPEED 7 does not: 2.6 frames is
43.39 ms, a constant 3 frames is 50.05 ms, **+15.3% too slow.** That is precisely the 20.0-vs-22.8 Hz gap
P3.17 recorded and carried as "constant-rate vs the oracle's variable cadence" — it now has a number and a
cause.

A **13/5 cadence (`3,3,2,3,2`)** gives 43.38 ms, within 0.01 ms, and reproduces the oracle's *observed 2–3
frame spread* rather than flattening it. The oracle genuinely varies; a fractional cadence is therefore more
faithful, not a hack.

**Per §10.3 I am not picking the convenient number:** the integer answer the dispatch asked for is SPEED 7 → 3
frames, and I am reporting its error as +15.3% rather than calling it good. The recommendation is the
fractional cadence, and the decision is Jay's.

**★ HIS DIAGNOSIS AT (4) IS CORRECT, AND IT IS THE ORACLE'S OWN DATA THAT SAYS SO** (§3C). `SUBS.S:306-307`:

```
ptorchx  db 13,25          ptorchoff db 0,6
```

The two torches sit at **different sub-byte offsets inside their Apple bytes.** Apple hires is 7 px/byte,
CoCo3 4-colour is 4 px/byte, and **7 does not divide into 4** — so their true CoCo positions land on
**different phases**:

| torch | oracle | true CoCo px | phase | drawn at | error |
|---|---|---|---|---|---|
| 0 (left) | 13×7 + 0 = 91 | **111** | **3** | 112 | +1 |
| 1 (right) | 25×7 + 6 = 181 | **201** | **1** | 200 | −1 |

**The flame cel was converted ONCE, at `start_col=91` — torch 0's alignment.** One cel set can only place both
torches on the *same* phase, which is exactly why correcting the right one necessarily moved the left one, and
why request (2) — *"change torch on right, leave left alone"* — **cannot be satisfied with the data in the
tree.**

**One refinement to the diagnosis: it is not a COLOUR problem.** Apple px 91 and 181 are **both odd**, so the
screen-column parity the converter keyed on (`converted.s`: *"start_col=91 screen-col parity=ODD"*) is
identical at both torches. **Purely alignment.**

**★★ AND (5) IS THE UNLOCK, MEASURED** (§3E). **The flames are the last compiled sprites in the tree.** P3.18
established compiled sprites as the memory problem — *"the same 49 cels are 11.9 KB as raw packed bitmaps and
100.8 KB as compiled code — 8.2×"* — and the **characters** moved to data-driven segment streams.
**The flames never did.**

| | |
|---|---|
| 9 flame cels as **data** (segment streams, replay-verified) | **675 B** |
| 9 flame cels as **compiled** | **2,163 B** |

Bundle free goes **184 B → 1,672 B**, and `blit_save`/`blit_erase` are already resident for the characters, so

blocker I reported dissolves — by finishing a migration the project already decided on and left half-done.**

### 3 — Reasoning

#### 3A — The anchors, derived fresh (CLAUDE.md §3)

§3 forbids reusing recorded coordinates for a spatial correction, so these were re-derived from the oracle and
cross-checked against the source's own comment, which turned out to record the same truth:
`TORCH1_COL equ 50 ; true px 201 -> byte 50.25, rounded`. **It had been rounded down — the pixel Jay saw.**
Reported to him for confirmation before executing, per §3, and he confirmed.

#### 3B — What was built, and the two-sided proof it landed

A 1 px right shift in 4-colour is `>> 2` bits per row. **Checked before assuming**: across all **117 rows of
all 9 cels**, every row's last byte has its low 2 bits clear, so the shift **fits in the existing 13×2
footprint** — no third byte column, and `PEEL_BYTES` / the slot arithmetic are untouched. My earlier worry
about peel geometry (P3.50 §3C) was wrong, and the measurement retired it.

**`content/` was never edited.** `shift_cel.py` writes shifted copies into `build/`, so no converted asset
became ALTERED (§2B) and the shift stays reproducible from a command rather than living as an untracked edit
in a data file.

**The pixel check gave a two-sided result, which is the only reason the shift was known to have landed:**

| expectation | result |
|---|---|
| unshifted (`content/`) | **FAIL** — 6 mismatches, `got $01 want $05` |
| shifted (`build/flames_shifted/`) | **PASS** — 32 bytes byte-identical |

**A checker that fails on the change and passes on the corrected expectation is one that can see a 1 px
move** — worth stating in a session where three separate instruments have been blind.

#### 3C — Why request (2) is impossible with one cel set

Stated as arithmetic rather than as an obstacle: the two desired positions are **px 112 (phase 0)** and
**px 201 (phase 1)**. A single cel set carries one sub-byte alignment; the draw origin is a **byte** column, so
placement is adjustable only in 4 px steps. **Two targets on different phases therefore require two cel sets.**
Every variant considered — shifting the shared data either way, compensating with a byte-column change, or
shifting by 5 px and moving a column — reduces to the same thing, because any single shift moves both torches
together.

#### 3D — Why it was reverted rather than half-landed

Request (4) asked for the left torch back. With one cel set that means **reverting the shift entirely** — the
right torch returns to px 200, 1 px left of true. Recompiled from the pristine cels, rebuilt, **room suite
green against the originals**. Both torches are exactly where they were before this work started.

#### 3E — The unlock, measured rather than estimated

`cel_blit_prep.py` on `flame1/converted.s`: **75 segment bytes, 2.88 B per footprint byte, replay OK** — the
tool reconstructs the bitmap over a background before emitting, so the figure is verified, not counted.

- 9 cels as data: **675 B**
- 9 cels compiled: **2,163 B** (draw 663 + save 684 + erase 816, measured from the flames map)
- **frees 1,488 B**; bundle free **184 → 1,672 B**

**And the save/erase halves disappear entirely rather than being replaced**: the peel becomes the shared
`blit_save`/`blit_erase` already in the bundle for the characters, which need no per-cel code.

**What is NOT established: the cycle cost.** The compiled save/erase are hand-optimised straight-line code
(measured by the compiler at 5.33 cy/footprint-byte draw, 9.92 erase); the generic primitives will be slower,
and the honest position is that this needs measuring rather than assuming. **The cadence gate left headroom —
72% of budget — but "there is headroom" is not a measurement.**

#### 3F — Three faults of my own, recorded

1. **The shift tool dropped a row.** First run reported *"12 rows shifted"* on a 13-row cel: it skipped "the
   first matching `fcb`" as the header, but the header is **decimal** (`fcb 13,2`) and never matched the row
   pattern at all — so the skip ate row 0. Fixed to exclude the header **by pattern, not by a counter**.
   Row 0 is blank in every flame cel, so it would have shown nothing and stayed.
2. **The verifier's `--cel-dir` did not take effect** on its first wiring — the assignment went in at a
   `parse_args` that was not the one used. Caught by asserting the value after a run rather than trusting the
   flag, and the suite was still red until it was fixed.
3. **Two failed edits to the runner**, one of which wrote a literal `\n` into the script. Caught by reading the
   file back.

**All three were caught by checking the result rather than the intent**, which is the only reason the shift's
green run means anything.

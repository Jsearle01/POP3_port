### 1 — Summary

**PART A — the frame budget survives, and that is the most important result in the audit.** Measured by
execution this dispatch: with both subsystems ablated the engine spins **4,216.6 times per video frame**, and
the spin loop is 7 cy, so **a frame holds ≥29,516 cy**. At normal speed a frame is 14,930 cy and could not
contain it. **Double speed is confirmed by execution and the 29,859 constant is corroborated to ~1.2%.** The
denominator's denominator is sound — **HARD-STOP #2 does not fire.**

**But the audit found a load-bearing counted figure that is wrong, and it is wrong in the file's own
comment** (§3B): `blit_core.s` documents the merge path as **22 cy/byte** and calls it *"a 6809 FLOOR rather
than an estimate: P3.19 counted this exact sequence."* **The sequence beneath the comment is 32 cy/byte** —
the count omits its own `dec bc_count` (7) and `bne` (3). **45% low, on the single largest documented rate in
the draw path, asserted as a floor.**

**PART B — the peel decomposed, all four components measured directly:**

| | cy/iteration | of the 29,673 budget |
|---|---|---|
| **draw** (`blit_cel`) | **26,849** | 90% |
| **erase** (`blit_erase`) | **13,074** | 44% |
| **save** (`blit_save`) | **11,001** | 37% |
| erase + save + pass setup = **peel** | **25,402** | 86% |

**★ THE STRUCTURAL ANSWER, AND IT IS NOT THE ONE THE DISPATCH EXPECTED: no peel change alone brings the frame
inside budget.** With the peel **entirely free** the frame is **31,672 cy = 107%**. With the draw entirely free
it is **30,225 = 102%**. **Each half is on its own about one whole frame budget**, so the frame is not over
because of the peel — it is over twice.

**The per-character skip is worth 6.8% here, and that is a ceiling, not a saving** (§3E). Measured off the
engine's own `ch_move` store: the **vizier moved in 100.0%** of frames and the **princess in 86.3%**;
**neither moved in 0.0%**. The demo animates both characters continuously, which is precisely the scene in
which the skip cannot fire.

**And P3.32's reason is live in this scene, not historical:** footprints **overlapped in 13.8% of samples,
closest approach −5 byte columns.** A per-character skip is correct only where the footprints are disjoint —
which is a real gate, not a formality.

**The oracle does not peel at all** (§3F). It keeps 30 **redraw buffers** (`redbuf`/`fredbuf`), characters
**mark the blocks they impinge on** (`MARKRED`, `QUICKFLOOR`), and `FAST` **repaints those blocks from the
background data** before drawing characters over. **There is no per-sprite save/restore anywhere in it.** The
port's peel is a CoCo3-side invention, not a ported model — so the largest component of the port's frame is
paying for a mechanism the original never had.

**Where the peel's time actually goes: per-row overhead, on rows too short to amortise it.** `erase − save` =
**2,073 cy** for identical byte movement over 90 rows — **23 cy/row of pure difference** — and the derived
overhead share is **44% of save and 53% of erase** (§3D). Worse than the shifter's 38% that P3.39 flagged.

#### 3B — The merge rate: the comment contradicts the code beneath it

`blit_core.s:98-102` states:

> *22 cy/byte, and that is a 6809 FLOOR rather than an estimate: there is no 16-bit AND/OR against memory and
> no register-to-register logic op (no `ora b`), so a masked byte cannot be done two at a time. P3.19 counted
> this exact sequence.*

The sequence it counted, with the file's own annotations and the two lines it left out:

```
bc_merge_loop
                lda     ,x        ; 4   <- annotated
                anda    ,u+       ; 6   <- annotated
                ora     ,u+       ; 6   <- annotated
                sta     ,x+       ; 6   <- annotated      = 22, the quoted figure
                dec     bc_count  ;     <- NOT annotated: DEC extended = 7
                bne     bc_merge_loop ; <- NOT annotated: branch taken = 3
```

**32 cy/byte.** The four annotated instructions sum to exactly the quoted 22, so the omission is visible in
the file: the loop control was not counted. The *architectural* argument is sound — a masked byte genuinely
cannot be done two at a time — but the **number attached to it is 45% low**, and it is stated as a floor.

This is the P3.42 §3B failure mode in its other direction: there, a check read a comment as if it were code
and reported a fixed file as broken. **Here a comment has been read as code for five dispatches** — the 22
appears in the representation costings — and nobody read the four lines below it. *A check must distinguish
code from commentary about code*, and so must a citation.

**Consequence, bounded honestly:** the merge rate feeds the draw-cost model, which P3.44 has now measured
directly (26,849 cy) — so nothing downstream still depends on the 22. It is corrected here so that it is not
cited again.

#### 3C — Part A's first item: the frame budget, measured

The budget is the denominator of everything and it has been wrong once before — P3.41's benchmark reported
623.6 cy/row for a routine counted at 284 because it never set double speed, *"a clean factor of two."* So it
is checked by execution rather than accepted.

From P3.43's `neither` ablation (both subsystems NOPped, the loop doing almost nothing):

- **1.000 frames per iteration, 4,216.6 spins per iteration.**
- `hal_vbl_spin` is `cmpb <hal_frame_lo` (4) + `beq` taken (3) = **7 cy**, so the engine spends
  **≥29,516 cy per frame spinning.**
- At normal speed (0.89 MHz) a 59.94 Hz frame holds **14,930 cy** — it could not contain 29,516 cy of
  spinning. **Double speed is confirmed by execution, not by trusting `$FFD9`.**
- 29,516 measured spinning + the loop's small residual work ≈ **29,859**, the standing constant, **within
  1.2%.**

**An internal check on the instrument:** the spin tap is a read-tap, and P3.43 §10a established read-taps can
over-count. **An inflated count would have produced a frame LONGER than 29,859.** It produced a slightly
shorter one, which is what a true count plus a little real work looks like. The measurement is
self-limiting in the direction of the known fault.

**Verdict: the frame budget is sound. HARD-STOP #2 does not fire.**

#### 3D — Part B: the peel taken apart

Four ablations, each NOPping exactly one `jsr [BLIT_TAB+n]` call site inside `char_draw`, located by operand
and required to be unique in the range; each gated on `chars_frame` still being entered 1.00×/iteration:

| mode | site | work cy | component |
|---|---|---|---|
| `full` | — | 57,074 | — |
| `nodraw` | `$3BC3` | 30,225 | **draw = 26,849** |
| `nosave` | `$3B8B` | 46,073 | **save = 11,001** |
| `noerase` | `$3B73` | 44,000 | **erase = 13,074** |
| `nopeel` | `ch_anymove` forced 0 | 31,672 | **peel = 25,402** |

**The decomposition closes, and its residual is meaningful rather than noise.** save + erase = 24,075 against
the peel's 25,402 — a **1,327 cy** gap, which is exactly what `nopeel` additionally removes: it returns at
`cp_none` and so skips `co_variant` / `co_dims` / `ch_index` / `co_here` / `co_setup` for **4 pass-character
combinations**, ≈332 cy each. The two ablations differ in scope by precisely that, and the arithmetic agrees.

**Erase costs 2,073 cy more than save while moving identical bytes** — same rows, same widths, same pair
loop. The difference is per-row bookkeeping alone (erase must reconstitute the framebuffer stride from the
remainder, `blit_core.s:286-294`), and over 90 rows it is **23 cy/row**.

**So the peel is dominated by per-row overhead, as the dispatch suspected.** Footprints are ~470 bytes
(vizier 47×5-6, princess 43×5-6); at the shipped pair loop's 26 cy per 2 bytes the byte movement is ~6,100 cy:

| | measured | byte movement | **per-row overhead** |
|---|---|---|---|
| save | 11,001 | ~6,100 | ~4,900 = **44%** |
| erase | 13,074 | ~6,100 | ~7,000 = **53%** |

*(the byte-movement term is counted, from the shipped loop; the totals are measured — the split is therefore
counted-inside-measured and is labelled as such)*

**Rows are 5-6 bytes wide and there are 90 of them per frame.** That is the same shape P3.39 found in the
shifter (per-row overhead 38% of the cost) and it is worse here.

**And the draw is bigger than the peel** — 26,849 vs 25,402. §3H's cel census shows why it is far above any
byte-rate model: 4 cels carry **704 segments** and **418 skip bytes against 572 drawn bytes**, so a typical
frame dispatches ~346 segments to draw ~272 bytes. **The encoding is dispatch-heavy relative to its payload.**

#### 3E — Why the skip never fires, and what a per-character one is worth

**Measured, from the engine's own decision** — a write-tap on `ch_move`, which `ch_moved` stores once per
character before `ch_scan` ORs it. Reading `ch_last`/`ch_drawn` and re-applying the test myself would have
produced a number that is right only if my copy of the rule matched the engine's, and this project has shipped
five variants of a checker that assumed part of the state it checked.

```
694 frames tallied
vizier   moved in 694 of 694 frames (100.0%)
princess moved in 599 of 694 frames  (86.3%)
both 599 (86.3%)   only vizier 95   only princess 0   NEITHER 0 (0.0%)
```

**The skip cannot fire because nothing is ever still.** `viz_walk` applies `chx` on every step and `pri_demo`
applies `chx` on every step, so the frame-wide OR is 1 by construction. A **per-character** skip would remove
**95 of 1,388 character-peels — 6.8%, ≈1,700 cy.** That is a ceiling.

**★ AND IT IS NOT ACHIEVABLE, because P3.32's reason is live in this scene.** P3.32 made the test frame-wide
because *"if her erase is skipped, her pixels are still on screen during his save — the interleave,
reintroduced through the back door."* So a per-character skip is correct **only where the two footprints are
disjoint.** Measured geometry: **they overlapped in 13.8% of samples, closest approach −5 byte columns.** The
gate is real and it would fire.

**A correct narrowing therefore exists** — skip a character's peel when its own state is unchanged **AND** its
footprint is disjoint from every other character's (old and new). It does not re-break P3.32, so **HARD-STOP
#3 does not fire.** But on this scene it is worth **under 6.8%, for a new per-pair geometric test on the most
defect-prone code in the project.** I am reporting it; I am not recommending it.

**★ The caveat that matters more than the number:** this demo is **pathological for the skip** — both
characters in continuous motion. P3.38b's trace of the *real* `play 13` says the vizier repeats cel 67 and is
**fully static for five of six steps**, and `Pback` settles into a static `:loop db 17`. **In the scene the
port is actually being built for, a per-character skip would fire most of the time.** The 6.8% is a
measurement of the demo, not a prediction for the cutscene, and it should not be quoted as one.

#### 3F — The oracle does not peel

Read from the vendored source. The oracle's per-frame model is **dirty-block repaint**, not save/restore:

- **`redbuf` / `fredbuf`, 30 bytes each** (`EQ.S:222-223`) — one entry per screen block, 3 rows × 10 columns.
- **Characters MARK the blocks they impinge on** — `QUICKFLOOR` (*"Mark for redraw whatever floorpieces
  character might be impinging on"*, `CTRLSUBS.S:1165`), `MARKRED`/`MARKFRED` (`CTRLSUBS.S:1736-1741`).
- **`FAST` repaints only the marked blocks** — *"Same general structure as SURE, but redraws only those blocks
  specified by redraw buffers"* (`FRAMEADV.S:183-186`) — **from the background data**, then draws characters
  over (`drawobjs`, `redrawd` *"(both bg and fg)"*).

**There is no per-sprite framebuffer save and no restore-from-a-saved-copy anywhere in the frame path.** The
background is regenerated from its source, so it cannot be contaminated by whatever was drawn on top of it
last frame.

**This is a substantive finding about the port, not trivia.** The port's `blit_save`/`blit_erase` pair — 25,402
cy, 86% of a budget, the largest single component — implements a mechanism the original **did not have**. And
**every accumulating peel bug in this project's history is a bug about captured state**: P3.21 (the peel
rotated), P3.25 (buffer sized to one cel), P3.28 (cel change skipped the peel), P3.32 (a save captured another
character's pixels). **A repaint-from-source model cannot have any of them**, because nothing is captured.

#### 3G — The unit the arc quietly changed, and never reconciled

PA.2 measured the oracle's page-flip interval from **738 flip events: median 6.0 video frames**, and concluded
*"the budget denominator was wrong by 6×... The real budget is 6 × 29,859 − 186 = 178,968 cyc per animation
step. At 29,859 the typical load reads 6.7× over; at the measured figure it reads 1.12× over. Same cost model,
opposite indication."*

**The P3.19-onward arc costs against one hardware frame (29,673) and does not cite PA.2.** Both figures are
measured; they are budgets for **different units**, and which applies is a design question the record does not
answer:

- The **oracle** redraws on an animation step (~6 frames) and draws its flames straight onto the displayed page
  without flipping (`cutscene_room.s:210-215` says so explicitly).
- The **port** flips every iteration, so **both buffers must be maintained**, so it redraws everything every
  frame — even when nothing changed. Measured this dispatch: content changes far less often than that. The VM
  steps every **3.15 frames**, and the torches step about every **4 iterations** (`blit_cel` at 2.25/iteration,
  of which 2.00 is characters — the residual 0.25 is the torch redraw rate).

**So the port pays a full frame of work every video frame for content that changes roughly every third
frame.** I am flagging this as an **unreconciled contradiction in the record**, not resolving it: PA.2's
measurement is sound, the arc's 29,673 is sound, and nobody has written down which unit the port is obliged to
meet. **That question is upstream of every option in §5.**

#### 3H — The cel census, and what it says about the draw

`harness/tools/cel_byte_census.py` over the shipped streams:

```
  cel                    rows   w  blast  merge   skip  segs
  vwalk48_p0.s             47   5     73     88     74   198
  vwalk49_p0.s             47   6     90     93     99   196
  pslump.s                 43   6     43     74    141   162
  pstand.s                 43   5     45     66    104   148
  totals: rows=180 blast=251 merge=321 skip=418 segments=704
```

A typical frame draws one vizier cel + one princess cel: ~118 blast + ~154 merge = **272 drawn bytes** across
**~346 segments**, plus **~178 skipped bytes**.

- **P3.19's byte-rate model** gives 118×4.5 + 154×22 = **3,919 cy**. **Measured: 26,849.** 6.8× — because the
  model charges only bytes.
- At the **corrected** 32 cy/byte the merge alone is 4,928, and ~346 segment dispatches at ~19 cy each add
  ~6,600 — **segment dispatch costs more than the merged pixels do.**
- **418 skip bytes vs 572 drawn**: over 40% of the footprint is transparent runs that still cost a dispatch.

I am **not** publishing a reconciled draw model — the counted terms above are rough and the arc's whole lesson
is that counted terms are. The measured 26,849 stands on its own; the census explains its *shape*.

**★ First, the framing that constrains all of them: no single component fixes the frame.** Peel free →

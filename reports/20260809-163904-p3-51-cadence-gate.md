### 3 — Reasoning

#### 3A — §3C implemented, both traps respected

`chars_tab` extended to `fdb chars_frame,chars_due` at bundle offset **+66**; `chars_due` is
`stu vm_now / ldd vm_now / subd vm_due` → A=1 when non-negative, **touching nothing else**; `room_loop` asks
via `jsr [CHARS_TAB+2]` before `flicker` and waits a VBL when idle; `fl_div` and `FLAME_DIV` are **deleted**,
not retuned.

**Trap 1 — `vm_nextframe` still owns the step.** `chars_due` reads `vm_due` and writes only `vm_now`; `cad_idx`
advances where it always did. The measurement confirms it: **1.00 draws per animation step**, which is only
possible if one thing decides.

**Trap 2 — the idle path waits.** `HAL_gfx_swap` was pacing the loop; the idle branch calls
`HAL_time_vbl_wait` before looping.

**Offsets unmoved**, as §3C predicted: `flame_erase $3024` (+36), `blit_tab $303A` (+58), `chars_tab $3040`
(+64). Only the compiled cels shifted, and they are reached through tables the assembler regenerates.

#### 3B — The draw rate needed a write counter, because the read-taps disagreed

`frame_baseline` reported **`chars_frame` 1.00 per iteration** and **`flicker` 0.71** — two routines called on
the same iterations, so at most one could be right, and 1.00 would have meant the gate was not gating at all.

Settled with a **write** counter on `probe_frames`, incremented once per drawn frame: **555 draws over 1,497
video frames = 0.371 draws/frame**, and **556 animation steps → 1.00 draws per step.** So **0.71 was the
correct figure** (555/784 iterations) and the `chars_frame` read-tap was inflated.

**Ninth-family instrument fault, same session as the eighth.** Write counts have reconciled exactly every time
in this arc; read-taps have now been wrong three ways — inflated non-uniformly, blind on a range, and blind
in a way that survives changing the tap population.

#### 3C — The build guard, wrong for the third time, now keyed to the fault

It compared `peel_base` to a literal. That literal has now moved three times — `$22C2` (P3.49) → `$22C1`
(P3.50) → `$22C7` (this dispatch) — and each move made the guard wrong in one direction or the other.

**Re-keyed to what is actually being guarded against.** The fault is *"`build.bat` silently did nothing and
returned 0"*, which is a question about **freshness**, not about an address: the runner now refuses when any
of the three sources is newer than the disk image. **Proven to fire by negative control** (`touch` a source →
`Refusing`). An address literal is a photograph of one build; staleness stays true however the layout shifts.

#### 3E — Jay's finding: the walk's x, and why the port is not at fault

***"it looks like he moves back a bit while walking forward."*** He is right that it happens; three checks say
we did not cause it.

**One — the data is the oracle's, verbatim.** `SEQTABLE.S:1513-1522` against `char_draw.s`'s `viz_walk`:

```
Vwalk    db chx,1            viz_walk        fcb SEQ_CHX,1
Vwalk1   db 48,chx,2         viz_walk1       fcb 48,SEQ_CHX,2
Vwalk2   db 49,chx,6                         fcb 49,SEQ_CHX,6
         db 50,chx,1                         fcb 50,SEQ_CHX,1
         db 51,chx,-1                        fcb 51,SEQ_CHX,-1     <-- the back-step
         db 52,chx,1                         fcb 52,SEQ_CHX,1
         db 53,chx,1                         fcb 53,SEQ_CHX,1
```

**Prince of Persia's own vizier walk contains a single-pixel reversal**, and it has to: the six deltas sum to
10 px per cycle, and `10 mod 4 = 2` is what puts each cel on exactly two sub-byte phases — the property the
whole baked-walk representation depends on (P3.30).

**Two — the trace does exactly that and nothing more.** Every write to the vizier's `CH_X`, in order, over
40 changes:

```
#  x    delta          cycle: -1, -1, -2, -6, -1, +1   (net -10)
#  144    +1   <-- BACKWARD        exactly ONE positive per six
#  143    -1                       magnitude 1, never larger
#  142    -1                       no second positive anywhere in 40 changes
#  140    -2
#  134    -6
#  133    -1
#  134    +1   <-- BACKWARD
```

The expectation was **derived from the sequence data**, not typed in, so the check cannot agree with itself.

**Three — it is not the renderer.** A 1 px move changes the sub-byte phase, and a walk cel is baked at only
two of the four. If the back-step landed on an unbaked phase, `co_variant` would fall back to the previous
cel's pointer and draw the **wrong cel** — a far more visible stutter. It does not: at the back-step,
**cel 51 sits on phase 1/3 and cel 52 on phase 0/2**, which are exactly the baked sets, and the walk suite
reports **0 bytes wrong at all 28 captures**.

**What I cannot settle here.** `addcharx` — the oracle routine that applies a `chx` delta — is declared
`ds 3` in `GAMEEQ.S` with **no body anywhere in the vendored tree** (only `jsr` call sites). So the source
cannot tell me whether the oracle treats a negative delta exactly as we do, and **CLAUDE.md §2 is explicit
that where the source does not settle a behavioural question, the running game does.** That makes this a
side-by-side, which is §8.1.

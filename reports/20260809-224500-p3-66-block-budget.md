### 3 — Reasoning

**3A — Why a tap on the MMU registers and not on RAM.** The question is whether anything can *address*
`$0C-$0F`. On a 128 KB machine they are the CPU's `$8000-$FFFF`, and `gfx_map_blocks` remaps `$FFA4-$FFA7` onto a
framebuffer at init. If no value written to those registers ever aliases into `$0C-$0F` after that, the blocks are
unreachable — which is a stronger statement than "nothing was observed writing to them". Write taps are also the
reliable direction on this target (idioms §10a).

**3B — The measurement, verbatim** (`run_block_budget.sh`, reproducible):

```
# gfx init mapped the window at frame 1251
  $FFA4 : $10(->$00)@f1259 $14(->$04)@f1251 $3C(->$0C)@f0  (firmware boot map)
  $FFA5 : $11(->$01)@f1259 $15(->$05)@f1251 $3D(->$0D)@f0  (firmware boot map)
  $FFA6 : $12(->$02)@f1259 $14(->$04)@f1497 $16(->$06)@f1251 $3E(->$0E)@f0  (firmware boot map)
  $FFA7 : $13(->$03)@f1259 $15(->$05)@f1497 $17(->$07)@f1251 $3F(->$0F)@f0  (firmware boot map)
# RESULT: $0C-$0F are never mapped: 32 KB free on 128 KB, MEASURED.
```

`$FFA0-$FFA3` hold `$38-$3B` (→ `$08-$0B`) — the program, the blob at `$3000`, `DR_VARBASE` at `$6A00` and the
stack at `$7F00` all live there. So the sixteen blocks are: `$00-$03` buffer A, `$04-$07` buffer B, `$08-$0B` the
program's lower 32 KB, `$0C-$0F` **free**.

**3C — Four instrument faults, which is the part worth recording.** The first three answers this probe gave were
all wrong, each for a different reason, and each looked plausible:

1. **Measured DECB at the BASIC prompt.** My probe never loaded the port, so it reported the firmware's
   `$3C-$3F` and concluded the blocks were in use. The tap was correct; the machine was not running the thing
   under test.
2. **Sampled before `gfx` init.** Gated on `EXEC + 700` = frame 1085; `gfx_map_blocks` does not run until ~1251.
   It reported `$FFA4-$FFA7` "never written" about a window that had not been mapped yet.
3. **Fired `EXEC` mid-load.** I keyed the settle to the frame the `LOADM` was *posted* rather than the frame it
   *landed* — P3.6's bug, reintroduced by writing a launcher instead of using the one that works. `probe_status`
   sat at 0 for 5,000 frames.
4. **Counted the boot map as the port's.** The final verdict line flagged `$0C-$0F` as reached, from frame-0
   values written before the port existed.

Each was found only because the *next* check disagreed with it. The instrument now takes its launch from
`room_test.lua` and separates the firmware's writes from the port's by the port's own first window write.

**3D — What §1 does NOT establish.** That the bank is *reachable cheaply*. Paging a block in means remapping one
of `$FFA4-$FFA7` — which is the draw window — so the window is not a framebuffer while the copy runs. The switch
cost, the frequency, and whether it can avoid landing between the three passes are §2 and §3, unmeasured.

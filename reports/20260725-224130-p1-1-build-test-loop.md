### 1 — Summary

**The loop is closed and proven.** `build.bat` assembles the target and images a bootable `.dsk`;
`run_probe_test.sh` boots it in `mame coco3`, drives DECB through `natkeyboard:post`, and checks six
observables against a spec, exiting 0 on PASS and 1 on FAIL. Both a full PASS and two independent
deliberate-FAIL modes are demonstrated verbatim in §5.

The trivial target (`src/harness/loop_probe.s`, 149 B) exercises every link: GIME → 320×192×4 (the mode
the port ships in), both framebuffers filled with distinct patterns, a VOFFSET page-flip present, and
**exactly 120 VBLs counted by the 6809 itself** off the GIME `$FF92` VBORD latch. The check that makes the
timing real rather than asserted: **the 6809's own VBL count is cross-validated against MAME's independent
`frame_number` clock** (120 vs 119, within ±2 tolerance — the 1-frame gap is sampling phase). Two
independent clocks agreeing is evidence; either alone is not.

`project-state.md` is the new durable build-phase artifact — state, the idiomatic-6809 standard as a hard
coding constraint, the verification standards, and an ordered build backlog with its two blocked items
named.

**Five distinct failures stood between `imgtool` and a running program**, all now fixed and filed as idioms
(§3.2). The one worth reading is **14e**: the trivial target initially copied Karateka's `$0100` interrupt
vector block, which is correct there and **actively fatal** here — Karateka's drivers are *poked in* with
the CPU halted; a DECB-`LOADM`'d image writing `$010C` destroys DECB's **live** IRQ vector. The load
succeeded, the image was byte-correct, and DECB then wandered off and never returned. That is the captured
methodology candidate (§10).

**One reactive deviation to flag up front:** AC2 asks for a bootable `.dsk` and AC3 for the
`natkeyboard:post` path — both delivered and both are the primary evidence. I *additionally* built a
`--mode direct` load path (Lua parses the DECB binary, pokes it, sets PC), because that is Karateka's proven
driver-test mechanism and is the mode the later oracle framebuffer-diff will need. It is a cross-check, not
a substitute; the PASS in §5 is the disk path. See §6.1.

### 3 — Reasoning

#### 3.1 — The trivial target: what it proves, and what it deliberately does not

Chosen to make every link in the chain produce a *deterministic, spec-checkable* observable rather than a
visual impression:

| Link | Exercised by | Observable |
|---|---|---|
| build | lwasm `--decb` | 149 B, one segment @ `$0200`, exec `$0200`, first bytes `7E 02 08` |
| image | imgtool `coco_jvc_rsdos` | `PROBE.BIN` present in DIR |
| boot | DECB `LOADM`+`EXEC` via natkeyboard | `$0200` reads `7E 02 08` in guest RAM |
| GIME video write | `$FF90/$FF98/$FF99/$FF9D/$FF9C/$FF9F/$FFD9/$FFDF` + palette | 15,360 B of frame A all `$1B` |
| page-flip present | `std $FF9D` VOFFSET swap | 15,360 B of frame B all `$E4` |
| timing | `$FF92` VBORD poll ×120 | `probe_vbls == 120`, and MAME frame delta = 119 |

The GIME init order is **not invented** — it is Karateka's MAME-verified sequence (`gfx.s`), which itself
supersedes `memory-map.md §5` on one point: **palette must be written AFTER the video mode**, per idiom §9.
I followed `gfx.s` + idiom §9 and cited the conflict inline rather than silently picking one.

**Deliberate interrupt policy.** `CC.I/F` stay masked for the entire run; VBL is *polled* from the `$FF92`
status latch with the VBORD source enabled (`$FF90` IEN=1, `$FF92`=`$08`). Ground truth confirms the read
both reports and acknowledges. This needs **no `$010C` install**, which sidesteps the DECB overlap entirely
— and, as it turned out, was the only reason the fix in 14e was available at all.

What it does not do, on purpose: no engine, no HAL, no sprite work, no game logic, no MMU programming (it
relies on the same MAME-default MMU floor Karateka relies on — CPU `$8000`→phys `$78000`, `$C000`→`$7C000`,
which is exactly why Karateka's VOFFSET constants `$F000`/`$F800` are correct, and I re-derived that rather
than copying it).

#### 3.2 — Getting from `imgtool` to a running program: five failures

Each was measured, not inferred. All six idioms filed under §2A.3 (provisional — §6.3).

1. **`-ext fdc` is mandatory** (14a). A bare `coco3` has no disk controller: it boots Extended Color BASIC,
   `LOADM` does nothing, program silently never runs (`status=0`, `PC=$CFFD`). Idiom §12's quick-command
   line omits it; Karateka's `disk-boot-decb-overlap.md:67` has the correct form. Also recorded:
   `-verifyroms` reporting "bad" is **benign** — the only missing files are three *alternate* DOS ROMs.
2. **`natkeyboard.in_use` defaults FALSE, and arming it in the same frame as the first post scrambles that
   post** (14b) — `PRINT 7*6` arrived as `PREPRINT` → `?SN ERROR`. Arm at script load.
3. **Posting is asynchronous and slow** (14c) — a 12-char `LOADM` took ~130 frames to drain. Gate on
   `nk.empty`, never a frame gap. Both `\n` and `\r` work as ENTER here.
4. **`LOADM` takes ~400 frames** (14d) — poll the load address for the expected opcode. This also turns a
   load failure into a *reported* load failure instead of a mystery crash downstream, which is why the
   harness now prints `$0200 = xx xx xx (want 7E 02 08)`.
5. **The `$0100` block** (14e) — below.

**On 14e, and why it is the finding worth keeping.** The trivial target opened with Karateka's 18-byte
vector block at `$0100-$0111`. Under `LOADM`, `$010C` is DECB's **live** IRQ dispatch vector. The failure
was maximally misleading: LOADM *succeeded*, the image was *byte-correct* (`$0200 = 7E 02 08`, verified),
and DECB then executed its own destroyed vector — `PC` observed wandering `$010D → $FEF9 → $FE0B → $C60B`,
never returning to the prompt. Before finding it I had cleared the plausible suspects instead: the quote
character (typed **perfectly** — `$62` is simply the VDG *screen code* for `"`, not a mangled byte; 14f),
ENTER encoding (both forms work), and disk readability (`DIR` listed the file). The repo's own idiom §5
already documented `$010C`/LOADM — but framed as something DECB does *to you*, not something your load
image must not do *to DECB*. The fix was deletion: a run with interrupts masked throughout needs no vectors.

#### 3.3 — `.gitattributes` is not housekeeping

`cmd.exe` cannot parse an LF-only `.bat`: it mangles the file into truncated command names
(`'wasm' is not recognized`) and fails in a way that reads as *a missing toolchain*. `build.bat` is the
`CLAUDE.md §1` build contract, so its line endings are load-bearing. Pinned in `.gitattributes` rather than
left to any developer's `core.autocrlf`, and **verified by round-trip rather than asserted**:
`git checkout-index --temp` reproduces `CRLF=76, bare-LF=0` (§5). Repaired with `read_bytes`/`write_bytes`,
never `write_text` — the P1.2 `.gitignore` corruption is the reason that rule exists.

#### 3.4 — `project-state.md` placement

Repo root, alongside `CLAUDE.md` and the idiom files, so a fresh session finds it without searching. Per
§2(d) I checked it against `CLAUDE.md §2D`: it is **Clyde-authored operational state**, not an authored
authoritative doc — it carries no decision records, post-mortems, or behavioural models, and it says so in
its own header. Those remain Orchestrator-owned.

### 7 — Uncertainty flags

1. **The `$FF92` VBORD polling approach is proven for this probe, not chosen for the engine.** It works and
   avoids the `$010C` install, but the engine may still want a real IRQ-driven frame counter (Karateka's
   `irq_vbl.s` shape). Backlog item 2 names this as an open decision, not a settled one.
2. **The MAME↔6809 frame agreement carries a ±2 tolerance.** Measured delta was consistently 119 vs an exact
   120, which is sampling phase (Lua samples once per frame; the 6809 sets its status flags between
   samples). Tight enough to catch a real timing break, loose enough that a 1–2 frame systematic error
   would pass. Stated so the number is not over-read.
3. **No MMU programming.** The probe relies on MAME's default MMU floor for `$8000`→`$78000` /
   `$C000`→`$7C000`, the same assumption Karateka carries as an undischarged open item (its plan §A4/A7).
   The derivation checks out arithmetically and the framebuffer reads confirm it in practice, but this is an
   inherited assumption, not an independent verification.
4. **`-verifyroms` "bad" is judged benign on the basis that boot works.** I did not verify each of the three
   missing ROMs is genuinely optional from documentation; the evidence is behavioural (DECB boots, DIR
   reads, LOADM loads, the program runs).
5. **The six new idioms are filed PROVISIONALLY.** The §2A.3 authorship ruling is still open (now ten
   deferrals). Filed under the Orchestrator's standing recommendation and flagged here for Jay's
   confirmation, exactly as §6 of the dispatch directs. If the ruling goes the other way, §14/14f/14g should
   be moved, not deleted — the content is measured.
6. **The harness proves the loop, not the port.** It can read framebuffers and count VBLs, which is what the
   oracle comparison will need — but **no oracle comparison has been exercised**, so its capability to
   enforce behaviour-identity is designed-for, not demonstrated. First real engine dispatch should exercise
   it against something.

### 3 — Reasoning

#### 3A — ★★★ `vm_due = now` IS THE SAME AS `vm_due = 0`, AND THE GATE IS THREE INSTRUCTIONS

```
vm_nextframe
                ldd     vm_now
                subd    vm_due
                bmi     vn_hold                 ; this step's frames have not elapsed
```
[`char_draw.s` `vm_nextframe`]

| `vm_due` | D | N | `bmi` | result |
|---|---|---|---|---|
| `0` (today) | `now - 0` = large positive | 0 | not taken | **STEP CONSUMED** |
| **`now`** (§1's fix) | `now - now` = **0** | **0** | **not taken** | **STEP CONSUMED** |
| `now + 1` | `now - (now+1)` = −1 | 1 | taken | HOLD — but see §3B |

**`bmi` branches on N, and zero is not negative.** So the proposed initialisation changes nothing about the
first tick: it consumes the step exactly as `0` does, **the princess loses the same step, and 45 → 38
reappears.** ★ *That is HARD-STOP 2's named signature, which is why this is reported rather than built.*

**★ The dispatch's own diagnosis of `0` is right and the inference from it is not.** Zero *is* maximally
overdue — but so is `now`, to a `>=` test. Only a **strictly future** `vm_due` holds, and §1 explicitly and
correctly forbids that.

#### 3B — ★★ THERE IS ONE GATE AND ONE DUE-TIME; THE SONG IS **INSIDE** THE STEP

§1's model — fire the events due now, leave the ones due later — describes a scheduler with per-event due
times. **This VM has one.** `vm_nextframe` is a single gate; everything downstream of it happens *because a
step was consumed*:

```
vm_nextframe:  gate -> advance cad_idx -> vm_due = now + 6 -> jsr vm_beat_tick -> vm_step (viz) -> vm_step (pri)
vm_beat_tick:  ldu vm_beat / bne vb_running / ldu #cel_plan / bsr vb_apply     <- beat 0, on the FIRST step
vb_apply:      ... lda 6,u / beq vb_nosong / jsr msys_play                     <- the song, if the row has one
```

**So the song cue and the animation advance are the same event.** There is no value of `vm_due` that fires
one without the other: a value that lets the beat tick run also steps both characters, and a value that holds
the characters also skips `vm_beat_tick` entirely — **so beat 0 is never applied and no song can fire at
all.** **AC2 is unsatisfiable by construction**, and that is a property of the design rather than a bug in it.

[`content/cutscene/chars/cel_plan.s`, generated by `bake_scene.py`]

nothing.

#### 3E — §2H's three checks

1. **A second mechanism for a different object class?** ★ **Yes, and it is the one that matters.**
   `vm_beat_tick` serves a *third* object class alongside the two character scripts — the block schedule and

   characters, the scenery strobe **and** the page mapping. ★ *Any scheme that "just fires the cue" moves all
   four.*
2. **The routine that CALLS it.** `vb_apply`'s caller is `vm_beat_tick`, whose caller is `vm_nextframe`,
   **inside the consumed-step branch**. Naming `vb_apply` alone would have hidden exactly the coupling this
   report turns on — *the enclosing routine is the fact*.
3. **Prior-report grep** (`cel_plan|vm_beat|vm_due|cad_tab`): P3.65, P3.72d/k, P3.78, P3.87, P4.23. **One

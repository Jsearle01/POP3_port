### 3 — Reasoning

#### 3A — The control, run first, and what it licenses

P3.48b's lesson set the bar: *a probe that reads the same with the mechanism removed cannot testify that the
mechanism is working.* So the control preceded the measurement.

**Seed:** `torch_step` opens `lda t_prev / beq ts_nosave`; patching the `beq` ($27) to `bra` ($20) skips the
restore on every call, every slot, every frame. The gate is **located by instruction pattern** — scan for
`B6 <t_prev>` and take the branch after it — not by a byte offset, because counting instruction lengths put it
13 bytes early in P3.48b and the guard refused to patch the operand it landed on.

**Result:**

```
# SEEDED: $2154 $27 -> $20 (BEQ->BRA); the erase is disabled
# dispatches: erase 0, save 2872
# CONTROL PASSED: the seed drove erase dispatches to 0 while saves continued.
```

**The probe registers the presence and absence of the erase.** Only then was the real reading taken.

#### 3B — Why the dispatch capture is the trustworthy instrument

`torch_call` selects its compiled routine with `ldx a,x` off one of three dispatch tables, then `ldy t_peel`.
**A read-tap on a TABLE fires exactly on that kind of call** — `erase_tab` ($3024) for an erase, `save_tab`
($3012) for a save — which is the one moment when "which operation is this" is unambiguous. `t_peel` is
sampled there, so what is recorded is the pointer that call will use.

Both tables are watched deliberately, because **the discriminating comparison is erase-vs-save for the same
slot**: the save is known to land correctly (9022 writes into each range), so had the erase's `t_peel`
differed, that difference would have been the defect. It does not differ, anywhere.

**Arithmetic check on the counts:** 2,776 erase hits over 694 iterations = 4 per iteration. `ldx a,x` is a
16-bit load, so each dispatch produces **two** tap hits; 2 torches × 2 bytes = 4. Per slot: 694 hits = 347
dispatches × 2, and 347 is exactly the number of frames at that base. **The counts reconcile, which is a check
the address capture would fail if the tap were firing on something else.**

#### 3C — What is NOT resolved: why the range read-tap is blind on that range

Stated plainly rather than glossed, because it is an instrument fault that produced a wrong finding and could
produce another.

- Slot 3's range read-tap reports **0 reads** while its write-tap on the identical range reports **9022**.
- It is **not tap population**: 0 with three taps installed, same as with thirteen.
- It is **not a fixed address**: it followed slot 3 across two builds (`$230F..$2328` at one layout,
  `$2310..$2329` at the other).
- It is **not adjacency**: slots 0/1 and 1/2 are equally adjacent and fire.

**I have no mechanism for it.** What I have is a direct measurement that overrides it, taken with a probe that
passed a seeded control the range tap never had. **The safe rule to carry forward: a range read-tap's ZERO is
not evidence of absence** — this is now the ninth instrument failure logged in this project, and the third
where the tool's own success signal was the lie.

#### 3D — The stale-build trap, closed in the runner

P3.48b measured the wrong binary because `cmd /c ... build.bat` from Bash prints a banner, does nothing and
**returns 0**. The fix moves `peel_base` from `$22C9` (unfixed) to `$22C2` (fixed), so **the map states which
binary exists**. The runner now refuses to measure unless it sees the expected layout:

```
if [ "$P_PEELBASE" != "0x22C2" ]; then ... Refusing.
```

**A precondition the tool enforces beats a step the operator remembers**, and this one had already been
forgotten once.

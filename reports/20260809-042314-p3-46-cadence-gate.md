### 3 — Reasoning

#### 3A — Part B: the mechanism, and how I missed it

**B1 — the scroll "chunking" is window capacity, not time.** From the code
(`scene4_scroll.s:173-183`), the chunk boundary is `min(clen, $2000 - coff)`: `$2000` is the **8 KB MMU page**
and `coff` the offset within it; the loop remaps `$FFA2` and continues **until `clen` is zero, inside one
call**. There is no cycle count, no frame counter, no VBL reference. **It is address-space capacity, and it
does not even span frames.** P3.45 called this correctly — but it is not the referent for Jay's memory.

**B2/B3 — the real mechanism, found via history.** `git log --all -S "SCROLL_VBLS_PER_STEP"` leads to
`tests/scripted/scene6_b2prime_driver.s`, present in the tree today:

```
main_loop:
        jsr     HAL_time_vbl_wait       ; ONE PHASE = ONE VBL
        lda     mg_phase
        beq     ml_init                 ; phase 0: step_init
        cmpa    #SA_NCHUNK
        bls     ml_sc                   ; phases 1..6: strip the band
        cmpa    #SA_NCHUNK+1 → FUJI     cmpa #SA_NCHUNK+2 → ARCH
        cmpa    #SA_NCHUNK+3 → cliff+seam
        cmpa    #SA_NCHUNK+4 → ml_flip  ; ACTORS + PRESENT
ml_next:
        inc     mg_phase / cmpa #SA_HOLD / blo main_loop / clr mg_phase
```

Answering §2 exactly:

| question | answer, from the code |
|---|---|
| what is a slice | **one VBL**, indexed by `mg_phase`, gated by `HAL_time_vbl_wait` at the top of the loop |
| how many | **11** (`SCROLL_VBLS_PER_STEP equ 11`, = the oracle's 11 VBL/run pose). Jay: ~12 |
| assignment unit | **whole work items** — init, six strip chunks, Fuji, arch, cliff+seam, actors |
| how decided | **a static hand-written schedule**, a branch ladder in source. **No budget arithmetic**, nothing measured, nothing greedy |
| **when does it flip** | **the last phase only** (`ml_flip`), after the actors |

**Why I missed it, stated plainly.** P3.45 searched **`src/`** for the vocabulary of **time-budgeting** —
*slice, budget, quota, partial, resumable, deadline*. The mechanism is in **`tests/scripted/`** and uses
**none of those words**; it says *phases* and does no arithmetic. **Scope and signature are independent ways to
miss, and I got both wrong** — then reported the absence with an enumeration, which made the negative result
more authoritative than a hedge would have been. The dispatch's standing invariant predicted this exactly:
*a thorough search for the wrong signature returns a confident absence.* **Jay's memory was right and my
search was not.**

#### 3B — Reconciling it with POP: the mechanism is real and POP does not need it

**Karateka slices because its work does not fit its VBL.** One scroll step rebuilds a full band strip; the step
is 11 VBLs (the oracle's cadence); the work is spread one item per VBL so no single VBL overruns. That is
Jay's description, and it is exactly right.

**POP's arithmetic is the other way round:**

| | |
|---|---|
| POP per-step work (P3.44, measured) | **57,074 cy = 1.92 VBLs** |
| POP step length (P3.23, measured on the oracle, SPEED 7) | **2.60 VBLs** |
| | **1.92 < 2.60 — the work already fits inside one step** |

**So POP does not need to spread anything.** It needs to stop doing a step's work *every VBL*. Slicing solves
work > step; gating solves work < step done too often. **Both mechanisms present the completed frame at the end
of a step — Karateka in its last phase, the oracle in `FrameAdv` — and that is the shared invariant worth
carrying over, not the phase table.**

**And it settles the P3.45 hazard question properly.** P3.45 argued the partial-frame hazard "belongs to
slicing, which nothing does". Slicing *is* done, so the hazard is real — and **Karateka's answer is to schedule
the present as the final work item.** Under that rule the back buffer may sit erased-but-not-drawn for ten
VBLs harmlessly, because it is not the displayed page. **P3.32's invariant would survive slicing too**, if POP
ever needed it.

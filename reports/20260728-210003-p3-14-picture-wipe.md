### 1 — Summary

The port now sweeps whole pictures in, column by column, left to right — the
transition `DblExpand` performs and the port has never had. Option B as Jay chose:
decode into the back buffer as before, then blit onto the **displayed** buffer a
column at a time through `$FFA2`. No asset change, no extra RAM, 128 KB held.

**Jay's correction was right on both counts**, and Phase 1 confirms it by
measurement: there are three regions, and P3.13 conflated the middle one with the
centring margin. The ring between the margin and the text is real artwork, and it is
*identical in both pictures* — which is why it shows no motion.

**But the build that follows from that would have been wrong**, and this is the one
place I have departed from the dispatch. The static region is a property of what two
pictures **share**, so it is different for every transition. A hard-coded swept
region is wrong for three of the four and leaves 98–192 genuinely-differing cells
unwritten. The oracle special-cases nothing — it sweeps everything, and the shared
parts show no motion for free. The build does the same, and reproduces Jay's
observation exactly. Full reasoning and evidence in §3B; deviation in §6.

Motion is measured on both machines with one instrument, and a **mid-sweep capture**
now guards the behaviour — the check a plain page flip cannot pass, and whose absence
let this defect survive three gates and a green suite.

### 3 — Reasoning

#### 3A — Phase 1: the three regions, pinned by motion

**On the running oracle** (`oracle_wipe_motion.lua`, three sample rows, every frame,
"which columns changed since the previous frame" — motion, not endpoints):

```
f  1739  row1[  quiet  ]  row2[ 32.. 32]  row3[  quiet  ]
f  1754  row1[  quiet  ]  row2[128..132]  row3[  quiet  ]
f  1790  row1[  quiet  ]  row2[336..336]  row3[  quiet  ]
f  1819  row1[  quiet  ]  row2[520..524]  row3[  quiet  ]
```

A single narrow band marching monotonically **x=32 → 524 of 560 over 81 frames**
through the text row, while the top and bottom border rows stay quiet — bar one patch
at x≈256–300. Converting to our framebuffer, x=32→524 is **content cols 18→141**.

**Independently, from the data:** per-column counts of differing bytes between the
outgoing and incoming pictures give cols 17–141, rows 14–167 — the same region, by a
different method.

The three regions, for splash → prolog1:

| | bounds | what it is |
|---|---|---|
| **#1 centring margin** | cols 0–9, 150–159 | the +20 px of the 280→320 contract. No counterpart on the Apple II, where 80 columns is the whole active width. **Never written.** |
| **#2 the image's own drawn border** | cols 10–16, 142–149; rows 0–13, 168–191 | **real artwork** — `$11 $08 $88 $EE $B1 $6E $C6` — not background. Identical in both pictures, so it is rewritten with the same bytes and shows no motion. |
| **#3 swept interior** | cols 17–141, rows 14–167 | dominated by two values ($10 39%, $02 38%) — text on ground. What visibly animates. |

**Jay's correction is confirmed, and P3.13's conflation is corrected**: #2 is inside
the content, is artwork, and is not the margin. P3.13 missed it because a bounding box
is driven by outliers — 192 stray cells in the top band stretched the box to the
content edges.

#### 3B — Why the sweep is nevertheless full-width (the deviation)

`#2` is static because the two pictures **share** it. That is not a property of the
artwork; it is a property of the pair. Measured across all four whole-picture
transitions:

```
cleared -> splash    cols  10..149 rows   0..191    ring cells differing:   0
splash  -> prolog1   cols  17..141 rows  14..167                          192
prolog1 -> prolog2   cols  28..126 rows  36..143                           98
prolog2 -> splash    cols  17..141 rows  14..167                          192
```

Three consequences:

1. **There is no single swept region.** Beat 0 sweeps the entire picture (nothing
   underneath); beat 4's moving region is far smaller than beat 3's.
2. **A hard-coded region breaks the endpoint.** The ring carries 98–192 cells that
   genuinely differ. Skip them and the finished picture is not the picture — AC-W2
   fails, and the existing byte comparisons would catch it.
3. **The oracle special-cases nothing.** `WipeRgtExp` walks all 80 columns
   unconditionally. The static border is emergent.

So `wipe_in` sweeps the full content width (cols 10–149) and lets the data decide what
appears to move — which reproduces all four behaviours, including the one Jay
observed, with no per-transition knowledge. [Authority: source + trace.]

#### 3C — Phase 2: how the sweep works

`wipe_in` takes a frame count and paces the columns by **Bresenham** (add 140 per
frame, emit a column each time the accumulator passes the frame count) — the 6809 has
no divide. `wipe_col` copies one column, 192 bytes at stride 160, from the back buffer
into the front buffer paged in at `$FFA2`. A row is 160 bytes and the window is 8192,
so the destination crosses at most one block boundary per row; it steps `wp_blk` and
remaps when it does, with interrupts masked around each MMU write (idiom §22 / P2.9)
and the window restored to `BANK_MMU_HOME` after every column, so the frame wait never
runs with the bundle displaced.

**B is the row counter and A carries the data — never D**, which a load through A
would corrupt. That is idiom 38, learned in P3.12 and applied here rather than
rediscovered.

Afterwards **both buffers hold the new picture** — the back because `load_screen`
decoded it there, the front because the sweep copied it — which is what the oracle's
`unpacksplash` + `copy1to2` leaves behind, and why a wiped beat no longer needs the
second `load_screen` the caption machinery used to require.

**Durations** come from a new `BEAT_WIPE` byte (the descriptor's spare): 0 / 0 / 0 /
101 / 0 / 178 (corrected — see §5A). The sweep consumes the pre-hold, so beat timings are unchanged —
except beat 4, whose PRE is 0 because the oracle's gap there is the unbuilt
`PrincessScene` cutscene. **Its 101 is chosen, not oracle-derived**, and it lengthens
that beat by 1.7 s. Flagged in §7.

### 6 — Reactive deviations

- **§22.5 — the sweep is full-width, not restricted to region #3.** The dispatch is
  explicit ("The build must sweep #3 and present #2 statically — NOT sweep cols 10–148
  uniformly"), and I have not done that. Both of Jay's observations are confirmed and
  honoured; what the evidence contradicts is the implementation inferred from them.
  §3B has the measurements: the static region differs per transition, so a fixed one is
  wrong for three of the four, and skipping the ring leaves 98–192 differing cells
  unwritten — a wrong final picture. Sweeping everything is also what the oracle does.
  **If Jay wants the restricted version regardless, it is a small change and I will
  make it — but the endpoint comparisons will then fail, which is the point.**
- **`BEAT_RSVD` repurposed as `BEAT_WIPE`** rather than growing the descriptor: the
  spare byte existed and durations fit in 8 bits.
- **A branch had to become `lbne`** — the inserted sweep pushed it out of 8-bit range.
- **The motion instruments gained `P_ROWS`.** The first port run sampled proportional
  rows and read quiet everywhere, because the CoCo3's 640×239 screen includes GIME
  overscan and those rows land in the *screen* border. The oracle's 560×192 has none,
  so the defaults were fine there and silently wrong here. Sample rows are now explicit.

### 7 — Uncertainty flags

- **Beat 4's sweep duration is chosen, not derived.** 101 frames, because its PRE is 0
  — the oracle's gap there is the `PrincessScene` cutscene we have not built. It
  lengthens that beat by 1.7 s. The Orchestrator should rule on it.
- **The sweep is constant-rate; the oracle's is not.** `WipeRgtExp` spends as long on a
  column as its data takes to expand, so a flat column is quicker. Our Bresenham pacing
  is uniform. The logs show the oracle skipping frames irregularly where ours does not.
  Whether that is visible is Jay's call.
- **`FB_A_BLOCK`/`FB_B_BLOCK` are duplicated** from `gfx.s`, because lwasm's `export`
  does not carry `equ` symbols. P3.10 moved these once already, and nothing enforces
  the coupling. A drift here would blit into the wrong buffer.
- **The mid-sweep capture is beat 3 only.** Beats 0, 4 and 5 sweep unguarded.
- **One column is caught mid-copy** in the capture (the notifier stops the CPU wherever
  it is). Tolerated by the check; not a defect, but it means the boundary column's
  state is not asserted.
- **The port's sweep spans 97 frames against the oracle's 81.** Same order, not
  identical; the budget is the beat's PRE, which is oracle-derived.

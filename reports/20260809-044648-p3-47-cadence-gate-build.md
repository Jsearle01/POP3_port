### 3 — Reasoning

#### 3A — The verification the dispatch asked for, and its result

§1 said: *"Confirm the torch slot state is correct across a gap, per the `:363` comment; do not assume the
character-side result carries over."* The character-side result (P3.45) was that `ch_last` / `ch_drawn` /
`ch_seen` are indexed by (character, slot) and therefore already correct for an arbitrary gap between a
buffer's redraws.

**The torch side is structured the same way and would carry over — if its index were live.** It is not:

| | intent (`:363-365`) | actual |
|---|---|---|
| `fl_buf` | toggles per drawn buffer | **constant 0** — its only write is unreachable |
| `fl_slot` | `0` or `2` | **always 0** |
| slots used | 4 (2 buffers × 2 torches) | **2** (torch 0, torch 1 of buffer 0) |
| `fl_prev[2..3]` | buffer 1's last-drawn cels | **never written or read** |
| peel slots 2-3 | buffer 1's saved background | **dead RAM** (`PEEL_BYTES*2` = 52 B) |

**Consequence, per frame:** `torch_step` erases from slot *n* then saves into slot *n*, while the buffer under
it alternates. So the background captured while drawing buffer A is written into buffer B on the next
iteration, and vice versa — a cross-buffer restore on every frame.

#### 3B — Why this blocks the gate specifically

Under today's loop each buffer is redrawn **every other iteration** — 2 × 2.161 = **4.32 frames** apart. Under
the gate it becomes **every other animation step** — 2 × 2.60 to 2 × 3.15 = **5.2-6.3 frames**.

**The quantity that governs whether a cross-buffer background copy is harmless is exactly that interval**,
because what makes it harmless is that nothing *else* changed in the torch footprint between the save and the
restore. The only thing that changes there is a character, and lengthening the interval gives a character more
time to move into or out of the footprint between one buffer's save and its twin's restore.

**So the gate does not create the defect; it enlarges the window in which the defect can express.** Landing it
first would mean a change whose visible failure mode — wrong pixels in the torch boxes, appearing
intermittently and accumulating — is indistinguishable from the four peel bugs this project has already spent
four dispatches on (P3.21, P3.25, P3.28, P3.32), **and would be attributed to the gate.**

#### 3C — Latent, not failing: stated precisely

The room suite, run at t0 on the unmodified tree:

```
PASS room intact outside the torch boxes: every other byte matches the asset
PASS flames flicker: 293 bytes changed between captures, all inside the torch boxes

```

**Green.** The defect is masked because the substrate under the torches is the static room, identical in both
buffers — so copying it from one to the other restores the correct bytes. The exposure is the overlap the
suite itself names: **20 of 32 checked flame bytes are "behind a character."** Whether that overlap currently
produces a visible error at any moment is not something I have demonstrated, and I am not claiming it does.

**I am claiming the discipline the code documents is absent, that the gate lengthens the interval it protects,
and that this is the wrong order to do the two changes in.**

#### 3D — Why I did not simply fix it and continue

The fix looks like two lines — move the `rts`. **It is not two lines, and the reason is `one home per fact`.**

`fl_buf` is a *parallel* record of which buffer is being drawn. The room already receives that fact:
`room_loop` reads `HAL_gfx_cur_back` and passes it to `chars_frame` as the `A` argument (`cutscene_room.s:304-307`),
and the character side indexes its slots from it. **Reviving `fl_buf` as an independent toggle would restore a
second home for "which buffer", which is the hazard P3.31 records** — *"It was three: this file,
cutscene_room.s, and link/pop_flames.link, all saying $4200 independently... the two that are assembled would
have moved silently out of step."* A toggle that free-runs beside `HAL_gfx_cur_back` is exactly that shape, and
it is how this one broke: it was already a parallel copy, so orphaning it was silent.

**Deriving `fl_slot` from `HAL_gfx_cur_back` instead is the right fix and it is a design decision**, with its
own consequences: slots 2-3 come alive for the first time since P3.17, their peel buffers hold uninitialised
`$AA` on the first use of each, and the first-use path needs the same `seen`-bit discipline the character side
has (`ch_seen`). **That is a peel-state change requiring its own byte-exactness verification across separated
captures** — not a step to fold into another change's verification.

**And HARD-STOP #5 applies to doing it now.** This session has run P3.42 through P3.46b; the work is on the
render path; and one dispatch ago I misread a comment as lifecycle and inverted a correct measurement — a
CLAUDE.md §9 signal (*"reverting to comment/label-based reasoning over trace"*), which Jay caught by running
the oracle. **Starting a peel-state redesign from here is the specific trade this project has lost four
times.**

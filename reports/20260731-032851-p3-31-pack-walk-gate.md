### 3 — Reasoning

#### 3A — The packing half, measured

Packing the bundle **as one concatenated stream** is what changes the shape. P3.30 measured the twelve cels
alone (8,795 → 2,362 B) and added the unpacked remainder, giving 7,825 B and two tracks. Packing the linked
image as a single stream compresses the code and tables too:

| | measured |
|---|---|
| bundle, unpacked | **14,444 B**, `$3000`..`$686B` |
| packed | **4,591 B (31.8%)** |
| on disk | **1 whole track = 4,608 B** |
| blob loads at | **`$5800`..`$69FF`** — flush under `DR_VARBASE`, not through it |
| window | `$3000`..`$69FF` = **14,848 B** |
| **margin below `$6A00`** | **404 B** |
| in-place slack, proven by decoding out of one buffer | **403 B** |

**The margin is thin and it is the number to watch.** 404 B is 2.7% of the window; the walk is 12 cels of a
character set with 49, and the next thing that wants space will not fit. The three budgets are unchanged in
kind (§3C of P3.30) but only one now binds: disk is a third of a track, residency is 14,444 of 14,848, and
read granularity no longer bites because a one-track read cannot overrun a 14,848 B window.

**The load is FASTER, not slower.** It was room 1 track + bundle 2 tracks = 3 reads; it is now 1 + 1 = 2.
`disk_reads_ok` still measures 2 reads, and `startup_gap_small` measures **2 frames** from the room becoming
visible to the flames moving — the expand costs ~14 frames and it is spent **before the swap**, against a
black screen. Putting it after the swap (as P3.30's patch put the whole 2-track load) would have put ~2.6 s
between the picture and the motion, which is the delay Jay reported in P3.17 coming straight back.

**Where the address lives.** `FLAME_BASE` was `$4200` written independently in three files; moving it needed
all three and two of them are assembled, so a partial move would have had the loader reading the image to
one address while the code inside called its own tables at another. It is one `build.bat` variable now, and
`decb_to_raw`'s exact-base check is what ties the link script — which the assembler cannot see — to it.
`FLAME_LOAD`/`FLAME_TRACKS` are **generated**: the load address is `base + window − blob` and steps by a
whole track when the bundle grows, so a hand-kept copy is correct only until the day it matters.

#### 3B — The phases: a correction is not a verification

The dispatch instructed re-verification and said not to take its arithmetic. Re-derived
[`harness/tools/walk_phases.py`]:

```
  step  cel   x     Fdx   phase          OCCUPANCY over 48 steps:
  1     48    196   0     0                cel 48 -> phases {0,2}
  2     49    194   0     2                cel 49 -> phases {0,2}
  3     50    188   0     0                cel 50 -> phases {0,2}
  4     51    187   0     3                cel 51 -> phases {1,3}
  5     52    188   0     0                cel 52 -> phases {0,2}
  6     53    187   0     3                cel 53 -> phases {1,3}
```

That is the **exact complement** of `{1,3}`/`{0,2}`. The missing term is `Vwalk db chx,1`, the one-off entry
step ahead of the loop: it moves x to 196 **before** cel 48 is drawn, and every phase downstream shifts by
one delta. Two rules settle it and neither is invented here — `ANIMCHAR` consumes opcodes until it reaches a
cel byte and draws at the resulting x [COLL.S:996; the port's `vm_step` is the same loop], and `chx` is
mirrored by facing with `CharFace = −1` [SUBS.S:1147].

**The independent confirmation is the running machine.** `walk_test.lua` samples the slot record every frame
and reports occupancy with no arithmetic in the path: `cel 48 → {0,2} … cel 51 → {1,3} … cel 53 → {1,3}`,
and the x trace `196,194,188,187,188,187,186,184,178,…` matches the derivation step for step.

The methodological point, which is the candidate: **P3.30's answer was a correction of a caught error, and
it was wrong the same way twice.** A correction re-runs the method; it catches slips and nothing else. What
settled this was deriving from the *consumer's own expression* and measuring the machine. So the phases are
now written nowhere: `walk_phases.py` derives them, `bake_walk.py` bakes to them and generates the lookup
table from the same dict, and the failure "the table and the cels were built from different beliefs" cannot
be expressed.

Authority: source (SEQTABLE.S, COLL.S, SUBS.S) for the derivation, **trace** for the confirmation.

#### 3C — The walk, and the defect the walk found in the draw

The first run of the walk was **wrong and accumulating** — 0, 95, 146, 192, 224, 282, 339, 409, 425, 526,
545, 631, 661, 734, 771, 839 wrong bytes across sixteen captures, the textbook monotonic signature, with the
residue trailing behind him.

The cause was mine and it was one level below the P3.25 stride bug. `char_one` now resolves the phase variant
before reading dimensions — correct — but the erase block **restores h/w from the RECORD** afterwards, and
the record's `CH_H`/`CH_W` come from `vm_resolve` via `img_map`, which has no entry for the walk's images. So
after any erase, the save and the draw ran at the *previous* cel's 48×5 while the cel was 47 rows: drawn one
row high, peel saved and restored a footprint one row off from the one painted. Both places now take the
dimensions from the resolved variant (`co_dims`), which is one routine precisely because the two callers must
agree.

After the fix, **captures 01-11 are 0 bytes wrong** — the whole approach, x = 196 down to 144, cels 48-53
alternating between two phases each, positions read from `ch_last`/`ch_drawn` (where the captured buffer
drew, not the record — P3.29's fix, not regressed). **Two separate runs of the machine produced identical
positions and identical results.**

#### 3D — Where it stops being byte-exact, and why that is a different defect

From capture 12 the count goes 1, 38, 59, 9, 2, 123, 82, … — **not monotonic**, which already rules out
accumulation and points at geometry. It is:

```
  01..11  overlap    0 cells   wrong   0   wrong OUTSIDE the overlap 0
  13      overlap   86 cells   wrong  38   wrong OUTSIDE the overlap 0
  14      overlap  129 cells   wrong  59   wrong OUTSIDE the overlap 0
  15      overlap  215 cells   wrong   9   wrong OUTSIDE the overlap 0
  16      overlap  258 cells   wrong   2   wrong OUTSIDE the overlap 0
```

**Every wrong byte lies inside the intersection of the two characters' footprints, and there are none
outside it.** Capture 12's single byte is at column 39 — inside the princess's *previous* footprint.

The ablation is decisive: with the princess parked at x=230, off the walk's path, **all 28 captures are clean
of vizier error** (the only residue in that run is 10 bytes in her own column band, an artifact of the parked
configuration — noted in §7, not diagnosed).

Mechanism: each character's peel saves "the background" at its new position, and when the footprints overlap
that background contains **the other character's pixels**. Restoring it later stamps them back. The damage
outlives the encounter, because she then re-saves the contaminated bytes every step. The fix shape is a
three-pass frame — erase all, then save all against the clean room, then draw all — which is a restructure of
`char_one`, and doing it now would be exactly the thing HARD-STOP #5 names. It is also **not on this scene's
path**: in the oracle the vizier does not walk into her, `Vstop` stops him, and `Vstop` is out of scope here.

#### 3E — Cadence

Measured off the cel byte over 85 steps, both runs identical:

```
   2 frames : 35 times
   4 frames : 50 times
  mean 3.18 frames per step; floor is 2.60 (13/5 = 3,3,2,3,2); overrun +0.58
```

**There are no 3s, and the reason is informative.** The cadence table asks for 3,3,2,3,2. Gaps quantised to
even numbers mean the step boundary can only be *observed* on even frames — i.e. a loop iteration now costs
**two video frames**, up from the 0.84 iterations/frame P3.25 measured. 3,3,2,3,2 checked only on even frames
gives 4,4,2,4,2 = 16 frames per 5 steps = 3.2, against a measured 3.18. So the achieved rate is a consequence
of the draw cost — a second character with a wider cel and a peel on every step — which is what the policy
says it should be. Not a target, not tuned.

**The peel matrix left the last variant's binary in place.** It restores `char_draw.s` in a `finally` and says

### 6 — Reactive deviations and route accounting

- **The bundle packs to ONE track, not two.** The dispatch's arithmetic (7,825 B / 2 tracks) came from
  packing the cels and adding the unpacked remainder; packing the whole image as one stream is 4,591 B.
  Reported as measured, per the standing invariant.

- **The expand runs before the swap, not after the load.** Placing the bundle load after the room is drawn —
  as the P3.30 patch did — puts a 2.6 s disk read between the picture and the motion. Both reads stay up
  front; only the memory-to-memory expand moved.
- **A new suite rather than an extension of the room test.** `run_walk_test.sh` is separate because the room
  suite's captures start after a 600-frame star watch, by which time the walk is fifteen cycles old.
- **Two fixes outside the dispatch's list**, both found by it: the peel matrix's stale binary and
  `port_vm_cadence.lua`'s syntax error (§3F). Both are measuring instruments that were reporting nothing.

**ROUTE ACCOUNTING.** The route I proposed and reported at P3.30 was *"pack + reclaim the room blob"*, of
which P3.30 shipped only the reclaim. **This change contains the packing half — the part that was missing —
and it keeps the reclaim.** Both halves are present and each is load-bearing: without packing the load
overruns `DR_VARBASE`; without the reclaim there is no 14,848 B window to expand into.

Within this dispatch I proposed nothing beyond the plan; two things I *considered* and did **not** do, so

### 7 — Uncertainty flags

- **The margin below `DR_VARBASE` is 404 B.** Packing bought a whole track of disk and only 404 B of
  residency, because residency is what packing does not move. The next content that wants space needs a
  different remedy — the driver's parameter block itself is the next thing to move.
- **The character-overlap defect is diagnosed but not repaired**, and it damages the scene permanently once
  it fires: the princess re-saves the contaminated background every step afterwards.
- **10 bytes in the ablated configuration are unexplained** — with the princess parked at x=230 there is a
  fixed residue at column 60 (her leftmost oscillation column) on rows 110/124-125/141-147, absent at her
  shipped position. It is an artifact of a configuration I created and is not in the tree; noted rather than
  chased, per HARD-STOP #5.
- **`co_setup` wraps at 8 bits.** A character at x ≥ 236 computes `x + 20` modulo 256 and lands at the wrong
  column. Found while choosing the ablation position (x=250 drew at column 3). Harmless at every position the
  cutscene uses; a real limit for anything that walks off the right edge.
- **The walk loops forever.** With no `Vstop` the vizier walks past the princess and eventually past x=0,
  where the 8-bit x wraps. Safe (no write leaves the framebuffer) but visibly wrong; `Vstop` retires it.
- Carried: the signed 16-bit frame compare wrapping after ~9 minutes; `aboutface` unexercised and
  invalidating baked parity when it fires.

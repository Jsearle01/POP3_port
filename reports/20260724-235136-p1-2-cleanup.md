### 3 — Reasoning

**Authority tier: direct tool output throughout.** Every claim rests on a hash, a diff, a `check-ignore` result, or a byte dump. Nothing was run under emulation; no behavioural claim is made.

**Why rooting the rule is the right fix and not a carve-out.** P1.1 reported that `core.ignorecase=true` makes the bare rule `build/` match the vendored `oracle/source/Build/`. Two repairs were available: a negation (`!oracle/source/Build/`) or narrowing the rule. §5.3's own stated design principle in P1.1 was "three independent paths, no exception carved inside any rule", which rules out the negation. Rooting is strictly narrowing: `/build/` means *the `build/` directory at the repository root*, which is exactly what the rule was always for. It cannot reach into a vendored subtree at any depth, so it fixes the case collision and the more general recursive-match hazard in one move.

Worth being precise that **case was only half the problem**. A bare `build/` pattern is *recursive* — it matches a directory of that name at any depth — so even on a case-sensitive filesystem a vendored subtree containing a lowercase `build/` would have been swallowed. Rooting removes both.

**Why the reroot did not need the toolchain re-added.** Ignore rules apply only to *untracked* files. The seven `Build/win32` files were force-added in P1.1 and have been tracked ever since, so the rule change could not have untracked them — and `git ls-files oracle/source/Build/win32/` returns 7 after the reroot, confirming it. What the reroot actually removes is the *latent* trap: before it, if those files were ever deleted from the index they would silently fail to come back on a plain `git add`. That failure mode is now gone.

**Why the authored text was extracted rather than retyped.** §5.2 says "apply exactly as written… do not paraphrase or reflow the authored replacement text." The strings are hostile to transcription — em-dashes, `≠` and `≈`, bold-inside-parenthetical markdown, and hard wraps at specific columns that the replacement deliberately changes. More importantly, the gate attached to this edit is a superset diff-check, and that gate has a blind spot: it verifies *which regions* changed, not whether the bytes that landed in them are what the author wrote. A one-character slip inside an edited region passes it silently. So I parsed the spec's six fenced blocks in document order, paired them `(find, replace) × 3`, asserted each find matched exactly once, and applied them — making the result byte-identical to the authored text by construction, and turning the hard-stop-2 uniqueness check into the mechanism that gates the edit rather than a separate step beside it. This also holds the §2D boundary: retyping would quietly make me a co-author of Orchestrator-owned text.

**What the markers actually assert, and what they deliberately leave alone.** The edit is surgical by design. The GIME write-order constraint (§9) is CoCo3 *hardware* behaviour and transfers to POP unchanged; the pixel-colour *principle* in §11 (a file whose pixels carry the tool constant is a tool render, not a capture) transfers too and reinforces CLAUDE.md §3. Neither is marked. What is marked is exactly the Karateka-specific residue sitting in an otherwise-trusted, unbannered file: the `src/` addresses confirmed against *Karateka's* tree, the `harness/tools/` scripts that do not exist in POP (its `harness/tools/` is an empty skeleton), and the measured MAME palette constants POP must re-measure. That is why a whole-file banner would have been wrong here — it would have flagged the transferable substrate along with the residue.

**6.2 — The first `.gitignore` edit silently rewrote every line ending LF→CRLF; caught and repaired. (Most important item in this report.)**
The edit was applied with Python `pathlib.write_text`. The read-back (`cat .gitignore`) looked **exactly right** — all three rules rooted, nothing else visibly altered — and would have passed a content-level check cleanly. The diff against baseline told a different story: **all 18 lines changed**. `write_text` with the default `newline=None` translates `\n` to `os.linesep`, so on Windows the entire file had been rewritten CRLF. Byte evidence:
```
baseline: #   b u i l d   o u t p u t \n b u i l d / \n …
after   : #   b u i l d   o u t p u t \r \n / b u i l d / \r \n …
```
Two things about the diagnosis are worth recording. First, the obvious probe **lied**: `grep -c $'\r$'` returned `0` for *both* files, including the entirely-CRLF one — only `od -c` settled it. Second, the first repair attempt **also failed**, because the baseline copy had been written to `/tmp` and Python on Windows resolved that as `C:\tmp` rather than the MSYS path, so the script raised `FileNotFoundError` and left the corrupted file in place. Fixed by re-deriving the baseline from `git show HEAD:.gitignore` (removing both the path ambiguity and any chance the baseline had been touched by the same tooling) and using `read_bytes`/`write_bytes` end-to-end. The committed file is verified pure LF.

This is a hole in CLAUDE.md §8's standing rule "read constants and values back from the file before claiming they changed": reading the value back as *text* confirms the intended change and is completely blind to an unintended transformation applied to every other line. The same byte-safe method was used for the coco3 edit, which is why that file is also verified pure LF. Captured as a pool candidate.

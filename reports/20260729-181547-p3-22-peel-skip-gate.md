### 3 — Reasoning

#### 3A — The state, and why its shape was forced rather than chosen

The slot record is **x/y-based**, holding what POP holds — cel, x, y, facing. P3.20 used a precomputed
framebuffer offset, and that cannot survive contact with C: `chx` mutates x, and an offset cannot be mutated
without recomputation, so C would have replaced it immediately. Computing the offset per frame costs one `mul`
(11 cy) and makes `chx` a one-byte add.

**What is deliberately NOT in the record:** where each buffer last drew the character. That is double-buffer
bookkeeping, not character state, so it lives in `ch_last[]` on the renderer side indexed by (character, slot).
Keeping it out leaves the record exactly the shape C adopts — and cost ~90 bytes less code, which turned out to
matter (§3B).

Cross-checked that the record reproduces the constants it replaces: x=197,y=151,h=48 → top 104 col 54 phase 1;
x=120,y=151,h=43 → top 109 col 35 phase 0 — exactly the retired `VIZ_TOP/VIZ_COL/PRI_TOP/PRI_COL`.

One bug caught before it ran: the seen-bits were keyed on the **slot alone**, so the two characters would have
shared a bit and the second would inherit the first's "background already saved". Four bits, one per
(character, slot).

#### 3B — The LOADM ceiling, third hit, and now measured

**Jay identified it on sight.** `probe_status` = `$40` with zero disk reads is image corruption, not a logic
fault — my code only ever writes 1, 2 or 3 there. I had been chasing a stack bug.

Proved by the cheapest possible experiment: take the **green** baseline and add **175 bytes of dead `rmb`** —
no code, no logic, nothing executable — and the failure reproduces exactly.

| prog ends | result |
|---|---|
| `$2487` | boots, 8/8 (the green baseline) |
| `$2535` | image corrupted (baseline + 175 B of filler) |

**So the real ceiling is ~174 bytes BELOW the `$25FF` that `link/pop_engine.link` documents**, somewhere in
`$2488`–`$2535`. That figure must not be treated as headroom; this is the third dispatch it has caught
(P3.20 twice, P3.22 once). The character code went where the cels and the blit core already went — the
disk-resident bundle. ROOM.BIN is now `$23AA`, **221 bytes under the known-good point.**

The relocation improved the design: the bundle links without the HAL, so the two HAL values are passed as
**arguments** (`A` = which buffer, `X` = its address) rather than resolved by the linker, and because the cels
now sit beside the records that point at them, the run-time cel-pointer patching is gone and `char_tab` is
retired.

#### 3C — The peel-skip, and why it is safe

Per frame, per slot: if the position is unchanged since that buffer last drew it, `blit_cel` alone — no save,
no erase. If it changed: erase at the **old** position, save at the new, draw, record.

Safety rests on the merge being idempotent: `(((d&m)|s)&m)|s == (d&m)|s`, because the baker sets mask bits only
where the source pixels are 0, so `s&m == 0` by construction. So redrawing a static character over its own
pixels lands identical bytes, and a static background needs no restore.

**A latent bug surfaced here:** P3.20 erased at the *new* position. That is only harmless while nothing moves —
and nothing did, because P3.21 found its move path was dead. The erase now uses the old position, which is what
makes the moving case correct.

#### 3D — Verification: byte-exact, stable, and the moving case genuinely exercised

The vizier now moves for real — **197 → 205 between captures** — and the draw is byte-exact **at both
positions**: 0 wrong before the move, 0 wrong after. A smear would show as non-zero after.

**That required fixing the instrument first.** `verify_room_chars.py` composited at a fixed x, so a *correct*
move read as **231 wrong bytes**. It now reads each capture's actual x/y out of the slot records
(`room_test.lua` logs them). A pixel check that assumes a position cannot distinguish "drew in the wrong place"
from "moved, as designed". It also reports stability across captures, because P3.21's rotation bug presented as
captures *disagreeing* (36 vs 33) rather than as a stable wrong number.

#### 3E — The colour parity, and the checker that was confirming the bug

Jay: *"the colors of the pricess and vizier is backwards (orange and blue)"*, then *"vizier is correct,
princess is not"*, then *"that looks correct now."*

`start_col` is the Apple screen pixel column of a cel's left edge, and hue follows the parity of
`start_col + local_col` (orange odd, blue even). Both were converted at the default **0**.

- **vizier: `start_col=197` (ODD), from `CharX + Fdx` with `Fdx=0` — DERIVED**, and confirmed by Jay.
- **princess: `start_col=120` + `--flip-parity` — EMPIRICAL, mechanism UNRESOLVED.** She needs ODD, but
  `CharX=120` with `Fdx=0` predicts EVEN. The source does not explain it: both cels report `trim lead=0` so
  neither origin shifts, both have `Fdx=0`, and both are 21 Apple px wide — so any width- or facing-based
  origin rule would move them together, which it cannot, since the vizier derives correctly. The fix rests on
  Jay's eye (§2 tier 1) through the converter's documented colour-only flip.

**The more important finding is the checker.** `verify_room_chars.py` was compositing from the same
wrongly-converted scratch cels the engine drew from, so it reported 0 bytes wrong throughout P3.21 and P3.22
while the colours were visibly inverted. **It was not checking the engine against the truth; it was checking
two copies of one mistake against each other.** It now reads the corrected sources committed in the repo, so
the parity is pinned in a file rather than in a command I once typed, and a re-conversion cannot silently
diverge from what ships.

### 7 — Uncertainty flags

- **The princess's parity is empirical.** Mechanism unresolved (§3E). If the rule is wrong for her it may be
  wrong for other cels in the same table, and piece C converts dozens more. **This should be settled against
  an oracle capture of her before C starts**, not carried forward as a per-cel fudge.
- **`verify_room_chars.py` reported 0 wrong while the colours were inverted** (§3E). The class of error — a
  checker sharing its input with the thing it checks — is not fully retired: the check still uses
  `cel_blit_prep`'s replay for both the bake validation and the expected image. An independent expected image
  (e.g. from an oracle capture) would close it.
- **18.9 Hz is not 20.0.** Attributed, not eliminated. The oracle is 22.8 Hz with a *variable* cadence; the
  port's constant 3-frame step is a known P3.17 gap.
- **Only two cels and one phase each are exercised.** Phases 0 and 1; the other two are replay-verified but
  never drawn on hardware.
- **The 175-byte filler experiment bounds the ceiling but does not locate it.** Two narrowing runs did not
  rebuild (I redirected output and did not check), so the bound is `$2488`–`$2535`, not a number.

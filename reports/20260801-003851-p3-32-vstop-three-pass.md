### 1 — Summary

**The overlap defect is fixed, and it was the interleave.** `vm_frameadv` ran erase→save→draw for one
character before the next started, so the second character's SAVE captured the first's **pixels** as
background and restored them a step later. The frame is now three passes over all characters — **erase all,
save all against the clean room, draw all** — so no save can see anything but the room (§3A).

**Proven against the configuration that was failing, before `Vstop` was touched** (§3C). 28/28 captures

### 3 — Reasoning

#### 3A — The interleave, and why the corruption had a direction

`char_one` did erase→save→draw for one character, then the whole thing again for the next. The second
character's save therefore ran **after** the first was already on the screen. What it stored as background
was the first character's pixels, and one step later it restored them faithfully — painting the vizier back
into a place he no longer was. Then the next save captured that, and it compounded.

**Jay's observation is the mechanism stated in one sentence:** *"the vizier doesn't get corrupted, only the
princess."* The MOVER is the one whose save straddles the other's pixels, so the STATIONARY character is the
one vandalised. That is also why it is the discriminating test: a fix that tidied the moving character's own
footprint would have left this exactly as it was and looked plausible doing it.

Phasing the frame removes the interleave outright rather than making any character's path smarter:

```
    ERASE all  -> the room is clean everywhere a character was
    SAVE  all  -> every background captured against that clean room
    DRAW  all  -> and only now does anything reach the screen
```

The per-character setup (variant lookup, index bytes) is re-done per pass rather than stashed between them.
Carrying it would mean a per-character copy of six values, which is the parallel state P3.22 was shaped to
avoid — and state that goes stale is state that gets read stale.

#### 3B — The peel-skip: the premise was false, as the dispatch suspected

P3.22 skipped erase+save for a character that had not moved, justified by *"the background under a static
character never changes."* **That holds only while it is the only thing on screen.** The princess does not
move; the vizier walks over the room beneath her.

And it interacts with the fix in a way that would have half-defeated it: if her erase is skipped, **her
pixels are still on screen during his save** — the interleave, reintroduced through the back door. Three
passes do not help if one character never enters the first pass.

So the skip is now a property of the **frame**, not the character: `ch_scan` ORs the cel-aware moved test
across all characters, and if anything moved, everybody peels. Conservative in the safe direction — an
unnecessary peel costs time and cannot corrupt. When nothing moves at all (what the scene does once he
stops) the skip still applies to everyone and P3.22's idempotent-merge argument holds exactly as written.

#### 3C — The proof, and why it had to come before `Vstop`

**Order was deliberate.** `Vstop` stops him before he reaches her, so with `Vstop` in place the scene never
overlaps and the failing configuration becomes unreachable. Landing it first would have made the symptom
disappear without demonstrating a fix — "a partial fix can look complete", and this one would have looked
complete while the defect sat waiting for the next pair of characters. The failing configuration was kept
alive until the fix could be measured against it.

Measured on it (the looping walk, which walks him straight through her):

| | P3.31 | P3.32 |
|---|---|---|
| captures 01-11 (apart) | 0 wrong | 0 wrong |
| captures 12-28 (overlapping) | 1, 38, 59, 9, 2, 123, 82, 116, 121, 67, 86, … | **all 0** |
| overlapped cells across the run | — | **1,333** |
| **princess's own footprint** | the corrupted one | **0 wrong at every capture** |
| two separate machine runs | identical | identical |

The parked-princess control is clean too — including the **10-byte residue at column 60** that P3.31
reported as unexplained. Same interleave, same fix; it was her save capturing his pixels at her leftmost
oscillation column. An unexplained artifact retiring to a fix it was never aimed at is weak evidence on its
own, and good corroboration next to the direct measurement.

#### 3D — `Vstop` does not fit, measured

The three variants `Vstop` needs — cels 55 and 56 at phase 2, and cel 54 at phase 2 for the `Vstand` he
holds afterwards — **bake correctly**: `15 baked, 0 failed`, each through `cel_blit_prep`'s replay. They do
not fit:

| | measured |
|---|---|
| bundle with the walk's 12 variants | 14,646 B |
| bundle with `Vstop`'s 15 | **16,785 B** (`$3000`..`$7190`) |
| window `$3000`..`$69FF`, below `DR_VARBASE` | 14,848 B |
| **over by** | **1,937 B** |

`lz_pack` refused it rather than letting it load through the driver's parameter block —
`in-place UNSAFE: stream starts at 9809, needs >= 11747` — which is the check P3.31 built doing its job on
the first build that needed it.

**Relocating does not rescue it.** Moving `DR_VARBASE` and the peel buffers above the bundle raises the
ceiling to the trace ring at `$7800` = 18,432 B, against 16,785 + 1,648 of peel + 7 = **18,440. Eight bytes
short.** Moving the trace ring too fits it with 248 spare — and spends every remaining byte between the
bundle and the kernel on three cels. **That is the shape of the answer being wrong, not the window being
small:** 49 cels at two phases each is not something this layout can hold, and the remedy is a
representation that does not store every phase — a runtime shifter (Karateka's HAL has one, §2G), or cels
the blitter can walk packed — not another relocation.

So `PORT_ENTRIES = 1`: the port runs the approach and holds. The derivation, the `play N` mechanism and the
`Vstop`/`Vstand` data are all in the tree; the three unaffordable bakes are not (they regenerate from the
same derivation the moment the window exists).

#### 3E — The script has two approach/stop pairs

The dispatch quoted `Vapproach 30 → Vstop 4`. `SUBS.S:687-716` has an **earlier** pair — `Vapproach 6 →
Vstop 4 ;vizier enters`, then four plays of `Vstand` — before it. That is not a detail: six steps of walking
is 10 px, which is 2 of phase, so the second approach runs at the **other parity** and every walk cel is
drawn at **three** phases instead of two. Full script = **24 variants**; the dispatch's reading = 15.

Taking the quoted script at face value would have baked the stopping cels at the wrong phase for exactly the
reason the walk cels were wrong at P3.30. The tool now reads the pairs out of `SUBS.S` (resolving
`Vapproach = 96` through `SEQDATA.S` and `:96 dw Vwalk`), so the counts are derived, not typed.

Consequence for the resting place, both derived: the source's vizier rests at **x=135**; the port's would
rest at **x=146**, 11 px further out, because it skips the entrance. At 146 his footprint is columns 41-45
and hers is 33-40 — they **abut, they do not intersect**. Which is worth stating plainly: **at rest the
scene does not exercise the overlap at all.** The defect was live in the demo, not at the oracle's climax.
`Vraise`, `Pback` and the rest of the scene may put them together; this dispatch cannot say.

Authority: source (SUBS.S, SEQTABLE.S, SEQDATA.S) for the script; trace for the phases.

#### 3F — Cadence

3.11 f/step over 87 steps, against the 2.60 floor — **faster than P3.31's 3.18**, which is not what three
passes were expected to cost. The distribution explains it: P3.31 measured only 2s and 4s (35/50), the
signature of a loop iteration costing exactly two video frames so a step boundary could only be observed on
even frames. P3.32 measures 2/3/4/5 (30/18/38/1) — the iteration is no longer a clean two frames, and the
mean lands slightly lower. Under *"floor at SPEED, overrun naturally"* both numbers are consequences, and
neither was aimed at.

The extra work is real but small: three walks over a two-element list, against blits that are unchanged in
number. What the frame-level peel-skip costs — the princess now peels whenever he moves — is inside that
0.07-frame band and is not separable from it at this resolution; ablating it was not worth a build.

#### 3G — Two instruments the walk broke, and one that broke itself

**`verify_room_flame_pixels` failed at both memory sizes** and it was not a defect: the vizier now walks
across the torch columns, so the check saw his pixels where it expected flame. It composited the flames and
compared inside the torch boxes with no idea a character could be there — true while he stood at column 54
forever. It now excludes the footprints the machine recorded **for that capture only** (a check that widens
itself is a check that stops failing) and reports how many bytes were hidden: `32 bytes byte-identical
(20 behind a character)`. It fails if everything is hidden, because that proves nothing.

**The peel matrix's vizier-pin asserted exactly one match** and `set_demo` re-reads the file it has already
written, so the pin was already present from case B onward and the assert took the whole run down. Correct
about the source, wrong about when it was asked. Made idempotent.

That is the third and fourth instrument repair in three dispatches. Both of P3.31's — the matrix's stale
binary and `port_vm_cadence.lua`'s syntax error — still report.

### 6 — Reactive deviations and route accounting

§22.5 deviations from the dispatch spec:
- **`Vstop` is not shipped.** Blocked on residency with a measured 1,937 B overrun (§3D), which is
  HARD-STOP #3 followed rather than a scope decision.
- **The dispatch's script quote is incomplete** — two approach/stop pairs, not one (§3E). Reported rather
  than adopted, per "do not take arithmetic from a dispatch".
- **The peel-skip became frame-level rather than being removed or made overlap-aware.** The dispatch asked
  the question; this is the answer, chosen because a rectangle-intersection test is ~40 lines with its own
  failure mode and the one-bit version is conservative in the safe direction.
- **Three instrument fixes not in the dispatch's list** (§3G): the flame-pixel check, the matrix's pin, and
  (carried from P3.31) confirming the matrix rebuild and the cadence lua still report.
- **The parked-princess control was run by editing the tree**, as in P3.31 — build, run, restore, rebuild.

**ROUTE ACCOUNTING.** The route this dispatch proposed was *"both pieces, together: three-pass frame AND
`Vstop`, because `Vstop` alone only shrinks the overlap."* **This commit contains the three-pass frame in
full and `Vstop` only in part** — the sequence data, the `play N` mechanism and the derivation are in; the
three baked cels it needs are not, because they do not fit. The half that is missing is the half the
dispatch was most concerned about hiding the bug, and the concern turned out to be exactly right in an
unexpected direction: at rest the two characters only **abut**, so `Vstop` would have removed the overlap
from the scene entirely. That is why the fix was landed and proven against the failing configuration
**first** — had the order been reversed, there would be nothing left to prove it against.

Within this dispatch I proposed nothing further. Two things I considered and did not do, so they are not
silently absent:
- **I did not relocate `DR_VARBASE`/the peel buffers to make room.** It reaches eight bytes short of
  sufficient (§3D), it touches the intro's kernel define, and it is the wrong remedy.
- **I did not ablate the frame-level peel-skip's cadence cost separately.** It is inside a 0.07-frame band
  and would have cost a build to not measure.

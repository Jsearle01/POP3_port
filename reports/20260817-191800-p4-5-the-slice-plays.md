### 3 — Reasoning

**3A — ★★★ THE SLICE IS A REPLAY OF A MEASUREMENT, WHICH IS WHY IT EXISTS AT ALL.**

`MUSIC.SET*` has never been decoded (open since P4.1). **A vertical slice did not need it:** what
the port must reproduce is what the Apple's speaker *did*, and P4.4 recorded exactly that — one
(pulse, rest) pair per segment, off the bus. So `oracle_speaker_intervals.lua` now emits those
pairs, `pack_song.py` quantises them to GIME timer ticks at TINS=0 and run-length encodes:

```
3,924 segments -> 321 runs -> 1,286 bytes; 6,506.7 ms of music
pulse 7.83..22.51 us -> 3..8 delay iterations
over ceiling: 0 segments clamped
```

★ **Nothing was clamped**, so TINS=0 expressed the entire song — which is the practical form of
P4.4's floor finding.

**3B — ★★★ THE COST, MEASURED, AND IT IS OVER (AC5).**

The probe's foreground is nothing but `HAL_time_vbl_wait`, so status 1 (playing) and status 3
(torn down) are **the same loop on the same machine with and without the music** — the control is
internal and needs no separate baseline run:

```
#   playing   4070.8 spins/f ->   1364 cyc/f   (423 frames)
#   torn down 4252.9 spins/f ->     89 cyc/f   (152 frames)
#   THE PLAYER COSTS +1275 cyc/frame = 4.3% of the VBL budget
```

**Predicted: ~554 cyc/f (1.9%) for this song's 603 Hz mean; P4.2's envelope was ~55 cyc per
interrupt.** Measured is **2.3× that**, and HARD-STOP 2 applies: **report the number and the
levers, do not tune.**

★★ **The architecture is not what missed — my handler is.** P4.2's measured 55 cycles was a
handler that acknowledged the source and toggled a fixed value. This one also:

| what it adds | approx cycles |
|---|---|
| `pshs a,b,x` / `puls a,b,x` — the run-advance walks the table | ~12 |
| `probe_firqs` 16-bit increment — **a DEBUG counter** | ~15 |
| `dec sp_count` and its branch | ~5 |
| **the pulse delay, 3–8 iterations × 5 cycles** — this is the *fidelity*, §3C | ~15–40 |

**Levers, named and not pulled:** the debug counter is ~150 cyc/frame of the 1,275 and exists only
for the harness's liveness check; the `pshs` set could be narrowed on the common path (most
interrupts do not advance a run); the pulse delay is the sound and stays.

★★★ **AND IT STILL FITS WHERE IT HAS TO.** 4.3% is against the *whole* VBL budget, in beats that
are **holds** — torches only. P4.2's worry was the exit walk's 5.6% headroom, and **the exit walk
has no music**: `PlaySongI` drives `pburn`/`pstars`/`pflow` and not the character advance. Music
plays in the cheap frames.

**3C — ★★★ MY DEFECT, WHICH JAY'S EAR CAUGHT AND NO CHECK COULD HAVE.**

Jay: **"i need more volume."**

The first build emitted a **fixed ~4 µs pulse** — `sta DAC` then `clr DAC` on the next
instruction — and scaled the *DAC level* for amplitude instead. That is a **0.28% duty cycle**
against the oracle's measured **0.55–1.6%**: 2–6× under. Worse, the file's own header said the
slice *"reproduces the PULSE, because the mandate is that it SOUND right"* — **so it was a fidelity
bug wearing a volume complaint, and the header described something the code did not do.**

**Fixed properly**: the width is carried per run from the measurement (3–8 iterations of a 5-cycle
loop = 8–22 µs against the measured 7.8–22.5) and the **DAC sits at full scale** — which is the
Apple's own arrangement, one amplitude with duty doing the work.

★★ **Nothing in the headless check distinguishes a 4 µs pulse from a 22 µs one.** Both consume 321
runs and tear down cleanly. **This was only ever findable by ear**, which is the fourth defect in
this project that a suite could not see.

**3D — ★★ MY SECOND DEFECT: THE LAUNCH NEVER RAN.**

Jay: **"so it didn't laod the diskin mame, at least i didnt see it."**

The runner used `-autoboot_command` with a 3-second delay. **Every working runner in this project
drives DECB from a frame notifier after the boot settles**, with a 900-frame gap after `LOADM` —
because `LOADM` only returns to the prompt when the read finishes, and typing `EXEC` early lands
the characters in the line-input buffer. ★ **I departed from a proven pattern for no reason.**

★★★ **AND THE REAL LESSON IS THE ORDER, NOT THE FLAG:** I asked Jay to listen to something I had
never confirmed would start. `song_live.lua` now serves **one launch, two uses** — with `P_OUT` it
runs headless and checks the probe bytes; without it, it just drives the keyboard — so the live
gate cannot diverge from the thing that was verified. **This is the same correction as
`rebuild-before-asking-jay-to-look`, one step further out: verify it WORKS, not merely that it is
freshly built.**

★★ **I first told Jay "only 5.8% is above 874 Hz", which is true and misleading.** The error is
**quantisation against a 63.695 µs tick**, so it scales with pitch rather than switching on at
874 Hz: ±0.3% at 100 Hz but **±1.4–2% through 600–800 Hz, where three-quarters of this song
lives.** **What he is judging is ~a quarter-semitone across the body of the tune**, not a rare
top-end artifact. Corrected to him in the moment and recorded here.

**3F — §2H's THREE CHECKS.**

1. **A second mechanism for a different object class?** ★ Yes: the audio path is **three**
   registers and two are not the DAC — `$FF23` bit 3 is the sound enable and `$FF01`/`$FF03` bit 3
   are the mux. `HAL_sys_init` masks only bits 0–1 of each control register, so it leaves them as
   DECB set them; the probe sets all three explicitly rather than assuming.
2. **The calling routine.** The cost is `rate × handler`, and **the handler is mine** — §3B. P4.2
   measured a minimal one and I priced against it while writing a bigger one.
3. **Grep the reports.** P4.4's `+808 cyc/f at 936 Hz` is the envelope; this dispatch is the first
   to run a *real* handler against it, and the gap is the difference between an instrument and a
   player.

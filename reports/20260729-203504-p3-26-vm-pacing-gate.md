### 3 — Reasoning

#### 3A — The oracle's true rate, and why it had to be measured first

The dispatch's instinct was right, and measuring it first reframed everything after. P3.22's 18.9 Hz baseline
was taken with **static characters**, where P3.22's own win was *skipping the peel for characters that had not
moved*. The VM changes cels, a cel change changes the footprint, so it **must** peel. It therefore pays work the
baseline never paid, and comparing the two was comparing different workloads.

So the question is not "did we get slower than we were" but "does the oracle run this motion faster than we do".
Measured with `oracle_flame_rate.lua` — the flames advance once per `play` iteration, so the gap between flame
updates **is** the step interval — over two windows of the same run:

```
early  (f2700-4700): mean 2.6 frames between updates = 22.8 Hz
late   (f4700-6700): mean 3.9 frames between updates = 15.6 Hz
```

The late window is the stretch where the characters are actively animating. **The oracle drops from 2.6 to 3.9
frames per step**, a 50% slowdown, for the same reason ours does: drawing characters costs more than the pause
allows for.

**This is the bar, and we are inside it.** 16.8 Hz against the oracle's 15.6 Hz for equivalent motion. I am
deliberately *not* claiming we beat it — our demo has one character changing cels and one holding, while the
oracle's late window has both animating plus the hourglass, so its workload is heavier. The honest statement is
that **our rate is not a fidelity failure**, and the 18.9 Hz "baseline" should not be used as a bar again.

#### 3B — The decision this exposes: intent or observed behaviour?

The oracle's pacing primitive is a **minimum** delay: `play` does `lda SPEED` / `jsr pause` [`SUBS.S:876-881`],
and if the draw overruns, the step simply takes longer. So its 3.9 frames/step is not a designed cadence — it is
2.6 plus overrun.

That leaves two defensible targets:

| target | value | argument |
|---|---|---|
| the intent | 2.6 frames/step | `SPEED 7` says so; the source is authority on intent |
| the observed | 3.9 while animating | the trace is authority on fact, and it is what a player saw |

**Pacing to 2.6 makes the port run the animation faster than the original machine did.** That may be the right
call — it is what the designer asked for — but it is a fidelity choice, not an optimisation, and it is Jay's.
The current implementation targets 2.6 and achieves 2.74, which sits nearer the intent than the observed.

#### 3C — The counter fix

P3.25 attributed the +19% precisely: the cadence table counted **loop iterations**, and the loop ran 0.84
iterations per video frame, so `2.60 × 1.19 = 3.09`. The table was in the right unit; the counter was not.

`HAL_time_frame_count` [`time.s:169-176`] returns a 16-bit count and masks IRQ across the two-byte read to
prevent a torn value — the R-vbl race fix. The bundle links **without** the HAL, so the room reads it and passes
it in `U`, exactly as it already passes `HAL_gfx_cur_back` and `HAL_gfx_draw_base`. `vm_nextframe` now compares
`vm_now` against `vm_due` and sets `vm_due = now + cad_tab[idx]` when a step fires.

**Measured off the cel byte, not off a VM counter** — `port_vm_cadence.lua`'s existing property, kept
deliberately. A counter would report what the VM believes it did; the cel reports what reached the screen. That
distinction is what caught the original error, and reusing the same instrument is what makes before/after
comparable:

```
before  mean 12.36 frames between cel changes -> 3.09 frames per STEP  (+0.49)
after   mean 10.96 frames between cel changes -> 2.74 frames per STEP  (+0.14)
```

The compare is signed 16-bit, so it is correct until the counter passes `$7FFF` — about nine minutes at 60 Hz.
Recorded in the code rather than assumed away.

#### 3D — The 32 bytes, and my hypothesis marked as a hypothesis

`verify_room_chars` reports **32 bytes wrong, and the stability check agrees at 32 across separated captures** —
so systematic, not accumulating. That distinction matters: the two accumulating bugs this project has had
(P3.21's peel rotation, P3.25's peel dimensions) both presented as captures that *disagreed*. This does not, so
it is not that class.

The room suite is 8/8 and all three asset checks PASS; only the pixel-exact check is non-zero.

**Hypothesis, unverified:** the cel is read from the slot record **at capture time**, but the buffer being
captured was drawn a frame earlier and may still hold the previous cel. Faster stepping makes that skew more
likely, which fits its appearing exactly when the pacing changed. If that is right, **the instrument is wrong
again — a fourth variant of "the checker assumed part of the state it checks"** (assume the position, assume the
input provenance, assume the cel, and now assume the cel is *current*) — and the fix is to record the cel drawn
*into* the captured buffer rather than the one in the record now.

**I did not verify it, and per the standing invariant a prior classification is a hypothesis including mine.**
The cheapest test: log the cel at draw time into a per-slot shadow the capture reads, and see whether the 32
bytes vanish. If they do not, the draw is genuinely wrong and the hypothesis was a comfortable story.

- **The oracle comparison is workload-approximate.** Our demo animates one character; the oracle's late window
  animates two plus the hourglass. So 16.8 vs 15.6 is *reassuring, not a win*, and I have not built a matched

  smaller scale, but that is a guess and this project has been burned by exactly that shape of guess.
- **Signed 16-bit frame compare wraps after ~9 minutes** at 60 Hz. Fine for a cutscene; wrong for gameplay.
- **`aboutface` still unexercised**, and it invalidates baked parity when it fires (carried from P3.25).

#### 3B — The stagger's subject: there is no run-time shift to stagger

The dispatch is precise that the stagger removes **a re-shift**, and that stagger and cache are one mechanism.
Both are true of the *proposed* representation. Neither is true of the *shipped* one:

- **`blit_cel` never shifts.** Its header states the design decision outright: P3.18 measured that each cutscene
  cel is drawn at only 1-2 of the four sub-byte columns, so the shift is **baked into the data**
  ([blit_core.s:8-17](src/engine/blit_core.s#L8-L17)).
- **The walk is baked at two phases.** `content/cutscene/chars/vwalk48_p0.s` / `vwalk48_p2.s` and their
  siblings — 6 cels × 2 phases, generated offline by `bake_walk.py`. `co_variant`
  ([char_draw.s:530](src/engine/char_draw.s#L530)) *selects* a pre-shifted variant; it does not shift.
- **`shift_row` is linked into nothing.** No `import shift_row` in any `src/engine` or `src/hal` file, no
  mention in `link/pop.link`, `link/pop_engine.link` or `link/pop_flames.link`, and no reference in `build.bat`.
  Its only consumer is `shift_bench.s`, poked directly by Lua. P3.41 §4 states this itself — *"neither
  `shift_row.s` nor the benchmark is linked into a shipped target"* — as a reassurance about regressions. It is
  also the reason the stagger has nothing to do.

**This is not a scope question, it is an ordering one.** The cache holds shifted bytes; nothing produces shifted
bytes at run time. The stagger arranges for one character not to re-shift; neither character shifts. Building
either would compile and change nothing measurable — which, per the third candidate captured below, is the
failure mode that reads as a *wrong analysis* rather than as a half-built mechanism.

#### 3D — The forfeited peel-skip, measured: it forfeits nothing

This is the one element of §3/AC5 the current tree can answer, and P3.40 §3C explicitly left it open.

**Method** (`harness/tools/peel_skip_cost.lua`). MAME 0.281's Lua wrapper exposes **no cycle counter**
(`cpu:total_cycles()` and `cpu.clock` both nil) and `machine.time` is quantised to the scheduler timeslice, so
the established substitute is the VBL spin-wait itself: `hal_vbl_spin` is `cmpb <hal_frame_lo` (4) + `beq` taken
(3) = **7 cy/iteration** and it burns every cycle the engine is not working (idioms §0/§0a). One window =
`room_loop` → `room_loop`, tagged with `ch_anymove` read at the **close** of the window, which is the value
`ch_scan` computed for the `vm_frameadv` that ran inside it.

**Result, over frames 1900-3400, live-disk:**

```
# anymove=1    694 windows   2.161 frames/iter    1066.2 spins  -> work    57074 cy
# anymove=0  NO WINDOWS SAMPLED
# skip fired on 0 of 694 iterations (0.0%)
```

**An empty bucket is the exact shape of a broken instrument**, so it was falsified twice before being believed:

- **Raw-value histogram:** `$01:694` — never `$FF`, never varied garbage. A wrong address holding a non-zero
  constant would clamp to 1 and read as "the skip never fires", which is a *conclusion*.
- **An independent write-tap on the same byte:** `$00:695  $01:1390`. That is exactly `ch_scan`'s opening
  `clr ch_anymove` once per frame plus its two per-character `sta`s, both storing 1. **The address is live, the
  engine writes it every frame, and every frame closes at 1.** A read-tap and a write-tap cannot both be fooled
  by the same address error.

**The mechanism, which corroborates it:** `ch_moved` compares against `ch_last[(character, slot)]` — what *this
buffer* last drew. A buffer is redrawn every other iteration, **2 × 2.161 = 4.32 frames** apart, while the VM
steps every **3.15** frames (walk suite, below). Every buffer revisit therefore straddles at least one step. The
skip can only fire when the VM *holds*, and nothing in this scene ever holds — `pri_demo` applies `chx` on every
step, forever.

**So the answer to "what does the stagger forfeit here" is: nothing.** The saving being given up is already
zero. That is a stronger result than a cycle figure, and it retires P3.40 §3C's open item.

#### 3E — What the instrument caught on the way past: the baseline has never been executed

The same run measures the engine's real work, and it disagrees with the figure every verdict in this arc is
divided against.

| | |
|---|---|
| P3.19/P3.37 **model** of the frame — vizier, princess, two flames, hourglass, four stars | **19,652 cy** = 0.66 of a budget |
| **measured**, live scene, same ingredient list | **57,074 cy** = **1.91 budgets** |
| ratio | **2.90×** |

**Lead with the form that needs no constants.** The cycle figure depends on a clock, a frame rate and a
7-cy spin cost. This does not: **the loop takes 2.161 video frames per iteration** (histogram `2:582 3:112`),
counted off `frame_number` alone. *A frame costed at 0.66 of a budget cannot consume 2.16 budgets.* The
model is falsified without any of the arithmetic being trusted.

The idle side checks out too and confirms the engine is not merely waiting: idle = 1066.2 × 7 = **7,463 cy**
(0.25 frames), so 89% of each iteration is work. And `HAL_gfx_swap`'s only wait is `HAL_time_vbl_wait`
([gfx.s:546](src/hal/coco3-dsk/gfx.s#L546)) — the spin the tap counts — so no idle is being mis-booked as work.

**What this does and does not establish.** It establishes that the 19,652 denominator is badly wrong for the
live engine. It does **not** establish a new staggered-frame figure: 57,074 was measured on the *current* scene
(baked walk cels, two torches), not on `play 13`'s cels, and building a fresh verdict by adding 7,830 to a
measurement of a different frame would repeat precisely the error this arc keeps making. **I have deliberately
not published a replacement percentage.** The follow-up is to measure the real frame, not to re-model it.

Two prior reports flagged this baseline as inherited (P3.37 §7, P3.41 §7). **The flag was correct and changed
nothing** — the figure kept being used for six dispatches, which is itself the point.

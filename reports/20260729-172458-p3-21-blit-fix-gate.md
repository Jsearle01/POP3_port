### 3 — Reasoning

#### 3A — Why "12 stray bytes" was wrong, and what the method got wrong

P3.20 classified the room diff with hand-drawn boxes: bytes inside a character footprint were "expected",
bytes outside were "unexplained". That method can only answer *"is this byte where I predicted a change?"*
It cannot answer *"is this byte correct?"* — and **236 of the wrong bytes were inside the boxes**, invisible
to it.

The fix is to compare against a known-correct image rather than against a set of regions.
`verify_room_chars.py` composites the two baked cels onto the room asset using
`cel_blit_prep.simulate()` — the same byte-by-byte 6809 replay that validates the bake — and diffs the
capture against that. Every reported byte then has an expected value, so "wrong" is a fact rather than a
guess. Only the genuinely animated flames and the four window stars are excluded, and both exclusions are
named in the file.

| classification method | reported | actual |
|---|---|---|
| P3.20, expected-region boxes | 12 unexplained | — |
| P3.21, offline composite | **248 wrong** | 248 |

#### 3B — The two peel bugs (diagnose-before-patch, per §1 of the dispatch)

**The decisive narrowing was one build:** disable the peel, draw only → **0 bytes wrong**. So `blit_cel`'s
segment walker, its stack-blast and its masked merge were byte-exact the whole time, and the entire defect
lived in save/erase. That is what made both causes findable instead of guessable.

**Bug 1 — Y is clobbered, and the contract said so.** `blit_blast`'s header states *"A,B,D,Y clobbered; X
PRESERVED"* — `pulu d,y` loads Y with source data. Both peel routines held the **peel pointer in Y** across
the blast, so `leay a,y` afterwards advanced garbage and every row after the first read or wrote a wild
address. I wrote that contract in P3.20 and violated it in my own callers on the same screen.
**248 → 36.**

**Bug 2 — a false claim in P3.20, not a coding slip.** That version used `blit_blast` for both peel
directions on the stated argument that save and erase are exact inverses, so a group-reversed peel buffer
could never be observed. **The argument is false for any width that is not a multiple of 4.** `blit_blast`
reverses *group* order; with a tail the partition is asymmetric, so the permutation is not an involution. At
width 5 it is a rotation:

```
save   peel = [fb4, fb0, fb1, fb2, fb3]
erase  fb   = [fb3, fb4, fb0, fb1, fb2]      rotated again, not restored
```

so the background walked one byte per frame. **The accumulation is why two captures twelve frames apart
disagreed (36 vs 33) rather than failing identically — non-determinism was the tell**, and it is what
pointed at an accumulating state bug rather than a static data bug. Replaced with a plain forward copy.
**36 → 0** (the residual 2 and 1 were the twinkling stars, now excluded like the flames).

#### 3D — "Measure it": the mover I proposed is the wrong fix

Jay asked for the backward-reading stack-blast to be measured. Costed **per row**, which is the unit that
matters because a cutscene cel row is five bytes and amortises nothing:

| mover | cy/row | cy/byte | frame total | vs 29,673 |
|---|---|---|---|---|
| shipped forward copy | 127 | 25.4 | 33,169 | **OVER 1.12×** |
| tight forward (hoisted) | 65 | 13.0 | 21,885 | fits 74% |
| **backward stack-blast** | **73** | **14.6** | 23,341 | fits 79% |
| padded forward blast | 66 | 13.2 | 22,067 | fits 74% |

My estimate was wrong by 2.2× and lands **worse** than hoisting: the backward variant pays `leau`/`leas`
setup every row and `ldy ,--u` costs 9 cycles for the page-2 prefix, which swamps the better inner rate at
five bytes a row. **The per-byte figure was the wrong unit for a five-byte row.**

**And the model was optimistic anyway.** Hoisting was implemented and measured: still 6.00 frames between
flame updates (10.0 Hz), where the model predicted 92% of budget. So I stopped modelling and attributed the
cost by ablation:

| configuration | measured rate | fits one frame? |
|---|---|---|
| both characters, **draw only** | **20.0 Hz** | yes |
| **one** character + full peel | **20.0 Hz** | yes |
| both characters + full peel (shipped) | 10.0 Hz | **no** |

**The budget is crossed by the second character's peel.** No byte-mover fixes that. The structural fix is
to **not peel a character that has not moved** — a static character's background never changes, and the
masked merge is idempotent, `(((d&m)|s)&m)|s == (d&m)|s`, so redrawing in place is safe. Draw-only is
*measured* at 20.0 Hz, so that path is already proven to fit.

**Not implemented here.** It needs new per-slot position state, and this session produced three bugs from
writing new logic late (§7). Deferring it is the same judgement P3.20 made when it stopped rather than
pressing on.

#### 3E — Where P3.19's 66% came from

P3.19 predicted 19,579 cy (66%). Two of its assumptions do not survive contact:

1. It costed the peel at the stack-blast's 4.5 cy/byte. **The peel cannot use the stack-blast** (§3B bug 2),
   and a correct mover is 13–15 cy/byte. That alone is ~40% of the modelled frame resting on a mover that
   does not work for the job.
2. It costed per byte, not per row. At five bytes a row the per-row prologue dominates, which §3D shows is
   where the real cost sits.

The recon's *verdict* — that a runtime blit is viable on 128 KB — is not overturned: draw-only fits at
20.0 Hz with both characters. Its *margin* was overstated.

### 7 — Uncertainty flags

- **`blit_blast` now has ONE caller instead of three**, which materially weakens P3.20's "one blit core"
  claim. The peel cannot share it because the peel's source is live memory whose layout it does not control —
  the same reason P3.20 gave for not retrofitting the picture blitter. **That reason applies more widely than
  P3.20 thought**, and the one-core goal should be restated honestly rather than kept as an aspiration.
- **Three bugs in this session came from careless editing, not from the 6809:** `decb` as a pair counter when
  `ldd ,u++` clobbers B (the shipped code used memory for exactly that reason and I optimised the reason
  away); a slice-based edit anchored on `"blit_save\n"` that also matched `export  blit_save` and silently
  ate three routines; and a string replacement that silently no-opped because the real lines carry trailing
  comments. The assembler caught the first two; only an assertion caught the third, and it caught the same
  mistake twice more. **Every edit to assembly in this file should assert on its match count.**
- **The peel cost model is now known to be optimistic** (§3E). The ablation numbers are trustworthy; the
  cy/row table is a model and predicted a fit that did not materialise.
- **The masked-merge idempotence argument is algebraic, not measured.** `(((d&m)|s)&m)|s == (d&m)|s` holds
  because `s&m ⊆ s`, and the baked masks satisfy `s&m == 0`. Worth a replay check before the skip-when-static
  fix relies on it.
- **The move path is untested.** `ch_vizcol` is computed and never used — `char_one` reads a constant offset
  from the descriptor — so the character is static and the peel's move behaviour has never run. P3.20's
  "peel proven on move" was never true.

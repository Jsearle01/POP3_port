### 1 — Summary

**MY HYPOTHESIS WAS WRONG, AND TESTING IT IS WHAT FOUND THE REAL BUG.** P3.26 proposed that the 32 bytes were
instrument skew — the checker reading the cel at capture time while the captured buffer was drawn a frame
earlier. Implemented exactly as specified: a draw-time shadow (`ch_drawn`) recording what each buffer was
actually drawn with. **The shadow reported the same cels and the 32 bytes persisted.** It was the comfortable
story I flagged it might be.

**The real cause, localised by one ablation.** Freezing the VM gave **0 wrong** — so the static draw of both
cels was exact and the defect lived in the transition. `co_setup` computed the peel **slot stride** as
`slot × (h×w)` of the *current* cel: a save at `w=6` wrote slot 1 at `+258`, the following erase at `w=5` read
it at `+215`. **P3.25 sized the peel buffer to the widest cel; that was necessary and not sufficient — the
stride has to be constant too.** Fixed, and byte-exact with the VM actively stepping.

**The pacing policy is codified at the pacing site** — *"floor at `SPEED`, overrun naturally"* — with its
rationale, the ~1.4× cost, the `CLAUDE.md §2` intent-vs-fact citation, and Jay's revisit caveat, so a future
reader knows it is a judgement rather than a measurement.

**GATE — SPLIT, and recorded as Jay gave it.** *"the animation looks good so far"* — the engine's mechanism
confirmed by eye on `live-disk`. *"i cant tell pacing from that animation there needs to be more"* — **the
pacing is NOT gated**, because the demo changes state once every four steps and carries no cadence information.

**Trying to fix that found another bug.** Densifying the sequence to change cel *and* position **every step**
— which is what makes cadence visible — took the pixel check from 0 to **144 wrong with the captures
disagreeing**, the accumulating signature. Reverted rather than shipped; **HARD-STOP #3** invoked (§3E).

### 3 — Reasoning

#### 3A — The hypothesis, tested rather than adopted, and false

The dispatch was right to insist on testing it. `ch_drawn` records the cel at **draw** time, indexed by
(character, slot); the checker reads the entry for the buffer it is capturing (`1 − cur_back`). If the skew
theory held, the shadow would have disagreed with the record and the bytes would have vanished.

**It reported the same cels — 54/11 and 54/1 — and the 32 bytes persisted.** So the instrument was not lying
and cel identity was never the issue.

**The shadow is kept anyway.** Reading what was *drawn* is the correct input for a checker regardless of
whether it fixed this particular bug, and it is what made the ablation that followed trustworthy — the diff
could no longer be blamed on the checker.

#### 3B — The real cause, and what P3.25 got half-right

One ablation localised it, per the dispatch's instruction to narrow before guessing: set the cadence to 200
frames so the VM cannot step between captures. **0 bytes wrong, position static.** So both cels draw exactly;
the defect is in the transition.

`co_setup` derived the peel slot offset from the current cel's footprint:

```
save with w=6  ->  slot 1 peel base = base + 43*6 = +258
erase with w=5 ->  slot 1 peel base = base + 43*5 = +215
```

The erase therefore restored bytes that were never saved. **P3.25 sized the peel BUFFER to each character's
widest cel and stopped there** — correct as far as it went, and it left the *stride* varying with whatever cel
happened to be loaded. The two halves of a peel disagree the moment a differently-sized cel arrives, which is
precisely what an interpreter guarantees. `CH_STRIDE` is now a record field holding the character's widest
footprint and does not move when the cel does.

**Result:** 0 bytes wrong at both captures **with the VM stepping** (cel 11 → 1, col 35 → 33), stability
agreed, room suite PASS at 512 KB and 128 KB, intro PASS, cadence 2.74 frames/step measured off the cel byte.

#### 3C — The pacing policy, codified

Jay's decision, written at the pacing site rather than left in a dispatch: **the cadence table is a MINIMUM.**
A step waits at least its frames; if the draw overruns, the step takes longer; nothing clamps the rate.

This ports the **mechanism**. The oracle's `play` does `lda SPEED / jsr pause` [`SUBS.S:876-881`] — a minimum
delay — so its measured 3.9 frames/step while animating is that floor plus its own draw overrun, not a pace it
aimed at. **Matching 3.9 would mean inserting delay to reproduce the Apple's inability to keep up: porting a
limitation as a design.** It also would not generalise, since gameplay load varies by room and actor count.

`CLAUDE.md §2` — *"trace wins on fact; source wins on intent"* — and this takes **intent** for the floor
(`SPEED 7` = 2.6 frames), letting the achieved rate be a consequence of our draw cost exactly as 3.9 was a
consequence of the oracle's. **Acknowledged cost: ~1.4× the oracle's animated rate.** Jay's caveat that it is
revisitable by eye is recorded in the code, so the next reader knows it is a judgement.

#### 3D — The gate, split, and why the split is the honest record

**Animation: PASSED.** *"the animation looks good so far"*, on `live-disk` at 100.00% speed. Both characters
driven entirely from data — the vizier holding `Vstand`, the princess stepping through her sequence — with the
interpreter resolving cels, applying `chx` and looping via `goto`.

**Pacing: NOT GATED.** *"i cant tell pacing from that animation there needs to be more."* This is correct and
it is a limitation of my demo, not of his attention: the sequence holds a cel for four steps and moves every
fourth, so a visible change occurs roughly every 11 frames. **No cadence can be read off that.** Recording
this as an unmet gate rather than folding it into the pass is the point — the policy in §3C is explicitly
revisitable by eye, and that caveat cannot be exercised until the pacing is visible.

#### 3E — Making it judgeable exposed another bug

To make cadence readable I densified the sequence: cel **and** position change on **every** step, so the
visible change rate *is* the step rate. Also a harder test — the transition path runs every step instead of
every fourth, and a 4 px move overlaps a 5-6 byte-wide cel almost entirely.

**It went from 0 wrong to 144, with the captures disagreeing (0 and 144).** That is the accumulating signature,
the same class as P3.21's peel rotation and P3.25's peel dimensions — and distinct from the systematic 32.

**The finding matters more than the demo:** every byte-exact result this engine has produced, **including the
one behind Jay's "looks good"**, used a sequence that changes state once every four steps. The per-step
transition path has a defect that no test so far has exercised. **HARD-STOP #3** applies, so I reverted rather
than shipped and did not diagnose it at the end of a long session — the last three times I pushed on late I
introduced defects.

### 1 — Summary

**Diagnosis: the CONVERTER. Both render paths are correct and neither was touched.** Rendered the same
cel through both and measured, rather than assuming: `render.py` maps cel row 0 → image row 0 (proved with
a synthetic marker cel — the marker lands at the TOP), and `cel_probe` maps converted row 0 → framebuffer
scanline 0 (a passing `framebuffer_matches_converter` *is* that identity proof, re-demonstrated with the
same marker). **Both are identity; they agree with each other; the data itself was upside down.** That is
the dispatch's "BOTH flipped → converter bug" branch.

**Root cause — and it inverts a premise in the dispatch.** POP cel data is stored **BOTTOM-ROW-FIRST**.
Three *code* sites in `HIRES.S` establish it: PREPREP leaves `IMAGE` at data row 0; CROP computes
`TOPEDGE = YCO - HEIGHT` where `YCO` is the *lowest* visible line; and the draw loop advances `IMAGE`
**forward** while `DEC YCO` walks the destination **up**. So data row 0 is drawn at the BOTTOM scanline.
The dispatch states "the Apple cel format stores rows top-to-bottom (`HIRES.S:187`)" — **that is a comment,
and it is wrong as a statement of visual orientation**; taken at face value it would make the *original
game* render upside down. `CLAUDE.md §2` ranks comments lowest and mechanism above them, so the code wins.
Karateka's cels are top-first, which is exactly why a converter ported from it flips POP art.

**Fix:** reverse the row order at ingest in `sprite_convert.convert_one`. **Proven to be a pure
reordering** — `new == reversed(old)` and the row multiset is identical, so no pixel data changed. The
colour model is still byte-identical to Karateka's (guard re-run, exit 0). Neither render path was edited.

**The blind spot mattered more than the flip, and it is now closed.** P1.2's spot-check passed
**1152/1152 pixels on cels that were upside down** — it could not have failed, because both sides of that
comparison are downstream of the converter, so a uniform flip round-trips perfectly. I reported it as the
dispatch's strongest evidence. It wasn't evidence of orientation at all. `harness/tools/verify_orientation.py`
now anchors to the **original POP cel binary** plus the blitter's row-order semantics — inputs the converter
cannot influence — and is wired into the spot-check ahead of the MAME run. **Demonstrated failing on the
real pre-fix data recovered from git** (exit 1), passing on the fix (exit 0).

**25.3 — PNGs surfaced for Jay, uninterpreted:** `build/orientation-review/` holds BEFORE/AFTER pairs for
three cels. Per `CLAUDE.md §3` I generated and surfaced them without looking at their content. **Orientation
is a visual property and the confirmation is Jay's** — which is the whole lesson here: Jay's eye caught what
the byte-check structurally could not.

### 3 — Reasoning

#### 3.1 — Two-path diagnosis (AC1)

| Path | Row mapping | Evidence | Verdict |
|---|---|---|---|
| GUI `render.py` | `pixels[cy]` → buffer row `by+cy` | synthetic marker cel: bar on data row 0 → **top band lit** (255,255,255), bottom band gray | **IDENTITY** |
| `cel_probe` (real GIME) | converted row *r* → `FB_A + r*80` | marker cel: `framebuffer_matches_converter PASS, all 16 bytes identical` — the check compares scanline *r* to row *r*, so passing *is* identity | **IDENTITY** |

Neither inverts. Both agree. Therefore the flip is upstream of both — in the data.

#### 3.2 — Why the data was flipped (the source mechanism)

Three code sites, quoted in §5:
1. **PREPREP** — `ADC #2` past the `[width][height]` header ⇒ `IMAGE` points at **data row 0** at draw start.
2. **CROP** — `TOPEDGE = YCO - HEIGHT`, and `YCO` is *"Y-coord of lowest visible line of image"* ⇒ `YCO`
   is the BOTTOM scanline.
3. **Draw loop** — `* Next line up`: `IMAGE += WIDTH` (source forward) while `DEC YCO ... CPY TOPEDGE`
   (destination up).

⇒ data row 0 → bottom; data row h−1 → top. **POP cels are bottom-first.**

**On the contradicting comment.** `HIRES.S:187` says *"image bytes read left-right, top-bottom"*. If that
described visual orientation, then with a blitter that draws row 0 at the bottom, the original game would
render upside down — it does not. The comment describes sequential storage. This is precisely the tier
ordering in `CLAUDE.md §2` (comments lowest, mechanism above), and the dispatch's premise rests on that
comment, so I am flagging it rather than absorbing it.

**What I deliberately did NOT rest the fix on.** I ran a per-row shape profile of the largest kid cel and
started reading it as a figure. That is *my* visual interpretation of ASCII art — the weakest evidence
available and exactly the kind this project distrusts. I discarded it. I also ran a cross-frame stability
test (which end of the data is steadier across an animation run); it is consistent with bottom-first — the
data-row-0 end swings (stdev 3.17) while the far end is near-constant (stdev 0.76), matching feet-in-stride
vs a level head — but it depends on my assumption about which body part moves in a run cycle, so it is
corroboration, not proof. **The fix rests on the three code sites; the confirmation is Jay's eye.**

#### 3.3 — The fix, and why it is provably safe

Reversal at ingest in `convert_one`, before the colour model runs. The colour model is strictly per-row
(`_classify_row_convert` takes one row), so reversing input rows is equivalent to reversing output rows and
cannot alter any pixel's classification. Verified rather than argued:
- `new == reversed(old)` → **True**; `sorted(new) == sorted(old)` → **True** (identical row multiset).
- `verify_color_model.py` → both functions still **IDENTICAL** to Karateka's, exit 0.
- compile round-trip byte classes unchanged: footprint 2,506 / drawn 1,075 / mixed 644 before and after.

#### 3.4 — The guard, and why it is not circular (AC4)

`verify_orientation.py` re-derives the conversion **from the original `IMG.CHTAB*` binary**, calling the
colour model as a black box but **not** `convert_one`'s row loop, then asserts
`converted.s row r == straight_conversion row (h-1-r)`. Its inputs are the source asset and the blitter's
semantics — neither of which the converter can influence. It distinguishes three outcomes explicitly:
correctly flipped (PASS), matching the unflipped order (FAIL, "UPSIDE DOWN"), and matching neither (FAIL
with the first bad row). It also reports **vertically symmetric** cels as `PASS*`, where a flip is
genuinely undetectable — stated rather than hidden.

It is wired into `run_cel_test.sh` *before* the MAME run, so the spot-check as a whole now covers both
self-consistency and orientation-vs-source. Cels with no `ORIGIN` header (synthetic fixtures) are SKIPped,
not failed.

**What the guard does not do:** prove the ground truth itself. If the three code sites were misread, the
guard would faithfully enforce the wrong orientation. That residual is Jay's gate, and it is why the PNGs
are surfaced.

### 6 — Reactive deviations

1. **The dispatch's stated premise is inverted, and I am reporting rather than absorbing it.** It says "the
   Apple cel format stores rows **top-to-bottom** (`HIRES.S:187`)". That is a source *comment*; three code
   sites say the opposite, and the comment cannot be right or the original game would render upside down.
   The fix direction depends entirely on this, so it needed stating plainly rather than quietly inverting.
2. **Two diagnostic lines of evidence were run and then deliberately not used as proof** (§3.2): a per-row
   shape profile (my own visual read of ASCII art — discarded) and a cross-frame stability test
   (corroborating, but resting on my assumption about run-cycle motion). Reported for completeness; the fix
   rests on the code sites.
3. **The guard reports `PASS*` for vertically symmetric cels**, where a flip is genuinely undetectable.
   None of the 9 hit it, but the case is surfaced rather than silently counted as a pass.
4. **The guard lives in `harness/tools/` and is *invoked by* the spot-check**, rather than being written
   into `cel_test.lua`. The property is converter-output-vs-source (build-time), not a MAME property; putting
   it in Lua would have needed the cel binaries inside the emulator run for no benefit.
5. **Dispatch label:** third dispatch in the P1.2 family (`p1-2-cleanup`, `p1-2-sprite-tooling-port`, this).
   Filenames differ; noted for the same reason as the earlier collisions.

### 7 — Uncertainty flags

1. **The ground truth rests on three code sites, not on a trace or on the oracle's pixels.** I did not run
   POP on `apple2e` and correlate its HGR framebuffer against a cel. If all three sites were misread, the
   guard would faithfully enforce the wrong orientation. **Jay's eye on the surfaced PNGs is the confirming
   authority**, and an oracle A/B is the follow-up that would make it independent (§8.1).
2. **Only the 9-cel sample exists, and all 9 were re-converted — so no full-library re-convert is owed
   today.** But every future conversion depends on the fix being right; if Jay's gate rejects it, the
   reversal is a one-line inversion and the guard flips with it.
3. **Horizontal orientation was not examined.** This dispatch addressed the vertical flip only. The
   converter's `--mirror` path and left/right handedness are unverified against the source; the same
   self-consistency blind spot would hide a horizontal flip exactly as well.
4. **The cross-frame stability corroboration assumes** feet move more than the head across a run cycle.
   Reasonable, but it is an assumption about art, not a measurement.
5. **`PASS*` symmetric cels are a real hole** in the guard for any cel whose rows happen to be a palindrome.
   Rare, flagged, not solved.

### 3 — Reasoning

**Authority tier: direct tool output throughout.** Every claim below rests on a hash, an exit code, a diff, or a tool's own stdout. Nothing rests on a comment or a remembered value, and no behavioral claim is made — nothing was run under emulation.

**Why the vendored tree is provably `ec78dbf`.** AC1 asks for three spot hashes; those pass, with `git hash-object` and `sha1sum` agreeing on all three. But spot-checking three of 618 files is weak evidence for "the buildable whole", so I ran the stronger check available: a full recursive byte-diff of the vendored tree against the probe clone, excluding only `.git` and the two deliberately-omitted toolchain dirs. It returned **exit 0** — every vendored file is byte-identical. That upgrades the provenance claim from "three files match" to "the tree matches."

**Why `.gitattributes` was vendored despite not being enumerated.** §3 lists the tree by name and omits both top-level dotfiles. Reading them before deciding showed they are not equivalent in importance. Upstream's `.gitattributes` sets `* binary` as the default with explicit `crlf diff` overrides for `*.S`, `Makefile`, `LICENSE`, `README.mkd`, `Other/*.PATCH` and `Other/*.layout`. That default is what keeps the seven `Build/win32` binaries byte-exact under this host's `core.autocrlf=true`, and the overrides are why the `.S` sources are CRLF on disk (`MASTER.S`: 1447 of 1447 lines CRLF). Omitting it would not have been neutral — it would have handed POP's own `core.autocrlf` authority over the normalization of a tree whose build output is being hashed against a reference. Since that is precisely the reproducibility the vendoring exists to establish, I treated the omission as an oversight in the enumeration rather than a boundary, vendored it, and flagged it (§6.3). Upstream's `.gitignore` is a much weaker case — pure defence-in-depth against committing the three image outputs and `obj/` — and was vendored alongside it.

That reading also paid off immediately: it told me **before the build ran** that the Phase 0 reference sums came from a Linux/LF checkout while this build would consume CRLF sources, which is what made the eventual partial match readable rather than mysterious.

**What the md5 result actually establishes, and the hypothesis it falsified.** The `.hdv` matched `c4f0b13e…` exactly. Since the CRLF-vs-LF difference in the source did **not** perturb it, the assembler's output is insensitive to line endings here, and the 6502 object code is byte-identical to the Linux build. All three disk images are produced by `crackle` from that same `obj/` directory. Therefore the `.nib` divergence cannot originate in the source, the assembler, or the object code — it is confined to `crackle`'s output stage.

My first hypothesis was that the RW18 disk-protection path was the platform-sensitive part. **The layout scripts falsified it before it reached this report:** `Other/PrinceOfPersia_3.5.layout` contains **64 RW18 records** plus 4 BLOCK, so the matching `.hdv` exercises RW18 heavily. RW18 is therefore not the discriminator. What distinguishes the two 5.25" layouts is 16 **RWTS16** records and, more importantly, the `--format nib_5.25` output mode — GCR nibblization with sync and gap bytes — versus `hdv_3.5`'s plain block placement. The divergence is in the nibble encoder, not the protection scheme.

**Why the mismatch is a platform difference and not a broken build.** "Differs from the reference" has two very different meanings. A clean `make clean && make all` on this host reproduced all three artifacts **bit-identically** to the first run, so the build is deterministic here; the `.nib` difference is a stable Windows-vs-Linux `crackle` divergence. Per §5.5 and §6 I did not attempt to fix it.

**Why the toolchain had to be force-added.** Detailed in §6.2. The short form: `core.ignorecase=true` makes `build/` match `Build/`, so the §5.3 rule swallowed a §3 deliverable. I kept `.gitignore` byte-exact because AC4 pins it and §5.3's stated design principle forbids carving exceptions inside rules, and instead force-added the seven toolchain files by explicit path. Ignore rules do not apply to already-tracked files, so the repair is durable — but the trap is latent, which is why it is in the commit message, this report, and a pool row rather than only in the fix.

**6.1 — Both `.nib` images mismatch their reference sums while the `.hdv` matches. (Most important finding.)**

What the pattern establishes, since all three are produced by `crackle` from the same `obj/`:
1. **The 6502 object code is byte-identical across platforms** — otherwise the `.hdv` could not match. This also proves the CRLF-vs-LF source difference (§3) does not perturb `snap`'s output.
2. **The divergence is confined to `crackle`'s 5.25" output stage.** Not the source, not the assembler, not the object code.

The 5.25" layouts differ by carrying 16 **RWTS16** records and by using `--format nib_5.25` — GCR nibblization with sync/gap bytes — rather than `hdv_3.5` block placement. The nibble encoder is the suspect.

Per §5.5 and §6 I did **not** attempt to fix it. Consequence for the project: the artifact POP is actually graded against — the 3.5" `.hdv` oracle — reproduces exactly, so this does not block anything in the current plan. It would matter if a 5.25" image ever became a reference.

## A. COCO3 — **GIME register write ORDER matters; palette must be written AFTER video mode**

A real CoCo3 hardware/emulator behaviour, not a code-style preference: **palette register
writes (`$FFB0-$FFB3`) do not latch correctly until the GIME's video mode is already set.**
Writing palette **before** `$FF98`/`$FF99` (video mode + resolution) results in the
mid-range palette indices **not rendering** — only the extreme values ($00 black / $3F
white) survive; indices 1 and 2 (orange, blue/cyan) come out wrong or absent.

- **The constraint:** `$FF90` (CoCo3 mode) **first** (required — the `$8000+` framebuffer
  needs CoCo3 mode for CPU access), then clear buffers, then all GIME mode/offset/SAM setup
  (`$FF98`/`$FF99`, `$FF9D`/`$FF9E`, `$FF9C`, `$FF9F`, `$FFD9`, `$FFDF`), **then palette
  `$FFB0-$FFB3` LAST.**
- **Symptom of getting it wrong:** four-band palette test shows only 2 distinct bands
  (black + white); Brøderbund logos render without orange/blue.
- **This is empirical, not Sockmaster-documented** — the source is GFXMODE3.ASM (Jay's
  working reference) and Jay's own recollection: *"the GIME needs to be completely
  initialized before palette values are written."*
- **Cost of not knowing it:** the P2.3a display-init arc burned multiple followups
  (followup-2 was NOT CONFIRMED chasing palette *values* when the real cause was *ordering*)
  before the reorder fixed it.

**Candidate name:** `gime-palette-writes-must-follow-video-mode-set`.

*Established:* P2.3a.6 display-init followup arc (followup-3, the reorder).

## B. APPLE2E — **`-debug` launches PAUSED; set `wpset` BEFORE releasing boot**

To catch **boot-time** writes (a byte written once during disk load, before any runtime
code runs), the watchpoint must be armed **before the machine starts booting**.

- **Method:** `mame apple2e -debug -window -flop1 <disk>` launches **paused at the first
  instruction** (debugger window open, machine halted). Set watchpoints **there**, then
  `go`.
  ```
  wpset bffd,1,w        # addr, length(bytes), access(w=write)
  wpset bffe,1,w
  wpset bfff,1,w
  wplist                # verify armed
  go                    # release; breaks when a watchpoint fires
  ```
- **`wpset` syntax varies slightly across MAME versions** — if it errors, `help wpset`.
  (The `addr,length,access` form is stable across many versions but not guaranteed.)
- This is the **interactive-debugger** route (distinct from a scripted Lua tap), and it is
  the one that works where scripted taps false-0 on this target (see the opcode-fetch
  bypass in the main apple2e file).

**Candidate name:** `mame-debug-launches-paused-arm-watchpoints-before-go`.

*Established:* the `$BFFD-$BFFF` sync-byte watchpoint experiment (Q010).

## C. APPLE2E — **boot-time-static bytes: written once from disk load, never by runtime code**

A data-provenance quirk that changes *how* you instrument: some bytes are **set once from
the disk image at load time and never refreshed by runtime code**. A grep of `src/` for an
instruction that writes them finds **nothing** — because no runtime instruction does; the
value came in with the disk load.

- **Symptom:** "no instruction in `src/` writes `$XXXX`" is **not** proof the value is
  dynamic or protected — it can be **static from disk load**.
- **How to tell:** a **write-watchpoint armed before boot** (idiom B) fires **at boot**
  (during load), not during the attract/runtime loop. If it only fires at boot, the byte is
  static-from-disk.
- **Why it matters:** avoids chasing a "who writes this" runtime hunt for a value nothing
  writes at runtime (the `$BFFD-$BFFF` EOR-sync bytes were static-from-load: `$00/$3B/$49`,
  set at boot, never refreshed — which resolved whether they were copy-protection).

**Candidate name:** `boot-time-static-bytes-arent-written-by-runtime-code`.

*Established:* the `$BFFD-$BFFF` sync-byte investigation (Q010).

"TRUE" / "reference" / "ground truth" were tool renders, not MAME captures**, and were used
as ground truth across **multiple iterations** — meaning the "verification" was
**tool-output vs tool-output**, never tool-vs-MAME.

- **The tell is the pixel colour.** MAME's actual rendered palette colours differ from the
  conversion tool's colour constants:
  - **MAME blue ≈ `(25,144,255)`** vs the **tool constant `(0,0,255)`**.
  - A ground-truth file that contains `(0,0,255)` is a **tool render**, not a MAME capture.
- **Filename labels establish nothing.** "diagnostic TRUE", "reference image", "ground
  truth capture" are just strings. **Content + creation method + timestamp** establish
  provenance:
  - **Pixel-colour spot-check** (does it contain MAME's palette, e.g. `(25,144,255)`, or the
    tool's `(0,0,255)`?) — the fastest tell.
  - **Timestamp** (does the file's creation time match the claimed capture session? The
    contaminated files were created at 17:43, *after* the real snaps at 14:01).
  - **Creation method** (produced by the claimed MAME capture, or by
    `sprite_render_apple2.py`?).
- **The authoritative captures:** `C:\karateka-capture\snap\apple2e\` — snaps 0082-0085,
  560×192 px, **snap 0083 = record of record**. Derive rules against **those**, spot-checked
  by pixel colour before use.
- **Companion trap — automated-check tautology.** "109/109 pixels match the rule" is
  **tautological** if the rule generated the predictions being matched. Validate against
  **independently-grounded** raw pixel coordinates from the MAME snap, not against
  rule-derived expectations. (This is *why* Jay's eye repeatedly caught an off-by-one that
  Clyde's "109/109 pass" missed — the checks were self-consistent, not ground-truthed.)

**Candidate names:** `tool-render-is-not-a-mame-capture-verify-by-pixel-colour`,
`automated-check-tautology-validate-against-ground-truth-not-rule-predictions`.

**The mode values were confirmed, not guessed, and two sources agree independently.** GIME-RM §10's
Video Mode Reference table gives the answer directly — `320 × lines | 16 | 4 | 160 | 111 | 10 | $1E` —
and SockmasterGime.md's `$FF99` bit layout (LPF | HRES | CRES) reconstructs the same byte from first
principles: `%0 00 111 10` = `$1E`. Agreement between a lookup table and a bit-level derivation is
worth more than either alone, because the failure modes differ.

**The ordering deliberately diverges from GIME-RM §14, and that is a ruling, not an oversight.** The
manual's example loads the palette at step 4, before the mode registers, and writes `$FF90` late. This
codebase does neither: `$FF90` goes **first** (our framebuffer is at `$8000+`, ROM territory until the
CoCo3 map exists, so nothing can be cleared before it) and the palette goes **last** (empirically,
palette writes do not latch until `$FF98`/`$FF99` hold their final values — indices render black
otherwise). Per CLAUDE.md §2 the trace outranks the document on matters of fact. Recorded in the source
so the divergence reads as a decision.

**Geometry is published rather than assumed, and the probe consumes it.** `HAL_gfx_cur_stride` exists
because a wrong stride does not fail loudly — it skews the picture into a diagonal. The probe reads the
stride from the HAL instead of hardcoding 80 or 160, so a service that programs the registers correctly
but forgets its own bookkeeping fails the test rather than failing quietly later. The pattern check
verifies **row 1 as well as row 0**, which is the part that actually tests stride: a wrong stride still
paints row 0 correctly.

**Two things went wrong and both were caught by measuring rather than by reasoning.**

1. **The first cut grew Karateka's binary by 153 bytes.** Adding the service unconditionally to shared
   source is not "Karateka unaffected" (AC6), so it is now gated behind `ifdef HAL_GFX_MODE_SERVICE` —
   one shared source, compiled where a project asks for it, the same rule-3 mechanism as the dormancy
   guard. Byte-identity restored and re-verified. Adopting it in Karateka later is a one-flag change.
2. **The probe hung after stage 1.** It polled `$FF92` for VBL without arming the VBORD source first,
   so the latch never set and the wait spun forever. Stage 1 passed and stages 2–4 never appeared — a
   failure shape that reads like a broken mode switch but was a missing enable.

**A design error the build caught, worth keeping:** the mode ids were first defined in `gfx.s`, so a
caller including only `hal.inc` could not name a mode. Four "Undefined symbol" errors. The reflex fix is
to duplicate them into the contract; the right one was to notice the errors were correct about ownership
— a value a caller must name to invoke a service **is** contract. Moved to `hal.inc` alone, and `gfx.s`
turned out never to need them by name (its descriptor table is positional), so the duplication that felt
inevitable was not.

### 3 — Reasoning

#### 3.1 — §0.2 documentation-first: the mode values (AC1)

**GIME-RM §10 — Video Mode Reference** (verbatim from the PDF text layer):
```
Resolution      Colors  bpp  Bytes/row  HRES  CRES  $FF99(192L)
320 × lines     16      4    160        111   10    $1E
320 × lines      4      2     80        101   01    $15
```
**SockmasterGime.md:108-136 — `$FF99` bit layout** (verbatim):
```
Bits 6-5  LPF   00=192 scan lines on screen
Bits 4-2  HRES  111=160 bytes per row / 101=80 bytes per row
Bits 1-0  CRES  10=16 colors (2 pixels per byte) / 01=4 colors (4 pixels per byte)
```
Reconstructing: `%0` `00` `111` `10` = **`$1E`**. The table and the bit layout agree.
**Palette:** `FFB0-FFBF ... Color 0 ... Color 15`, bits 5-0 = `R1 G1 B1 R0 G0 B0`
(SockmasterGime.md:218-240; GIME-RM §2 "Palette registers (16 × 6-bit RGB)"). 16 registers confirmed.
Hard-stop 10.2 did not trigger — nothing needed guessing.

#### 3.2 — The service (AC2)

Table-driven so adding a mode is a row plus a palette, not a code change. Descriptor: `$FF99` value,
stride, framebuffer size **in words** (the clear loop's unit), palette pointer, palette count.

Sequence, using the codebase's proven ordering (§1): `$FF90` → **clear** → `$FF98`/`$FF99` → VOFFSET →
VSCROL/HOFFSET → SAM → **palette last**.

The clear reads its length from the same published geometry the caller reads, so "how big is the screen"
has one source and cannot disagree with itself. **Clear-on-switch is the contract**: at 2 px/byte vs
4 px/byte, surviving pixels are not old content, they are the same bytes re-read at a different width.

**Single-buffered by construction.** Framebuffer is FB_A (`$8000`), VOFFSET points at it. 16-colour
double-buffering needs 2 × 30,720 = **60 KB of the 64 KB CPU window** — recorded in the source and in
`hal.inc` because it is a real constraint for later animation, and explicitly not solved here (§6 scope).

#### 3.3 — The cycle, and why the repetition is the test (AC3)

Stages 1 and 2 prove a switch happens. Stages **3 and 4** are the test: switching back is where a mode
service fails — stale stride, stale palette count, a framebuffer cleared to the previous mode's size.
All four stages produced identical results to their same-mode partner.

Content is one vertical bar per palette index, sized so each mode fills a row **exactly**
(16 × 10 = 160; 4 × 20 = 80). A wrong stride therefore shows as a skew rather than as a subtly wrong
image, and counting bars by eye is the check: 16 distinct hues means the mode really is 16-colour.

#### 3.4 — Automated corroboration, and its limit (AC5)

14 checks: per-stage `$FF99`, per-stage stride, and the exact bar pattern across rows 0–1, ×4 stages,
plus stage count and completion.

**What it cannot do:** GIME palette registers are write-only and a palette byte's appearance depends on
the monitor mode, so nothing here checks colour. Stated in the Lua itself so a future reader does not
mistake a green run for a visual pass. This is the recurring lesson from P1.2 (orientation) and P1.3
(palette): both passed byte-diffs while being visibly wrong.

**Renders use decoded framebuffers, not MAME snapshots** (idiom §11b): `screen:snapshot()` is not
square-pixel and under `-nothrottle` manufactures artifacts. Each stage's framebuffer is dumped and
decoded offline at native 320×192.

#### 3.5 — One kernel, Karateka unaffected (AC6)

`ifdef HAL_GFX_MODE_SERVICE`, defined only in POP's `build.bat`. Sync bridge passes pre-build in both
directions. Karateka: `88eba89b…`, 17,978 bytes — identical to the P2.4 baseline — and 6/6 informative
tests PASS.

### 6 — Reactive deviations

1. **The service is gated behind `ifdef HAL_GFX_MODE_SERVICE`, not unconditional.** Adding it to shared
   source grew Karateka's prod binary by 153 bytes, which fails "Karateka guard-off build unaffected".
   Gating restores byte-identity, keeps one shared source, and makes Karateka adoption a one-flag change.
2. **Mode ids moved from `gfx.s` to `hal.inc`** after the build rejected the probe (§1). A design
   correction, not a workaround — and it removed a duplication rather than creating one.
3. **The probe arms VBORD in `$FF92` inside `checkpoint`, per stage**, not once at startup. Omitting it
   entirely hung the probe after stage 1; arming per checkpoint is immune to the fact that
   `HAL_gfx_set_mode` rewrites `$FF90` (IEN) on every call.
4. **`dist/mame-cfg/rgb/coco3.cfg` restored again** — MAME rewrites it on exit and strips its comment
   block. Third dispatch running. It is a template, not a constant.
5. **New harness files** (`mode_test.lua`, `run_mode_test.sh`, `render_fb.py`) were not named in the
   dispatch but are what AC3/AC5 require; `render_fb.py` exists because idiom §11b forbids trusting a
   MAME snapshot for visual work.
6. **The 4-colour default palette reuses POP's Jay-confirmed set** (`$00/$26/$19/$3F`, P1.3-fix) so the
   4-colour stages are checkable against something already accepted. The 16-colour palette is new.

### 7 — Uncertainty flags

1. **Nothing here validates colour, and the renders are a decode rather than a photograph.** They show
   what the framebuffer bytes plus the palette mean, in RGB. If MAME's live output disagrees, the live
   run wins (idiom §11) — that is precisely why 25.3 is Jay's.
2. **`gfx.s`'s existing `HAL_gfx_init` comment says the descriptor-0 palette is COMPOSITE format**,
   while POP's gate is RGB and P1.3-fix set RGB values. The new service's palettes are RGB by
   construction. The older comment and POP's gate are in tension; the inherited `HAL_gfx_init` path was
   not touched here, so that tension is untouched too. Worth resolving before art palettes land.
3. **The 16-colour palette is a diagnostic, chosen for maximum separation**, not derived from POP's art.
   "16 distinct hues" is its only design goal.
4. **`HAL_gfx_set_mode` sets VOFFSET to FB_A unconditionally**, so calling it discards whatever
   double-buffer state `HAL_gfx_init`/`HAL_gfx_present` established. Consistent with clear-on-switch, but
   the two paths now have different buffer models and only the new one is documented as single-buffered.
5. **16-colour double-buffering needs 60 KB of 64 KB.** Not solved, deliberately. It constrains any
   future animation work in 16-colour and the number should be on the table before that is planned.
6. **The mode table's palette is loaded in full on every switch** (16 register writes). Fine at this
   cadence; would matter if a caller ever switched per frame.

### 8 — Follow-up candidates

1. **Resolve the composite-vs-RGB palette-format tension** in `HAL_gfx_init`'s inherited comment and
   values (§7.2) before POP's art palettes are chosen.
2. **Reconcile the buffer models** (§7.4): `HAL_gfx_init` is double-buffered, `HAL_gfx_set_mode` is
   single-buffered. One of them should own the policy.
3. **Enable `HAL_GFX_MODE_SERVICE` in Karateka** if it wants the service — a one-flag change now.
4. **A 16-colour double-buffering decision** when animation needs it (§7.5) — the 60 KB number forces a
   choice: smaller playfield, banked buffers, or 4-colour for animated scenes.
5. **Extend the mode table** to the other GIME modes (640×192×2/4, 160×192×4/16) — the service takes a
   row and a palette per mode; no code change.
6. Standing: the **§2A.3 authorship ruling** (now **twenty-one** deferrals). New idioms surfaced here
   (the `$FF92` VBORD arming requirement, framebuffer-decode rendering for 16-colour) were recorded in
   source comments rather than an idioms file.

### 3 — Reasoning

#### 3A — Phase 1: the precedent held, except where it didn't

`intro_seq.s:140-159` is the worked example: `DISK_BUNDLE_TRK 25` "two tracks", `BUNDLE $3000` = 9,216 B →
`$52FF`, `SAVE_BUF $5400` sited clear of it. Following it rather than inventing a second mechanism was the
right call and cost almost nothing.

**What the precedent did not predict: the bundle could not grow in place.** Two tracks from `$0A00` reach
`$0A00 + 9,216 = $2E00`, and ROOM.BIN's `prog` starts at `$2000` — the load would have written straight over
the engine. So the bundle moved to `$4200`, immediately after the room blob (`$3000..$41FF`), reaching `$65FF`.
The peel buffers moved too: they were at `$5200`, inside the new extent.

| region | extent |
|---|---|
| room blob | `$3000`–`$41FF` |
| **cutscene bundle (2 tracks)** | **`$4200`–`$65FF`** |
| disk parameter block | `$6A00` |
| peel buffers | `$6C00`–`$727F` |
| trace ring / kernel / stack | `$7800` / `$7900` / `$7F00` |

**Headroom, as a number:** the bundle occupied 4,198 B of 9,216 after the move — **5,018 free**, against 70
before. `blit_tab` and `chars_tab` landed at `$423A`/`$4240`, matching the room's `+58`/`+64` offsets.

**D survived**, verified before anything was built on it: 8/8 in-emulator, 0 bytes wrong at both captures
including after a character move, stability agreed, **18.9 Hz — the baseline exactly**. 128 KB and intro green.

#### 3B — Phase 1: the ceiling figure, corrected

`link/pop_engine.link` claimed the program may run to `$25FF`. It is ~174 bytes too generous and **misled three
dispatches** (P3.20 twice, P3.22 once), each of which spent rounds hunting a logic bug in code that was fine.
Measured at P3.22 by adding **dead `rmb` filler** — no code, only size:

```
prog ending $2487   boots, suite 8/8      (the green baseline)
prog ending $2535   image corrupted       (baseline + 175 B of filler)
```

The file now states `$2480` as the practical limit, records how it was measured, documents the signature
(**a garbage probe byte plus ZERO disk reads means LOADM truncated on SIZE**, not a program bug; `$7900` reading
`$FF` is the same fault one step earlier), and points at the disk-resident-track route as the alternative to
growing `prog`. ROOM.BIN currently ends `$23AA` — 214 bytes of real margin.

#### 3C — Phase 2: the discriminating test, and a correction to the dispatch's framing

The dispatch nominated `Pslump` as the discriminating case. **It is not, and I said so before running it.**
`Pslump` exercises the rule's untried EVEN branch, but naive `CharX & 1` *also* predicts EVEN at `CharX=120`,
so it cannot separate them:

| cel | naive `CharX & 1` | the rule | discriminates? |
|---|---|---|---|
| `Pstand` 11 (`$80`, CharX 120) | EVEN | **ODD** | yes — and ODD is correct |
| `Pslump` 1 (`$00`, CharX 120) | EVEN | EVEN | no — both agree |
| `Vwalk` 51 (`$00`, CharX 197) | ODD | **EVEN** | yes — sharpest, still untested |

#### 3D — Phase 2: what Jay's gate actually established

*"the princess looks correct."* The value is not in `Pslump` alone but in the **pair**: `Pstand` needs ODD and
`Pslump` needs EVEN, at the **same character and the same `CharX`**. So:

| hypothesis | killed by |
|---|---|
| parity = `CharX & 1` | `Pstand`: naive says EVEN, correct is ODD |
| **parity is per-character** | **`Pslump` vs `Pstand`: one character, both parities** |

The second was not on my list before the result. It is the rule's central claim — **parity is per-cel** — and it
is what the whole per-cel conversion design rests on. That is the difference between "consistent with" and
"confirmed", and it is exactly what P3.24's postmortem said was missing.

**Peels sized to the widest cel, which blocked Phase 3.** They were sized to the single baked cel (48×5, 43×5)
— correct only while the cel never changes, and changing it is the VM's entire job. Measured across the
cutscene set, each cel converted at its own parity, allowing the byte a sub-byte phase adds:

```
vizier   widest 48 x 10 = 480 B   (cel 62, vturn-10)
princess widest 43 x  8 = 344 B   (cel 7,  pturn-9)
```

An undersized peel does not fail loudly — save writes past its buffer, erase restores garbage — so this would
have surfaced as corruption mid-Phase-3. **`Fdx` is now a record field applied in `co_setup`**
(`col = (x + Fdx + 20)/4`). Every cel drawn so far has `Fdx=0`, so it is a no-op today; the table carries −1…5
and the VM selects such cels immediately.

#### 3E — Phase 3: the interpreter, and the two bugs it exposed

It steps a byte stream where positive = cel and negative = opcode, mutating the P3.22 slot records with no
parallel state. `NextFrame` decides, `FrameAdv` draws, kept distinct. Proven with the state read out of the
machine:

```
first   vizier cel 54 @197   princess cel 11 @120   0 bytes WRONG
second  vizier cel 54 @197   princess cel  1 @112   0 bytes WRONG
stability: all captures agree (0)
```

Between those it selected a different cel, applied `chx`, and looped via `goto`. **`chx` is mirrored by facing**
as the oracle does it: `chx 8` with `CharFace=−1` moved her 120 → **112**, not 128.

**Bug 1 — the peel must be erased with the dimensions it was SAVED with.** `CH_W` changes when the interpreter
switches cels, so erasing `pstand`'s 43×5 save with `pslump`'s 43×6 restored a column that was never saved.
It presented as `$AA` (the uninitialised-peel signature) **and as captures that disagreed** — 127 vs 161 —
because it accumulated. `ch_last` now carries (x, y, w, h) per (character, slot) rather than (x, y).
**Unreachable while the cel was fixed**, which is precisely the space D's tests covered.

**Bug 2 — my checker assumed which cel was drawn.** It composited `pstand` while the VM showed `pslump` and
reported 127/246 wrong when both were correct. It now reads `CH_CEL` from the machine alongside x/y. This is
the *third* variant of one mistake in this project: assume the position (P3.22), assume the input provenance
(P3.22), assume the cel (here). **A checker that assumes any part of the state it is checking cannot tell
"wrong" from "changed".**

**What the demo proves and what it does not.** The dispatch asked for `Vstand` then a short `Vwalk`. **`Vwalk`
cannot run yet** — its cels (48-53) are not baked, and baking them needs the per-cel parity conversion volume
that is E's scope. The sequence uses the baked cels and still exercises cel bytes, `chx` in both directions and
`goto` looping. **`aboutface` is implemented but deliberately not exercised:** it flips `CharFace` and therefore
the required parity, and each baked cel carries one parity. The deferral P3.24 asked for is recorded at
`vs_face` rather than buried.

#### 3F — Phase 3: the pacing is wrong, and why

Measured, not modelled:

| | achieved | target / baseline |
|---|---|---|
| cadence | **3.09 frames/step** | 2.60 (13/5 = `3,3,2,3,2`) — **+19%** |
| frame rate | **16.8 Hz** (3.56 frames) | 18.9 Hz baseline |

**Attributed by ablation, and it matches to two decimals.** The loop now runs **0.84 iterations per video
frame** (1.19 frames per iteration), and `2.60 × 1.19 = 3.09`.

**The cadence table counts LOOP ITERATIONS, not video frames.** That was harmless while the loop was
frame-locked — P3.21's VBL fix made one iteration equal one frame — but the VM's added work pushes some
iterations past a frame, so the equivalence the table silently assumed no longer holds. The measurement is
in the right unit; the *counter* is not.

**Fix direction, not attempted:** pace off the HAL's frame counter (real VBLs) rather than off iterations,
and/or reduce per-frame work. Per HARD-STOP #5 this is reported rather than modelled.

`port_vm_cadence.lua` measures the cadence **off the cel byte** rather than off a counter the VM increments —
a counter would report what the VM believes it did; the cel reports what reached the screen.

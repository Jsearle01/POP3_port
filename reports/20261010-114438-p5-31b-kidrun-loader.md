### 3 — Reasoning
**A. What the 20 s was** (trace). Re-measured at the frame BASIC prints `OK`: 1,206 frames (20.1 s), each
of the five segments landing in order; Jay timed the live runner: *"close enough."* RS-DOS reads a file
one sector per command, and every disk this build makes is interleave 0, so each next sector has just
passed the head. Swept 0..17 with KIDRUN.BIN alone: il=4 is the minimum (9.6 s), il=0 20.2 s.

**B. Why not interleave 4** (trace). The whole build at il=4 vs il=0, suites green both ways: KIDRUN 20.1 →
9.7 s, but the intro's first picture +16.8 s (frame 2986 → 3992) and the driver's drive-engaged total
43.8 → 61.3 s. The driver reads a whole track per command and wants sequential sectors (idiom 29,
karateka's sweep). One disk serves both readers, so the interleave cannot be chosen for one.

**C. What karateka does** (read, karateka read-only). I first said karateka mixes nothing; checked:
`tools/make_decb_boot_disk.sh` and `make_game_dmk.sh` both `--interleave=0`; one small `BOOT.BIN` in the
directory; the game on FAT-reserved raw tracks read by the bootloader. So "both" = Disk BASIC for a small
boot file, the driver for the bulk — not two interleaves. POP's intro already works this way; P5.31's
probe did not, because I shipped it as one 18,460 B DECB file. That was the cause, not the disk.

**D. The layout, and why kd2 moved.** `disk_read_range` reads whole tracks only (`dr_r_count` a multiple
of 18), so every read's END is fixed by its start. The probe's data straddled the driver's parameter block
(`$6A00-$6A06`): kd2 at `$6B00-$77FF` could not be covered by any track-sized read without covering `$6A00`
or the running kernel at `$7900` (the window `$6A07-$78FF` is 3,833 B < 4,608). So kd2 moved to `$2000`
(free in this probe; `$3000` is the staging area/peel, hence the cap):
- read A, tracks 2-3 → `$0E00-$31FF`: prog + kd2 (7,862 B; the tail is staging, unused until later)
- read B, tracks 4-6 → `$3400-$69FF`: xftab + kd1, ending exactly at `$6A00`
- the loader sits at `$3200-$33FF`, between them. LOADM to `$3200` is safe: P5.31's KIDRUN.BIN LOADM'd
  segments up to `$7D50` and read back exact; the `$2488` ceiling is the intro image's (CLAUDE.md §2L).
- the kernel segment is dropped from both images; `kernel_identical_check.py` proves the loader's `$7900`
  is the probe's, byte for byte (1,105 B).

**E. Where the 16.1 s goes** (trace; RAM compared against each raw image every frame):

| | LOADM + |
|---|---|
| loader's LOADM → `OK` (EXEC typed then) | 5.8 s |
| read A's first data / last data | 7.2 / 8.5 s |
| read B's first data / last data | 10.2 / 12.6 s |
| probe status 1 (mode set) | 13.5 s |
| status 2 (tile page in) | 15.5 s |
| first step shown, stepping | 16.1 s |

Old disk, same script: `OK` at 20.1 s, stepping at 23.8 s. **The loader's own LOADM is 5.8 s for 1,223 B**
(the intro's 1,606 B LOADER takes 5.9 s) — Disk BASIC's fixed cost per file, which no interleave-0 file
avoids. The ~1.7 s between reads A and B is the drive being released after A (`disk_read_motor_off`) and
spun up again; see §8.

**§2H.** (1) Second mechanism: the per-file DECB cost vs the per-track driver cost are two mechanisms on
one disk — that is §B. (2) Calling routine: `load_tracks` in the loader, called twice, once per boot.
(3) Prior reports: P3.6 / idiom 29 (sequential is fastest for the driver) — consistent; P5.31 §3G's
load-time claim — corrected in place at `8d6f376`/`fa8f2eb`.

exactly that. I estimated *"about 2 s for the bulk instead of 20 s"*: wrong — the raw reads take ~5.4 s

`DMK_IL` switch from `9c12a12` (I offered; it defaults to 0 and is left in as the comparison tool).

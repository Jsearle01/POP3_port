**Acquisition — P3.1's blocker fell to reading the game's own code.** The aux read failed there because
I used `read_u8($C003)`; the IIe's RAMRD switches are **write**-triggered, and the oracle's own source
says so plainly (`sta RAMRDaux`). The subtler half: `SETDHIRES` leaves the machine **already banked to
aux**, so the "main" grab had been aux all along and the two matched because they were the same bank.
Selecting each bank explicitly settled it.

**The DHR bit structure was determined by controlled experiment, not research or correlation.** For each
4-bit value I synthesised a full 560-dot row carrying only that value, packed it 7 bits per byte across
both banks, wrote it into the running oracle and sampled the rendered frame. Every band came back
perfectly uniform — which proves the bit order (LSB-first), the group order (LSB-first) and the
interleave (aux on even columns) **simultaneously**, since a wrong assumption anywhere would have
produced mixed bands. The interleave independently matches the game's `PutScrByte`.

**The critical finding: the fringing is not in the data.** The same probe showed a single dot at phase 3
rendering across screen dots 2, 3 **and 4** — bleeding into the next group. The game's bytes hold exactly
140 colour values per row; the extra detail on screen is generated by the display. Converting the data
gives colour fields matching the oracle **100%** in interiors and no fringing at all — and this art is
74% edges. Reproducing the look therefore means *inventing* pixels, exactly as Karateka's 4-colour
converter does for single hi-res. Jay chose that path after comparing both.

**And the screen I first converted was the wrong one.** Jay: *"I don't think this is the first screen."*
He was right, and P3.1's own trace said so — `setdhires` → `tpause 44` → `DeltaExpPop`. Measuring
on-screen changes settled it in one run: **frame 306 = the graphic appears (50.6% of sampled pixels),
frame 406 = the text is added (2.0%), frame 687 = the text goes away (2.0%)**. The first screen is frames
306–405; I had sampled 600. Recaptured at 350; palette, overrides, converter, engine and memory map all
carried over untouched.

### 3 — Reasoning

#### 3.1 — Acquisition (AC1)

```
MAIN bank : 6807 non-zero      AUX bank : 6840 non-zero
bytes differing between banks: 7438 / 8192      banks PROVEN distinct
```
The guard from P3.1 was kept: the script refuses to write unless the banks differ and both are non-empty.
It fired correctly twice during development before the switch semantics were understood.

#### 3.2 — The bit structure, by experiment (AC2)

| probe | rendered | predicted |
|---|---|---|
| single dot, phase 0 | dark blue | `0001` = 1 ✓ |
| single dot, phase 1 | dark green | `0010` = 2 ✓ |
| single dot, phase 2 | brown | `0100` = 4 ✓ |
| single dot, phase 3 | red | `1000` = 8 ✓ |
| dots 0,1 | medium blue | `0011` = 3 ✓ |
| dots 0-3 | white | `1111` = 15 ✓ |
| `1010` repeating | grey | `0101` = 5 ✓ |
| `0011` repeating | orange | `1100` = 12 ✓ |

Sixteen bands, every one uniform and every one matching prediction.

#### 3.3 — The palette: measured, then overridden three times

Correlation against the rendered splash gave 11 of 16 at 100%, with the rest filled from a complement
rule (i + 15−i = white). The controlled experiment then produced all 16 exactly — and caught an error the
correlation had missed: grey1 derived as (127,127,127) where the truth is (128,128,128). Those straddle a
CoCo3 quantisation boundary (127 → level 1, 128 → level 2), so grey rendered visibly wrong. **Correlation
gets you near; a controlled experiment gets you exact.**

Then Jay's eye overrode the arithmetic three times, each recorded with its reasoning:

| index | measured | nearest | chosen | why |
|---|---|---|---|---|
| 14 yellow | (191,227,8) | `$32` | **`$30`** | `$32` read lime, `$36` too yellow, nothing between on the red axis — so hold yellow's hue and drop a level |
| 5 grey1 | (128,128,128) | `$38` | **`$07`** | 128 sits 43 from both 85 and 170; the tie broke upward and read too light |
| 10 grey2 | (128,128,128) | `$38` | **`$07`** | same source colour; splitting them would invent a distinction the source lacks |

A grey **dither** ($07/$38 checkerboard) averages to (127,127,127) — arithmetically nearer than either —
and was tried and **rejected on screen**: a checkerboard is a texture, not a colour. Recorded explicitly
because it looks like the obvious clever answer and would otherwise be re-derived.

#### 3.4 — Data-faithful vs display-faithful (AC2)

| | interior agreement | black coverage | asset |
|---|---|---|---|
| oracle | — | 33.8% | — |
| data-faithful | **100%** | 25.0% | 13,440 B |
| display-faithful 280 | — | **30.3%** | 26,880 B |

Two alternatives were rejected by measurement before this choice: mono (66.8% dot agreement) and a
280-window decode with no phase rotation (53.8%, worse than the 140-block's 77.2%).

#### 3.5 — The virtual-resolution contract, and the amendment it needed (AC3, AC5)

Under the display-faithful asset the contract collapses to a straight copy: a source row is 140 bytes =
280 virtual pixels at 4 bits, and the 16-colour mode packs 2 pixels per byte, so 280 virtual pixels are
also 140 framebuffer bytes landing on bytes 10..149 — the +20 px centring, no expansion, no rounding.

**The amendment:** the asset carries **280 distinct pixels**, not 140 doubled. The contract's "140→280 at
its natural 2×" still describes the DATA; it no longer describes the ASSET, because the fringing lives
*between* the data's colour pixels and has nowhere to go at 140.

#### 3.6 — The memory map, moved twice, and a linker that never complained

| | before | after |
|---|---|---|
| program | `$0200` | `$0200-$6B91` |
| kernel | `$3000` | **`$7000`** |
| stack | `$1F00` | **`$7F00`** |
| draw window | `$6000-$DFFF` | **`$8000-$F7FF`** |

`lwlink` placed overlapping sections **three times without a word** — prog `$0200..$7CE1` straight across
the kernel and the draw window. The only symptom would have been run-time corruption. Placement is now
checked against the `.map` after every asset change.

Moving the window to `$8000` means `$FFA7` (CPU `$E000-$FFFF`) is remapped, which P2.6 deliberately
avoided. Two facts make it safe and **both** must hold: `$FF00-$FFFF` is always I/O regardless of the MMU,
and MC3=1 in `$FF90` pins `$FE00-$FEFF`, so the vectors are not remapped either. What is remapped is
`$E000-$FDFF`, which the framebuffer legitimately occupies.

### 7 — Uncertainty flags

1. **The display-faithful asset embeds MAME's NTSC filter.** It is not the game's data and not real
   hardware — it is one emulator's rendering. If MAME's filter changes, or if real hardware differs, the
   art shifts with it. The data-faithful path remains in the converter for that reason.
2. **Every future screen needs an oracle run.** Conversion now depends on capturing the rendered frame,
   so assets cannot be produced from the disk image alone. That is a real pipeline dependency.
3. **The grey redundancy is spent.** Both grey indices now carry `$07`. A screen needing two distinct
   greys would have to revisit this.
4. **`$FFA7` is now remapped** (§3.6). The safety argument rests on two facts both holding; if either
   assumption about MC3 or I/O precedence is wrong, the failure would be spectacular and rare.
5. **The asset is 26,880 bytes and the program region reaches `$6B91`.** The next screen's asset, or any
   growth, collides with the kernel at `$7000` again. There is roughly 1.4 KB of headroom.
6. **Only one screen has been converted.** Whether the palette overrides suit the rest of the intro is
   unknown; they were tuned against this image.

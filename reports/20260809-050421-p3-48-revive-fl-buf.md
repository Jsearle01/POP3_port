### 3 — Reasoning

#### 3A — What was built, and why it was built that way

Three edits, all reverted:

1. **`fl_slot` derived from `HAL_gfx_cur_back`** (`ldb HAL_gfx_cur_back / andb #1 / lslb`) instead of the local
   `fl_buf`. **One home per fact** (P3.31): `room_loop` already reads that byte and passes it to `chars_frame`
   as the character side's slot index, so torch slots and character slots now cannot disagree about which
   buffer is being drawn. **A parallel toggle is what made the original failure silent** — it could drift with
   nothing disagreeing out loud, and did, for thirty dispatches.
2. **The orphaned three instructions deleted**, not made reachable — restoring them would put the parity back
   in two places.
3. **The `fl_buf` declaration removed**, so the toggle cannot be reinstated by reflex.

**P3.17's tearing fix is untouched and was checked first** (AC2). Its change was *"DRAW, THEN WAIT, THEN
FLIP"* — moving `HAL_gfx_swap` out of `flicker` to after `HAL_time_vbl_wait` in `room_loop`, so VOFFSET is
written at the frame boundary rather than mid-screen. **The parity is bookkeeping about which buffer is being
drawn; it does not require the swap to move back.** HARD-STOP #2 does not fire.

#### 3B — The proof, and why it is built to assert rather than to observe

The dispatch's §2 is the load-bearing instruction: *a green suite is not evidence here*, because the suite was
green for thirty dispatches while the discipline was absent. So the tool observes the mechanism:

- **Parity at the point of derivation** — a *write*-tap on `fl_slot` reads `HAL_gfx_cur_back` in the same
  callback, so the two are compared where they are set rather than reconstructed after. **694 agreements, 0
  disagreements.**
- **Per-slot peel writes AND reads** — writes are the SAVE, reads are the ERASE. **Both are required**: a slot
  written and never read is not participating in a restore, which is precisely the property the `:363` comment
  is about. This is what caught slot 3.
- On idioms §10a: a read-tap hit is not proof of *execution* because it also fires on data reads. **Here the
  data read is the measurement** — the peel buffer is data and the erase reading it is the event of interest —
  so no hit is being treated as an instruction.

#### 3C — What the anomaly is, and what I did not determine

Established:

| | |
|---|---|
| `fl_slot` alternates 0 / 2, agreeing with the HAL | **694 / 694** |
| slots 0, 1, 2 saved and restored | **9022 writes / 9022 reads each** |
| slot 3 saved | **9022 writes** (347 frames × 26 B) |
| slot 3 restored | **0 reads** |
| `fl_prev[3]` | written 347, read 347, last value `$09` — **non-zero** |
| `t_prev` at the gate, base-2 frames | **0 skipped, 694 ran** — both torches |

So the gate opens and the erase executes, but its peel pointer does not land in `$230F..$2328`. The candidate
explanations I did **not** discriminate between:

- **A real defect in the erase path** for the odd slot at base 2 — in which case the pre-change code was
  masking it by never using slot 3.
- **An instrument artefact** — the slot-3 read-tap failing to fire for a reason I have not identified. Slots
  0-2 use identical tap construction and do fire, which argues against it, but does not eliminate it.

**I am not guessing between them at this point in the session.** P3.43 §10a exists because taps here have
misled before, and the honest state is that the measurement and the green suite disagree and I have not
resolved which is right.

#### 3D — Why revert rather than commit with a caveat

`wip` may carry incoherent work (§2E), so committing was available. I reverted because the change is not
merely unproven — **it plausibly removes a restore that was previously happening.**

Before: torch 1 always used slot 1, and slot 1 is demonstrably read every frame it is used. After: on half the
frames torch 1 uses slot 3, which is never read. **If the anomaly is real rather than instrumental, the change
converts a working restore into a missing one on alternate frames** — a flame trail accumulating in buffer 1.
The suite cannot rule this out: it passed identically before and after, and I have not shown its capture ever
covers buffer 1.

**A known-latent defect thirty dispatches old is a better tree state than an unproven change that may have
introduced a new one.** The work is fully described here and is ten minutes to reapply once §8.1 is answered.

### 3 — Reasoning

#### 3A — the mapping, from the loader (AC2)

**Decoded from the code that performs it, as required — not from the file sizes.**

```
loadmusic1   lda #34 / sta track / jsr rw18 / db RdSeq,$4e   ;we only want $50-53
]mm          jsr setaux / jmp xmovemusic
loadmusic2   lda #20 / sta track / jsr rw18 / db RdGrp.Inc
             hex 50,51,52,53,00,00,...                        / jmp ]mm
loadmusic3   jmp loadmusic1
```

`rw18` reads an **18-sector RW18 track** through a per-sector page table in which **0 means discard**
[`RW1835.POP.S`: *"If this sector is to be ignored, then change `sta $FF00,Y` to `bit`"*]. So:

| | track | sectors kept | to | then |
|---|---|---|---|---|
| `loadmusic1` (title, epilog) | 34 | **2..5** — `RdSeq` from page `$4e`, only `$50-$53` wanted | `$5000..$53FF` | `xmovemusic` → `$D000` aux |
| `loadmusic2` (game) | 20 | **0..3** — named explicitly | `$5000..$53FF` | same |

**Both load exactly 1,024 B.** `MusicTable = $D000`, `MSYS` at `$D400` — the data is `$D000..$D3FF`.

**★ AND THE VENDORED FILES ARE DIFFERENT KINDS OF THING**, which is what made the sizes "not obviously
agree with the sector lists" (P4.1) for twelve dispatches:

- `MUSIC.SET1` = **4,608 B = a full 18-sector RW18 track image.** The music is **offset 512..1535**.
- `MUSIC.SET2` = **1,024 B = the `$D000` page image alone**, offset 0.

**Verified structurally rather than asserted:** at offset 512+104 — i.e. `MusicTable+$68`, where
`MADRHI` must be — the bytes are `d0 d1 d1 d1 d1 d2 d2 d2 d3 d3 d3 d3 d3`. **Thirteen high bytes,
non-decreasing, all inside `$D0-$D3`.** No other 1,024 B window in the file has that shape (§5).

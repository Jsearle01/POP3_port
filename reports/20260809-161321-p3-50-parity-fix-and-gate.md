### 3 — Reasoning

#### 3A — Part A: what was verified, and with which instrument

The check used is **P3.49's dispatch capture** — `t_peel` sampled at the `erase_tab` / `save_tab` read, which
is the one instruction where "which operation is this" is unambiguous. **Not the range read-tap**, which
HARD-STOP #5 and the dispatch both rule out and which reproduced its blindness again here (slot 3
`$230F..$2328`: writes 9022, reads 0, while the erase demonstrably dispatches against `$230F`). **The known
blind instrument was run and its output ignored, deliberately, so the contradiction stays on the record.**

**P3.17's tearing fix is intact and was confirmed rather than assumed:** that commit moved `HAL_gfx_swap` out
of `flicker` to after `HAL_time_vbl_wait` in `room_loop`, so VOFFSET is written at the frame boundary. Part A
touches only where the parity comes from; the swap's position is untouched, and the room suite's
`startup_gap_small` and two-capture checks pass.

#### 3B — The guard that would have failed open

At P3.49 I added a precondition to the probe runner so it could not measure a stale binary:

```
if [ "$P_PEELBASE" != "0x22C2" ]; then ... Refusing.
```

`$22C2` was the address under the *two-edit* variant I had been measuring. **Part A is the three-edit
variant** — it also deletes `fl_buf`'s byte — which moves `peel_base` to **`$22C1`**. The guard would have
refused the correct build and, worse, a future two-edit build would have satisfied it while a three-edit one
did not.

Re-keyed to reject the **unfixed** value, which is the thing actually being guarded against:

```
if [ "$P_PEELBASE" = "0x22C9" ]; then ... the UNFIXED layout. Refusing.
```

**A guard that enumerates the acceptable states fails open when a new acceptable state appears; one that names
the forbidden state does not.**

#### 3C — Part B: the design, and why it is not typed in

**The specification is settled.** The oracle draws torches, stars, sand, hourglass and characters in one pass
per animation step and flips once (`play → FrameAdv → DoFast`, P3.46b). POP's per-step work is **1.92 VBLs
against a 2.60-VBL step**, so it fits without slicing. Deleting `fl_div` leaves **one change source**, which
is what makes the gate simple — P3.45's 18.4%-only result came from the torches being a second one.

**What is not settled is how `room_loop` learns a step is due**, and this is the crux. The decision lives in
`vm_nextframe`, **inside `chars_frame`, inside the disk-resident bundle**; `flicker` runs *before*
`chars_frame` and must be skipped on a non-step frame. Three routes, and only one survives:

| route | why it fails |
|---|---|
| let `chars_frame` gate itself and return a flag | `flicker` has already run and already advanced the torch |
| reorder to chars-then-flicker | changes draw order; torches would paint over characters, and the room suite reports **"20 behind a character"**, so the overlap is real |
| **give the bundle a `chars_due` entry** | **works** — the room asks before drawing anything |

**The design, fully resolved:**

- **Space exists.** The bundle's self-describing tables sit at fixed offsets from `FLAME_BASE`:
  `flame_draw +0..+17`, `flame_save +18..+35`, `flame_erase +36..+53`, **gap +54..+57**, `blit_tab +58..+63`,
  `chars_tab +64..+65`, compiled cels from +66. **Extending `chars_tab` to `fdb chars_frame,chars_due`** uses
  +66 and shifts only the compiled cels, which are reached through the tables the assembler regenerates. The
  three offsets the room hard-codes (`+0/+18/+36`, and `BLIT_TAB +58`, `CHARS_TAB +64`) do not move.
- **`chars_due`** — `stu vm_now`, `ldd vm_now`, `subd vm_due`, return A=1 when non-negative. Side-effect free;
  it must not touch `cad_idx` or the slot records.
- **`room_loop`** — ask first, then draw:
  `frame_count → U`; `jsr [CHARS_TAB+2]`; if not due `jsr HAL_time_vbl_wait` and loop; if due, the existing
  `flicker` / `chars_frame` / `HAL_gfx_swap` body unchanged.
- **`flicker`** — delete `fl_div` and the divider; set `fl_step` unconditionally, because the routine now runs
  only on a step. **Delete the second cadence, do not retune it.**

**Two traps recorded so they are not rediscovered:**
1. **`vm_nextframe` must still own the step**, or there are two cadences again — `chars_due` asks, it does not
   decide. The `cad_idx` advance stays where it is.
2. **The idle path still needs a VBL wait.** `HAL_gfx_swap` is what currently paces the loop; skipping it
   without waiting spins the CPU and changes nothing on screen.

**Why I stopped here.** That is a new entry point in the bundle, a restructured main loop and a deleted
cadence — on the path whose peel has produced four accumulating bugs, **every one written late in a long
session**. It then needs byte-exactness across separated captures at two memory sizes and a live Jay gate on
two visible changes. **Part A was small, proven, and independently valuable; Part B is not, and it is the tenth
time this hard-stop has been reached.** The previous nine were vindicated: P3.42's decline avoided building on
a premise that was false, P3.47's stop found the dead state, P3.48's revert kept an unproven change out of the
tree, and P3.49 refuted the defect all three had been circling.
